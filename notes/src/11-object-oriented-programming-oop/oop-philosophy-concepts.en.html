OOP · Philosophy & Core ConceptsPhilosophy

1The Philosophy of OOP: Objects and Messages

foundation ★
Definition Object-oriented programming is a paradigm that builds a program out of objects — units that hold their own data and the operations on that data — which cooperate by sending messages to one another. Its philosophy in one line: "program the way we think about the real world." A car, a student or a bank account is a thing that has something (state) and does something (behaviour); OOP writes it the same way.
data + code travel together
An object has three things (Booch) Identity — what makes it this object: two accounts with the same owner and balance are still two objects (different addresses / references).
State — the current values of its attributes (fields, data members).
Behaviour — what it can do: its methods (member functions), which read or change the state.
Message passing — acc1.deposit(500) sends the message "deposit 500" to the receiver acc1: receiver + method name + arguments. The receiver decides how to respond.
Real-world thingState (has)Behaviour (does)In code
Carcolour, engine, speedstart, stop, acceleratefields + methods of Car
Studentname, id, gradesstudy, sitExamfields + methods of Student
Bank accountowner, balancedeposit, withdrawfields + methods of Account
Memory trick "Nouns become classes, adjectives become fields, verbs become methods." Read a problem statement aloud and you have a first class design.
Exam trap Identity is not state. Two objects with equal fields are equal but not identical: in Java a == b compares identity, a.equals(b) compares state.
Worked example ✍ spot the parts "A library lends books to members." Classes: Library, Book, Member. Book state: title, isbn, onLoan. Message: lib.lend(book, member) → receiver lib.
Where it came from Alan Kay, who coined the term, described OOP as "messaging, local retention and hiding of state, and late binding". Those three ideas reappear below as message passing, encapsulation and polymorphism.

2The Four Pillars of OOP

most tested ★
Definition Four principles make a language object-oriented: abstraction (show what, hide how), encapsulation (bundle data with the code that uses it and control access), inheritance (a new class acquires the members of an existing one) and polymorphism ("one interface, many forms"). Classes and objects are the building blocks; the pillars are the principles built on them.
PillarOne-line meaningTool in Java / C++Everyday picture
Abstractionexpose essential features, hide implementationabstract class, interface, public methodssteering + brake, engine hidden
Encapsulationdata + methods in one unit; access controlledclass + private fields + methodsmedicine capsule
Inheritancechild class reuses and extends a parentextends (Java), : public (C++)Car is-a Vehicle
Polymorphismsame call, different behaviour by typeoverloading (compile time), overriding (run time)draw() on circle vs square
Inheritance at pillar level A class is derived from a base class and gets its members: is-a relationship (Dog is-a Animal), unlike has-a = composition (Car has-a Engine). Types and constructor order: next lesson. Java: a class extends only one class but may implements many interfaces.
Polymorphism at pillar level Compile-time (static binding): function / operator overloading — chosen by the argument list. Run-time (dynamic binding): overriding through a base-class reference or pointer; in C++ the function must be virtual. Details: a later lesson.
Memory trick A PIE = Abstraction, Polymorphism, Inheritance, Encapsulation. "Which is not a pillar?" — overloading, class, object, compilation.
Exam trap Some books list only three pillars (no abstraction). Choose four unless the options force three. Class and object are not pillars.
Worked example ✍ name the pillar private int pin; → encapsulation. Savings extends Account → inheritance. Two add() with different parameters → polymorphism.

3Abstraction vs Encapsulation vs Data Hiding

frequently confused ★
Definition Three words, three different jobs. Abstraction is a design idea: decide which features the outside world needs and ignore the rest. Encapsulation is an implementation mechanism: wrap the data and the methods that use it into one class. Data hiding is the protection step inside encapsulation: make the data private so only the class's own methods can touch it.

Memory trick "Abstraction is the menu, encapsulation is the kitchen door, data hiding is the lock on it." The customer orders from the menu and never walks into the kitchen.
Exam trap Encapsulation ≠ data hiding. A class with all-public fields is still encapsulated (bundled) but hides nothing. And private is a compile-time check, not security: Java reflection can still read it.
Worked example ✍ classify "Shows only essential features" → abstraction. "Wraps data and functions into a single unit" → encapsulation. "Prevents direct access to fields" → data hiding.

4Advantages of OOP over Structured Programming

written favourite ★
Definition Structured (procedural) programming — C, Pascal, FORTRAN — splits a problem top-down into functions, and data moves freely between them, often as globals. OOP builds bottom-up from classes, keeping each piece of data inside the object that owns it. The advantages all follow from that one change: data stays with its code.
AspectStructured / procedural (POP)Object-oriented (OOP)
Design approachtop-downbottom-up
Unit of programfunction / procedureclass and object
Emphasisalgorithm (what to do)data (what exists)
Data and functionsseparate; global data sharedbundled (encapsulation)
Data securitylow: no access specifiershigh: private / protected / public
Reusefunctions and librariesalso inheritance and composition
Adding a featureoften edit existing functionsadd a subclass; old code untouched
Best forsmall programs, drivers, firmwarelarge, long-lived systems
ExamplesC, Pascal, FORTRAN, COBOLC++, Java, C#, Python, Smalltalk
Seven advantages to write ① data hiding · ② reusability (inheritance, composition) · ③ modularity — each class debugged alone · ④ easy maintenance · ⑤ extensibility — new subclass, old code untouched · ⑥ flexibility (polymorphism) · ⑦ real-world modelling, scalability.
Exam trap POP is not "no reuse": functions and libraries are reuse. OOP adds reuse with extension. OOP also has costs: larger programs, extra indirection, a steeper design effort — not best for a 50-line script. Good design = low coupling, high cohesion.
Memory trick "Top-down cuts the task; bottom-up builds the things." Coupling = how much classes lean on each other (keep it low); cohesion = how focused one class is (keep it high).
Worked example ✍ the cost of global data A C payroll keeps salary[] global; 30 functions touch it. One salary turns negative: all 30 functions are suspects. In OOP only Employee.setSalary() can change it, and it rejects negatives.

5History of OOP; Pure vs Hybrid Languages

MCQ facts
Definition OOP began in Norway with Simula 67 (Ole-Johan Dahl and Kristen Nygaard), the first language with classes, objects, inheritance and virtual procedures. Smalltalk at Xerox PARC (Alan Kay) made "everything is an object" the rule. C++ (Bjarne Stroustrup, Bell Labs) and Java (James Gosling, Sun) took the idea mainstream.

OOP · Philosophy & Core ConceptsClasses & objects

6Classes and Objects

foundation ★
Definition A class is a user-defined type: a blueprint that declares data members (attributes) and member functions (methods). An object is an instance of a class — a region of memory holding one set of those attributes. The class is a logical entity; the object is a physical one. Memory for instance data is allocated per object, not when the class is declared.
class Student { String name; // state int age; // state void display() { // behaviour System.out.println("Name: " + name + ", Age: " + age); } } public class Main { public static void main(String[] args) { Student s1 = new Student(); // object s1.name = "Alice"; s1.age = 20; s1.display(); // Name: Alice, Age: 20 } }
PointClassObject
What it isblueprint, user-defined typeinstance of that type
Entitylogicalphysical (occupies memory)
How manydeclared oncecreated many times
Created byclass keywordnew (Java); also Student s; (C++)
Field memorynone (static members excepted)one copy of every non-static field
Memory trick "Class is the house plan; objects are the houses." You cannot live in a plan, and every house has its own furniture (fields) but the same rooms (methods).
Exam trap In Java Student s1; creates only a reference (null), no object; new makes the object. In C++ Student s1; does create an object. C++ sizeof an empty class = 1, never 0.
Worked example ✍ count objects a = new Student(); b = a; plus Student c; → objects: 1; references: 3.
Same class in C++ class Student { public: string name; int age; void display(); }; — without public: every member is private. Methods are stored once, shared by all objects.

7Access Specifiers: Java and C++

highest-yield ★
Definition Access specifiers (Java: access modifiers) set who may use a member. They are how a class enforces data hiding. Java has four levels — private, default (no keyword, "package-private"), protected, public; C++ has three keywords — private, protected, public, plus friend to grant exceptions.

Memory trick Java, widest last: "Private Dogs Protect People" = private → default → protected → public. C++: "class keeps secrets, struct tells all."
Exam trap Java default ≠ C++ default. Java default = package; C++ class default = private. Java protected is wider than default (adds subclasses elsewhere). static, final, friend are not access specifiers.
Worked example ✍ who can read x? package a; public class P { protected int x; } Class Q in a: yes. R extends P in package b: yes, as this.x; via new P().x: no. S in b, not a subclass: no.

OOP · Philosophy & Core ConceptsEncapsulation in code

8Encapsulation in Code: Getters, Setters, Validation

programming question ★
Definition Encapsulation = bundling data and the methods that operate on it into one class, and restricting direct access to the data. The standard recipe: make every field private, expose public getters (accessors) to read and setters or operation methods (mutators) to change, and put the validation inside them so the object can never hold an invalid state.
class BankAccount { private String owner; private double balance; // hidden public BankAccount(String o, double b) { owner = o; balance = b > 0 ? b : 0; } public void deposit(double amt) { if (amt > 0) balance += amt; } public boolean withdraw(double amt) { if (amt <= 0 || amt > balance) return false; // refused balance -= amt; return true; } public double getBalance() { return balance; } public String getOwner() { return owner; } public void setOwner(String o) { if (o != null && !o.isEmpty()) owner = o; } }
Worked example ✍ trace the balance BankAccount a = new BankAccount("Rahim", 1000);
a.deposit(500); → 1500
a.withdraw(2000); → false, still 1500
a.withdraw(300); → 1200
a.deposit(-50); → ignored, 1200
a.balance = 9999; → compile error: balance has private access
Final a.getBalance() = 1200.0
What encapsulation buys Integrity — no negative balance can ever exist. Read-only fields — a getter with no setter. Freedom to change — store balance in paisa as long tomorrow; callers of getBalance() never notice. One place to debug — every change passes through three methods.
MemberAccessKindWhy
balance, ownerprivatefielddata hiding
getBalance(), getOwner()publicgetter / accessorread without exposing the field
deposit(), withdraw(), setOwner()publicmutatorchange only after a check
Memory trick "Fields private, methods public, checks inside." Three words for every encapsulation program you will ever write.
Exam trap A public setter with no check is encapsulation in name only. private is per class, not per object: one Account method may read another Account's balance.
C++ version Same design: class BankAccount { double balance; public: … }; — balance is private by default; the getter is marked const.

9Static vs Non-Static Members

output questions ★
Definition A static member belongs to the class: one copy, shared by every object, existing even when no object exists, accessed as ClassName.member. A non-static (instance) member belongs to each object: every object has its own copy. A static method has no this, so it cannot touch instance members directly.
class Counter { static int count = 0; // one, shared int id; // one per object Counter() { count++; id = count; } } // in main(): Counter c1 = new Counter(); Counter c2 = new Counter(); Counter c3 = new Counter(); System.out.print(c1.id + " " + c3.id + " " + Counter.count); // Output: 1 3 3

Memory trick "Static = the class's notice board; instance = each student's notebook." Why is main static? The JVM calls it before any object exists.
Exam trap Inside static void f(), id++ or this.id is a compile error; new Counter().id is fine. C++ needs one definition outside: int Counter::count = 0; Static blocks run once, before any constructor.
Worked example ✍ sizeof class A { int x; static int y; void f(); }; with 4-byte int: sizeof(A) = 4 — static y and function f are not in the object. Empty class: 1.
