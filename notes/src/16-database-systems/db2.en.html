DBMS · Query LanguagesRelational algebra

1Relational Algebra (RA): the Eight Operators

most tested ★
Definition Relational algebra is the theoretical language of queries: every request is written as a sequence of operations applied to relations, and the result of one step is the input of the next. It has five primitive operations (σ, π, ρ, ×, and the assignment) from which the rest — join, intersection, division — are derived. Every step returns a relation, so steps can be chained freely.

Derived operations Everything that is not primitive is built from the five: θ-join = σA=B(R × S) · natural join = θ-join plus automatic removal of the duplicated join attribute · intersection = A − (A − B) · rename is primitive, but ρ is what makes a self-join legal.
Worked example ✍ the set operators A = {1, 2, 3}, B = {3, 4} → A ∪ B = {1,2,3,4} (4, the 3 appears once) · A − B = {1,2} · A ∩ B = {3} · A × B = 3 × 2 = 6 tuples, all distinct.
∪, ∩ and − need union-compatible relations (same attributes, same domains) and never repeat a tuple. The product needs no common attribute name — which is why ρ comes before Students × Courses.
Memory trick "Sigma picks rows, pi picks columns." σ is the letter you point at a line of a table with; π is used in a list. In SQL they are WHERE and SELECT — never the other way round.
Exam trap σ does not change the number of columns and π does not change the number of rows (it may remove duplicates). "Which operator drops a column?" → π. "Which operator drops a row?" → σ. And ρ changes nothing at all: only the label.

Exam trap The Cartesian product of these two relations is 4 tuples, not 2 and not 3: rows × rows. In general a product of m rows and n rows gives m × n rows — a 3-row and a 3-row relation give 9.
Worked example 1 ✍ "List the name and department of every CSE student."
RA: π name,dept (σ dept='CSE'(Students))
SQL: SELECT name, dept FROM Students WHERE dept='CSE';
Read the RA inside out: the innermost bracket is evaluated first, so σ filters and π then trims the columns.
Worked example 2 ✍ "Show every student paired with every course."
RA: π name,cname (Students × ρ cname/name(Courses))
SQL: SELECT s.name, c.name FROM Students s, Courses c;
ρ is mandatory: after the product both relations have an attribute called name, and a relation may not carry two attributes of the same name.
Exam trap ✍ the classical pair A paper offers σ name (Students) and π dept (Students). The first is a type error: name is an attribute, not a predicate, so σ needs a condition while π needs a list of attributes. And "π removes duplicates" is true of RA — plain SQL's SELECT keeps duplicates unless you write DISTINCT.

3Product, Rename and Join — and Translating to SQL

join is the favourite ★
The join formula θ-join R ⋈A=θB S ≡ σA=θB(R × S) · natural join R ⋈ S joins on every attribute the two relations share by name, then drops the duplicate copy.
Why ρ exists: a relation may not carry two attributes of the same name, so Emp × Emp is illegal until one copy is renamed — which is also why every self-join needs two aliases.
Memory trick "Product first, then pick." That one sentence gives you the join, the semi-join and every θ-join you will be asked to expand. A WHERE-clause query looks like "join first, filter after" — the optimiser silently reorders it into exactly this shape.

Exam trap RA works on sets, SQL on bags, so the same question may return different row counts from the two languages — a deliberate, examinable difference, not a bug. And because SQL is declarative the user does not choose the order of operations: the optimiser does, by pushing selections down towards the leaves so the huge product never happens.

Exam trap WHERE filters rows before grouping; HAVING filters groups after it. That is the whole difference, and only HAVING may use an aggregate such as HAVING COUNT(*) > 5.
Memory trick + good to know "Where before, having after." Where comes When rows are still rows. HAVING without GROUP BY is legal too: the whole table is one group, so SELECT COUNT(*) FROM Emp HAVING COUNT(*) > 5 returns either one number or nothing.

5Aggregate Functions and the NULL Rules

every exam asks ★
AggregateReturnsNULL inside the columnEmpty set
COUNT(*)number of rowscounts them anyway0
COUNT(col)number of non-NULL values of colskipped0
SUM / AVG(col)total / mean of the non-NULL valuesskipped — never read as 0NULL
MIN / MAX(col)smallest / largest non-NULL valueskippedNULL
only COUNT(*) sees NULL
Worked example 1 ✍ COUNT T(a) holds 1, NULL, 3, NULL, 5.
SELECT COUNT(*), COUNT(a) FROM T; → 5, 3
COUNT(*) counts rows, so the two NULL rows are counted; COUNT(a) counts values of a, and a NULL value is not a value.
Worked example 2 ✍ AVG R(score) holds 10, NULL, 20.
SELECT AVG(score) FROM R; → (10 + 20) / 2 = 15
Every aggregate except COUNT(*) ignores NULL; reading it as 0 would give 10 — the wrong answer.
Worked example 3 ✍ GROUP BY + HAVING Sales(region, amount) = ('N',100), ('N',200), ('S',50), ('S',70), ('E',300)
SELECT region, SUM(amount) FROM Sales GROUP BY region HAVING SUM(amount) > 150;
Sums: N = 300, S = 120, E = 300. Only N and E pass 150 → 2 rows.
Exam traps ✍ three of them 1. AVG over 10, NULL, 20 is 15, not 10 — NULL is unknown, not zero. 2. COUNT(*) on an empty table is 0, but AVG, SUM, MIN and MAX return NULL. 3. A predicate on NULL is unknown, never true, so WHERE a > 0 drops those rows silently.
Memory trick "Star sees every row; a column sees only real values." The asterisk stands for the whole tuple, so a row that exists is counted even when one of its values is missing. Read COUNT(*) as "count the rows", COUNT(col) as "count the answers".

INNER JOIN ✍ SELECT e.eid, d.name FROM Emp e JOIN Dept d ON e.dept_id = d.dept_id;
eid 1 → 10 IT · eid 2 → 20 HR · eid 4 → 10 IT. eid 3 has NULL, and NULL = 10 is not true, so it is dropped; dept 30 has no employee. → 3 rows
LEFT and RIGHT JOIN ✍ LEFT = 3 matches + the unmatched employee padded → 4 rows: (1,IT) (2,HR) (3,NULL) (4,IT). RIGHT = 3 matches + the unmatched department padded → 4 rows: (1,IT) (2,HR) (4,IT) (NULL,Finance).
FULL OUTER and CROSS JOIN ✍ FULL OUTER = 3 matching pairs + 1 unmatched Emp row (eid 3) + 1 unmatched Dept row (30 Finance) = 3 + 1 + 1 = 5 rows; the formula is INNER + LEFT-only + RIGHT-only. CROSS JOIN is 4 rows × 3 rows = 12 rows, every row of one table against every row of the other with no condition at all; in general m × n, so two 3-row tables give 9.
SELF JOIN A relation joined to itself under two aliases, to relate rows inside one table — an employee to her manager. Give Emp two more columns, name and mgr_id (the manager's eid), then:
SELECT a.name AS emp, b.name AS mgr FROM Emp a JOIN Emp b ON a.mgr_id = b.eid;
Two aliases are mandatory: without them the condition would compare a column with itself.
Exam trap ✍ the NULL one An employee with a NULL dept_id is in no inner-join and no right-join result; it survives a LEFT and a FULL OUTER join, padded with NULLs. "Why did my row disappear?" → because NULL never equals anything, so the ON condition is unknown, not true.
Memory trick Read the keyword as a promise about the first-named table. LEFT: keep everything on the left, pad the right. RIGHT: swap the word. FULL OUTER: keep everything on both sides. INNER: keep only what agrees. CROSS: no promise at all.

7Join Patterns, Subqueries and Where the Rest Lives

written pattern ★
Pattern: every department, including those with no employees The default join drops them, so ask for them with LEFT JOIN and count the child column, not *.
SELECT d.dept_name, COUNT(e.emp_id) AS employee_count FROM Department d LEFT JOIN Employee e ON e.dept_id = d.dept_id GROUP BY d.dept_id, d.dept_name ORDER BY employee_count DESC;
Exam traps ✍ two counts, and WHERE that kills a LEFT JOIN COUNT(e.emp_id) skips the NULLs the outer join produced and correctly gives 0 for an empty department, while COUNT(*) counts the padded row and wrongly gives 1; grouping by dept_id as well as dept_name keeps two departments that share a name apart. And a condition on the right table placed in WHERE is evaluated after the join and discards the padded rows, quietly turning your LEFT JOIN into an INNER JOIN — put it in ON instead.
Three kinds of subquery Scalar — one value used in a comparison: WHERE salary > (SELECT AVG(salary) FROM Emp). IN / EXISTS — a set, or true/false: WHERE id IN (SELECT emp_id FROM Emp). Correlated — references the outer row, so it is re-evaluated once per outer row: WHERE e2.dept_id = e.dept_id.
SELECT MAX(salary) AS second_highest -- 2nd highest DISTINCT salary FROM Employee WHERE salary < (SELECT MAX(salary) FROM Employee); -- NULL if there is none -- and, above the average of the employee's OWN department: SELECT e.name, e.salary, d.dept_name FROM Employee e JOIN Department d ON d.dept_id = e.dept_id WHERE e.salary > ( SELECT AVG(e2.salary) FROM Employee e2 WHERE e2.dept_id = e.dept_id );
Exam traps ✍ three of them 1. The correlated subquery runs once per outer row, giving e's own department average; a derived table pre-computing each average is usually the faster plan. 2. The second-highest query uses <, not ≤, so it is right when the top salary repeats, and gives NULL when all salaries are equal. 3. NOT IN (subquery) returns no rows if the subquery holds one NULL — prefer NOT EXISTS.

Written question Explain the fundamental operations of relational algebra on Students(id, name, dept) and Courses(cid, name). Distinguish DDL, DML, DCL and TCL, and say exactly what DROP, DELETE, TRUNCATE and ALTER each do. Then, for Emp = (1,10),(2,20),(3,NULL),(4,10) and Dept = (10,'IT'),(20,'HR'),(30,'Finance'), give the row count of INNER, LEFT, RIGHT, FULL OUTER and CROSS JOIN and explain why employee 3 never appears in an inner join. 10 marks
  1. RA operators (2) — σ keeps rows meeting a condition, π keeps columns and removes duplicates, ρ renames, × pairs every row of one relation with every row of another (2 × 2 = 4), ∪ − ∩ are the set operators, and ⋈ is derived as σ(R × S). 2
  2. Command families (2) — DDL (Definition) on structure: CREATE, ALTER, DROP, TRUNCATE. DML (Manipulation) on rows: SELECT, INSERT, UPDATE, DELETE. DCL (Control) on privileges: GRANT, REVOKE. TCL (Transaction Control): COMMIT, ROLLBACK, SAVEPOINT. 2
  3. The four commands (2) — DROP removes structure and data; DELETE removes rows, optionally by WHERE, keeping the structure; TRUNCATE removes all rows, keeps the structure, allows no WHERE; ALTER changes the structure and keeps the data. 2
  4. Row counts (1) — INNER 3, LEFT 4, RIGHT 4, FULL OUTER 5 = 3 + 1 + 1, CROSS 4 × 3 = 12. 1
  5. Why employee 3 disappears (2) — its dept_id is NULL and NULL = 10 is unknown, not true; an inner join keeps a row only when the ON condition is true. It survives LEFT and FULL OUTER, padded with NULLs. 2
  6. Where vs having (1) — WHERE filters rows before grouping; HAVING filters groups after GROUP BY, and is the only one that may use an aggregate. 1
