DBMS · Functional DependenciesFDs & notation

1Functional Dependencies: What A → B Really Means

foundation of all ★
Definition R satisfies the functional dependency X → Y when every two tuples that agree on X also agree on Y. X is the determinant, Y the dependent; read A → B as "A determines B". Example: StudentID → Name — knowing the ID settles the name, so two rows sharing an ID can never carry different names. An FD is a statement about what a relation means, not about today's rows.
TypeRuleExampleNote
TrivialY ⊆ X(StudentID, Name) → Namealways true
Non-trivialY ⊄ XStudentID → Namethe only ones that matter
FullY needs the whole of X(StudentID, CourseID) → Gradewhat 2NF insists on
PartialY needs only part of XStudentID → StudentName, key (StudentID, CourseID)breaks 2NF
TransitiveA→B and B→C give A→CStudentID → DeptID → DeptNamebreaks 3NF
Memory trick "An arrow is a promise, not a coincidence." If A → B, the database must never hold two rows with the same A and different B — that is why StudentID is a key candidate, and why "same student, two names" is a design error.
Exam trap ✍ two 1. (A, B) → A is trivial and true in every relation — no information at all. 2. The arrow is one-way: StudentID → Name never licenses Name → StudentID, because two students may share a name.
Normalization Normalization is the process of reducing redundancy and improving data consistency by decomposing a badly designed relation into smaller ones, each obeying a normal form. The ladder is cumulative: 1NF → 2NF → 3NF → BCNF, each rung adding one condition to the one below.
Why bother? A relation in BCNF stores each fact in exactly one place, which removes the three anomalies — update, insert and delete. The price is extra joins at read time.

2Attribute Closure, Candidate Keys and Superkeys

where the marks are ★
Attribute closure X+ The set of every attribute you can derive from X using F repeatedly. X is a key of R iff X+ = R. Start with X, then keep adding any Q for which some FD P → Q has P already inside the set, until nothing new appears.
X⁺ = X repeat: for every FD P → Q in F: if P ⊆ X⁺ : X⁺ ← X⁺ ∪ Q until X⁺ stops growing
Worked example 1 ✍ the classic closure R(A, B, C, D, E) with F = {A→B, BC→D, D→E}.
start {A, C} → A→B (A is in) → {A, B, C} → BC→D (B, C in) → {A, B, C, D} → D→E → {A, B, C, D, E} = R, so {A,C}⁺ = {A,B,C,D,E} and AC is a key. With all five attributes in, every FD fires, so it has stopped growing.
Superkey · candidate key · prime attribute A superkey is any attribute set whose closure is all of R — AB is one above, since {A,B}+ = {A,B,C,D,E}. A candidate key is a minimal superkey: no proper subset still closes R. An attribute is prime if it belongs to some candidate key.
Worked example 2 ✍ the superkey trap R(A, B, C, D) with F = {A→B, B→C, C→D}. A+: A → {A,B} → {A,B,C} → {A,B,C,D} = R, so A is a superkey; being a single attribute it is minimal, so A is the candidate key. A also appears on no right-hand side, so every key of R must contain A. Then AB is a superkey but not minimal (drop B and A alone still closes R), so AB is not a candidate key. And B+ = {B, C, D} — A can never be reached from B.
Exam trap ✍ minimal is the whole question "Which is the candidate key?" is not "which set determines all attributes?" — that is the superkey, and there is usually more than one. Always test minimality second: remove one attribute, recompute the closure, and if it is still all of R the set was too big. R(A,B,C,D) above has superkeys AB, AC, AD, ABC, ABD, ACD, ABCD — and exactly one candidate key, A.
Memory trick "Super is a superset; candidate is the smallest one inside it." And "prime = in some key", not "in every key" — in R(A,B,C) with key A, only A is prime even though A is the sole key. Prime/non-prime is the exact test that separates 3NF from BCNF.

3First and Second Normal Form

the two easy rungs ★
1NF — First Normal Form Every attribute holds a single atomic value. No repeating groups, no lists or arrays inside a cell, no "one row, many facts" columns. A cell is atomic if it cannot usefully be split into several independent values.
Before 1NFStudentIDCourses

After 1NFStudentIDCourse

Exam trap The comma-separated list breaks three rules at once: it is not atomic, it is a repeating group, and it hides a second fact per row. You cannot index CSE101 without string surgery, and "how many courses does 101 take?" needs a LIKE guess. The fix costs one extra row and nothing else — always take it.
2NF — Second Normal Form R is in 2NF iff it is in 1NF and no non-prime attribute depends on only part of a composite candidate key. Partial dependency is impossible when the key is a single attribute, so 2NF only ever bites on composite-key tables.
Worked example ✍ before 2NF Key is the composite (StudentID, CourseID).
(StudentID, CourseID) → StudentName, Instructor, Grade
Problems: StudentName depends on StudentID alone (partial); Instructor depends on CourseID alone (partial). Only → Grade needs the whole key, so only it stays behind.

Exam trap ✍ two 1. A partial dependency is defined against a composite key; if you are asked about a relation whose key is a single attribute, 2NF is automatically satisfied and the real question is 3NF. 2. The split must be lossless: here R1 ∩ R2 = {StudentID}, and StudentID → Student (the whole of R1), so joining the three tables reproduces the original rows exactly — nothing is invented, nothing is lost.
Memory trick "Split by the arrow, not by the column." Draw the FDs; every arrow whose tail is only half the key is a partial dependency, and the head of that arrow moves into a table of its own keyed by that tail. 1NF splits by value (one fact per cell); 2NF splits by dependency (one fact per table).

DBMS · Functional Dependencies3NF & BCNF

4Third and Boyce–Codd Normal Form

the tested pair ★
3NF — Third Normal Form R is in 3NF iff it is in 2NF and no non-prime attribute depends transitively on the key: for every FD X → A with A non-prime, X must be a superkey. In words: no attribute may depend on another attribute that is not itself part of the key.
Worked example ✍ the genuine 3NF violation Before — Student(StudentID, Name, DeptID, DeptName), key StudentID:
StudentID → Name, DeptID and then DeptID → DeptName
so StudentID → DeptID → DeptName. DeptID is not part of the key, yet DeptName hangs off it: a transitive dependency on a non-key attribute. After — Student(StudentID, Name, DeptID·FK) plus Department(DeptID, DeptName). Now DeptName is stored once per department, no matter how many students sit in it.
BCNF — Boyce–Codd Normal Form R is in BCNF iff for every non-trivial FD X → Y, X is a superkey. In the shortest exam phrasing: every determinant must be a candidate key. It is strictly stronger than 3NF — 3NF only demands this when the dependent is non-prime.
Worked example ✍ a BCNF violation that 3NF cannot remove Consider R(CourseID, Semester, Instructor) with (CourseID, Semester) → Instructor and Instructor → CourseID. Instructor is a prime attribute — it sits in no candidate key here, but the relation is still only 2NF, because the determinant Instructor is not a superkey. Check each side: neither CourseID alone nor Semester alone closes the relation, so the determinant (CourseID, Semester) is not a superkey either. BCNF solution: split — Instructor(CourseID, Instructor) keyed by Instructor, and Offering(CourseID, Semester).
Exam trap ✍ three 1. 3NF says "every non-prime attribute depends on the key"; BCNF says "every determinant is a key". A relation can satisfy 3NF and still fail BCNF exactly when a transitive chain runs through a prime attribute. 2. The single-attribute key case has no partial dependency at all, so it can be in 2NF while still failing 3NF — the two rungs test different things. 3. BCNF is not the top of the ladder: a 4NF exists for multi-valued dependencies. "The highest normal form" in an MCQ still means BCNF.
Memory trick "1NF one value, 2NF whole key, 3NF no detour, BCNF key on every arrow." Read BCNF as a rule about the left-hand sides: walk through every FD in F and ask "is this determinant a key?" If any answer is no, split that relation.

5The Ladder in One Table — and How Far Up It Goes

memorise the table ★
Normal formRequirementIn plain words
1NFatomic values, no repeating groupsone fact per cell
2NF1NF + no partial dependencynothing hangs off half a composite key
3NF2NF + no transitive dependencynothing hangs off a non-key attribute
BCNF3NF + every determinant is a candidate keyevery arrow starts at a key
Worked example ✍ "the highest normal form" R(A, B, C) with F = {A→B, B→C}, and A its only candidate key.
Keys. A appears on no right-hand side, so every key contains A. A+ = {A, B, C} = R, and A is one attribute, so A is the sole candidate key and the only prime attribute.
2NF? The key is a single attribute, so no partial dependency can exist. R is in 2NF.
3NF? A→B→C is transitive: in B→C, B is not a superkey and C is not prime. So R violates 3NF and BCNF too. Answer: 2NF. Decompose: R1(A, B), R2(B, C).
How to answer any "highest normal form" question Four moves, in order: 1. find the candidate keys (closures + minimality); 2. list the prime attributes; 3. if the key is composite, look for partial dependencies — if any, stop at 1NF; 4. otherwise look for a transitive dependency on a non-key attribute — if any, stop at 2NF; if none but some determinant is not a key, stop at 3NF; otherwise BCNF.
Memory trick for the whole ladder "Atomic, All-key, Away-from-key, BCNF." 1NF is about values, 2NF about the key's parts, 3NF about non-key detours, BCNF about the determinants themselves. Each rung is "the one below, plus one more clause" — so a relation in BCNF is automatically in all three below it, never the reverse.
Exam trap ✍ Students often answer "3NF" whenever a transitive dependency exists, forgetting that 3NF only forbids a transitive dependency whose destination is non-prime. And they often call AB the candidate key when A alone already closes the relation — minimality, not size, is the test. Check prime membership before you write "3NF".

6Decomposition: Lossless Join and Dependency Preservation

prove or it failed ★

Splitting a relation is a legitimate normalisation only if it is lossless (no information invented or destroyed) and dependency-preserving (the FDs can still be checked without joining).

The lossless-join rule For R → R1, R2 the join is lossless iff
(R1 ∩ R2) → R1  or  (R1 ∩ R2) → R2
Read it as: the attributes the pieces share must be a key of at least one of them. If the shared attribute decides one whole side, every original tuple has a definite partner and nothing is fabricated or lost.
Dependency preservation The decomposition is dependency-preserving iff the union of the projections of F onto R1 and onto R2 is exactly F — in practice, iff every FD in F lives entirely inside one piece and can be enforced there alone, with no join.
Worked example ✍ the standard two-part answer R(A, B, C) with F = {A→B}, decomposed into R1(A, B) and R2(A, C).
Lossless? R1 ∩ R2 = {A}, and A→B means A→R1, so the common attribute A is a key of R1. The first alternative holds → lossless: every original tuple has one A-value, hence exactly one R1 row and one R2 row to pair.
Preserved? The only FD in F is A→B and it lies entirely inside R1, so it can be enforced there with no join → dependency-preserving.
Exam trap ✍ the lossy counter-example Take the same R(A, B, C) with F = {A→B} but decompose it wrongly, into R1(A, C) and R2(B, C). Now R1 ∩ R2 = {C}, and C determines neither R1 nor R2, so the rule fails: the join is lossy — pairing C = 3 from R1 with C = 3 from R2 produces a row (3, 3) that was never in R. The pieces must be split so the shared attribute is a key on one side; sharing a mere foreign key is not enough.
Exam trap ✍ lossless ≠ preserved The two tests answer different questions and a decomposition can pass one and fail the other. A split can be lossless yet force you to join to check A→B, leaving the database unable to police the constraint. A split can preserve every dependency yet be lossy — which silently corrupts data. Give both verdicts separately.
Memory trick "Lossless asks about the overlap; preservation asks about the arrows." Overlap: the shared columns must decide one whole side. Arrows: every FD must sit inside one side. Neither test needs the data — the FDs alone decide it, which is why both can be examined in a written paper.

the standard written answer ★
StudentIDNameDeptIDDeptNameCourseIDCourseNameGrade

What is wrong with this one table It is already in 1NF — every cell holds a single value. But the key is the composite (StudentID, CourseID), and the table repeats three facts: Alice is written twice, 10 / CSE is written twice, and a course name would be written once per student. A student's name and a department's name each live in several rows, and any one of those rows can disagree with the others.
The three anomalies it causes Update — rename Alice and you must edit every row she appears in; miss one and the database holds two names for student 101. Insert — a new department with no student cannot be recorded, because there is no StudentID to put beside it. Delete — delete Alice's only enrolment row and you lose her name and the fact that department 10 exists.
Step 1 — 1NF ✍ Already satisfied: each column holds one atomic value and the grade belongs to the pair (student, course), not to the student. Nothing to do.
Step 2 — 2NF ✍ The key (StudentID, CourseID) is composite, and three non-key attributes depend on only half of it: StudentID → Name, CourseID → CourseName and StudentID → DeptID are all partial, while (StudentID, CourseID) → Grade is full. Split each partial dependency into its own table.
Step 3 — 3NF ✍ The genuine remaining violation is the transitive chain StudentID → DeptID → DeptName inside Student(StudentID, Name, DeptID, DeptName): DeptID is not part of the key, yet DeptName hangs off it. Moving DeptName out into its own Department table is exactly what removes it — that is the whole content of the 3NF step, and it is why Department must appear in the final design.

The final design, and what it buys Four relations: Student(StudentID, Name, DeptID) · Department(DeptID, DeptName) · Course(CourseID, CourseName) · Enrollment(StudentID, CourseID, Grade). Grade stays with the pair it describes, a department's name is stored once, a course name is stored once. Renaming a student is now a single row update, a new empty department can be inserted without inventing a student, and deleting an enrolment cannot take a department with it.

8Anomalies, Denormalization and the Trade-off

the "why" questions ★
The three anomalies, named An anomaly is a wrong update that becomes possible only because the same fact is stored in several places. There are exactly three kinds, and a written question usually wants all three by name.
Update anomaly ✍ A fact must be changed in every copy or the relation becomes self-contradictory. Changing Alice's name means editing each row where 101 appears; one forgotten row leaves two names for the same student, and nothing in the schema stops it.
Insert anomaly ✍ A perfectly valid fact cannot be stored because the key demands a companion fact that does not exist yet. A brand-new department with no students has no StudentID to accompany it.
Delete anomaly ✍ Deleting one row silently removes facts that had nothing to do with it. Removing Alice's only enrolment row deletes her name and the existence of department 10 as well.
Benefits of normalisation 1. Less redundancy, so less disk and fewer copies to keep in step. 2. Better integrity — each fact has one home, so a single update is the whole update. 3. Fewer update, insert and delete anomalies. 4. Smaller, more meaningful tables, so indexes and joins are cheaper to plan.
Denormalization — the deliberate undo Denormalization is intentionally re-introducing redundancy after normalising so that reads get fast. A normalised schema needs a three-table join to print one report row; copying a department name into a fact table turns that join into a single scan. It is a deliberate trade — write once, read a million times — and it re-opens all three anomalies.
Exam trap ✍ the direction question "Which is better?" has no answer — it depends on the workload. Normalise for OLTP (many small inserts, updates and deletes, integrity enforced by the DBMS); denormalise for reporting / data warehousing (huge read volumes, occasional batch reloads). "Denormalization always improves performance" is false: it speeds reads and slows every write.

Written question Define a functional dependency and name the five types, distinguishing trivial from non-trivial. For R(A, B, C, D, E) with F = {A→B, BC→D, D→E}, compute {A, C}+ and say whether AC is a candidate key. For R(A, B, C) with A→B, B→C and A the only candidate key, state the highest normal form and decompose it. Then test the split of that R into R1(A, B) and R2(A, C) for lossless-join and dependency preservation. 10 marks
  1. Definitions (2) — X → Y holds when every two tuples agreeing on X also agree on Y; X is the determinant. Trivial: Y ⊆ X, e.g. (A, B)→A. Non-trivial: Y ⊄ X, e.g. StudentID→Name. Full: Y depends on the whole of X. Partial: on part of X. Transitive: A→B and B→C give A→C. 2
  2. Closure (2) — {A, C}; A→B adds B → {A, B, C}; BC→D adds D → {A, B, C, D}; D→E adds E → {A, B, C, D, E} = R, so AC is a candidate key. 2
  3. Highest normal form (2) — A is on no right-hand side and is one attribute, so it is the sole candidate key and the only prime attribute. A single key means no partial dependency, so R is in 2NF. But A→B→C is transitive, and in B→C the determinant is not a superkey and C is not prime, so 3NF fails: the answer is 2NF, decomposed to R1(A, B) and R2(B, C). 2
  4. Lossless (2) — R1 ∩ R2 = {A}, and A→B gives A→R1, so the shared attribute is a key of R1: the join is lossless. 2
  5. Preservation + rules (2) — the only FD, A→B, lies entirely inside R1, so it holds with no join: dependency-preserving. In general lossless ⟺ (R1∩R2)→R1 or (R1∩R2)→R2; preserving ⟺ the projections of F onto R1 and R2 union to F. 2
