FunctionalNon-functional

3Specification: What the SRS Must Contain

SRS (IEEE 830 / ISO-IEC 29148) 1 Introduction — purpose, scope, definitions, overview, references · 2 Overall description — perspective, functions, user classes, environment, constraints, assumptions · 3 Specific requirements — external interface, functional, performance, design constraints, system attributes · 4 Appendices — glossary, index.

5Feasibility Study: TELOS

  • Techical — can it be built at all with the available hardware, software and skills?
  • Economic — cost–benefit: do the benefits exceed the costs? (payback period)
  • Legal — law, privacy, licensing, contracts, standards
  • Operational — will it fit the way the organisation works?
  • Schedule — can it be delivered in the time available?
Memory trick Say it as a word: T-E-L-O-S — Greek telos = the goal. The report ends in a go / no-go call.
Exam trap Feasibility is judged before the SRS and again when the model is built — it is not the last step.
Validation Proving the model and spec are right: reviews and inspections, prototypes, acceptance test cases, model walkthrough, decision tables. Check correctness, completeness, consistency, realism, verifiability.
Worked judgement ✍ A hospital wants online appointments. T: a server and a biometric device must be bought. E: six staff-years saved, licences cost three, payback five years? L: patient data must stay in the country. O: counter staff will not re-key everything. S: go-live before the quarter closes? Only T, L and O clear — the project waits.

6The Analysis Model and the DFD

high-yield
Analysis model an abstract representation of the system built from the requirements. DFD = what happens (functions and flows) · ERD = what exists (data structure) — complements, never rivals.
ElementSymbolMeaning
External entitysquarea source or sink outside the system
Processcircleturns input data into output data; numbered 1.0, 2.0 …
Data storetwo linesrelated data at rest, inside the system
Data flowarrowa named data element moving between elements

7Level 0: the Context Diagram

Level 0 = context diagram ★ The whole system as one process, joined to its external entities by the flows crossing the system boundary. No store, no internal process — level 1 adds those.
Exam trap It shows neither the database tables (that is the ERD), nor the internal processes (level 1), nor timed messages.
Levels & decomposition Context (0) → level 1 = one bubble per major function → level 2, 3 … Numbering: 1.0, 2.0, then 2.1, 2.2. Complexity is handled by divide and conquer.
Rules (DFD) No store → store, no store → entity, no entity → store. Every process needs ≥ 1 input and ≥ 1 output (a grey or black hole is an error). Flows are logical and named.

8The Data Dictionary

notation
Definition The specification of every data flow, data store and data element in the DFD. Each entry has four parts: name = composition / definition / where used / comment. An entry that cannot be written down is a requirement that is still fuzzy.
SymbolMeans

x = [a | b]selection — a or b
x = {a}iteration — zero or more (1{a}n sets bounds)
x = (a)optional — zero or one
@xx is the key that identifies the entry
* text *comment / alias
Entries for case A ✍
Loan = loan_id + member_id +
    accession_no + issue_date +
    due_date + (return_date)
Member = member_id + name +
    phone + membership_type

Case A — the same library system, drawn as a DFD

  • 1.0 Register: member data → D1 Members.
  • 2.0 Search: catalogue query → book list; reads D2.
  • 3.0 Loan: issue / return → checks D2, writes D1, returns book + due date.
  • Librarian: maintains D2, receives the overdue report.

Balanced against the context diagram of sheet 4: every flow entering the system there is consumed by a process here, and every flow leaving there is produced here.

Exam trap A DFD shows logical flow, so a "book file" is not "C:\library\books.txt". If the question asks for the database design, draw the ERD.

SE · Analysis & DesignER modelling

9Entity–Relationship Modelling

high-yield
Definition The ER model (Chen, 1976) is a conceptual data model: it pictures the real world as entities, the attributes they carry and the relationships between them, with no reference to any DBMS, table or file.
Entity a real-world object or event that can be distinctly identified. A strong entity owns its key; a weak entity (double rectangle, partial key) has none of its own and is identified only through its owner.
Attributes simple / composite (name = first + last) · single / multivalued (several phone numbers) · derived (age from date of birth) · key (underlined, minimal).
Relationships an association among entities. Degree = how many entity types take part: unary (1), binary (2), ternary (3). Unary is also recursive — Employee manages Employee.
CardinalityLibrary example
1 : 1one member ↔ one card
1 : None member → many loans
M : Nmembers ↔ books, over time
Total part.every instance must join
Partial part.an entity may stay out
Exam trap Cardinality and participation are different questions: "how many at most?" vs "must it take part?". 1 : N does not make the N side mandatory.

SE · Analysis & DesignER → relation

10Case B — the ER diagram, then the relational schema

A MEMBER issues 0..* LOANs and a BOOK appears in 0..* LOANs; LOAN joins both totally, so it cannot exist without both. It carries Issue_date, Due_date and Return_date. When the same two entities meet again later in time — loans, orders, enrolments — you need a third relation holding the event.

Exam trap MEMBER–LOAN is not a plain 1:N on one line: the pair (member, book) repeats over time, so it is M:N, resolved by making LOAN the associative entity.

11ER → Relational Mapping: the Seven Rules

#Source constructRelation produced
1Strong entitysame attributes; its key = primary key
2Weak entityowner key as FK; PK = owner key + partial key
31 : 1 relationshipone side's key as FK in the other relation
41 : N relationshipkey of the one side as FK in the many side
5M : N relationshipnew relation: the two keys as FKs; the pair is the PK
6Multivalued attributenew relation: entity key + attribute = the PK
7N-ary relationshipnew relation: all participants' keys = the PK
Case B applied ✍ MEMBER(member_id, name, phone)
BOOK(accession_no, isbn, title)
LOAN(member_id, accession_no,
    issue_date, due_date, return_date)
AUTHOR_BOOK(isbn, author_name)
rule 2 gives the LOAN key; rule 6 splits a multi-author title.

12Design: Turning Requirements into a Blueprint

PrincipleIn practice
Abstractiondescribe what a unit does, hide how
Modularitysplit into separately testable modules
Information hiding ★(Parnas, 1972) hide what is likely to change
Separation of concernsone module, one concern
Refinementtop-down, step by step to code
Reusereuse an existing design or component
Why it pays Modules are understood, unit-tested, reused and changed independently; a fix stays inside one module.
Exam trap Abstraction ≠ encapsulation. Abstraction decides what to expose; encapsulation bundles data with its operations. Modularity is the goal, information hiding the technique.

14Three Levels of Design

written favourite
LevelDecides
1 Architecturalthe system structure: components, their relationships and constraints; the data architecture and interfaces
2 High-level (modular)modules → submodules; which data structures and abstract data types each module owns
3 Detailedthe exact algorithm, nesting of records, language-level data structures

15The Architectural Design Process

  1. Address the design: which functions must the design model perform?
  2. Design the data — the domain model becomes the design class diagram (DCD)
  3. Assign functions to components: map each class onto a component or subsystem
  4. Refine the design classes: attributes, operations, associations and navigability
  5. Define the design sequence: the order in which classes are implemented and unit-tested
  • The domain model (data only) gains operations, navigability arrows and packages.
  • Case C: Member 1 → 0..* Loan, Book 1 → 0..* Loan, Loan 1 → 0..1 Fine.
  • Design sequence: Book and Member first (they carry the data), then Loan, then Fine; unit-test each with its collaborators.
  • The named GRASP patterns do exactly this job.

Information Expert, Creator, Low Coupling–High Cohesion

Exam trap The DCD is not the domain model: it is implementation-aware, while the domain model holds only classes, attributes and associations.

Memory trick: MVC Model = what is true · View = what it looks like · Controller = what the user just did.

17UI Design: Principles for a Usable Interface

  • Visibility of system status — show what is happening.
  • Match the real world — the user's language, their units.
  • User control and freedom — undo, cancel, a clear exit.
  • Consistency and standards — one look, one meaning.
  • Error prevention — constrain, confirm, offer a default.
  • Recognition over recall — show the options.
  • Accessibility — usable by elderly and disabled users.
Goal intuitive, efficient, pleasant use. Three golden rules: place the user in control, reduce the user's memory load, make the system consistent.
Exam trap Usability ≠ learnability. A system can be learnable and still not usable; a novice-friendly system can be unusable for an expert doing the same job all day.

Written question What are cohesion and coupling? Why should a good design have high cohesion and low coupling? List the types of each from best to worst. 10 marks
  1. Cohesion = how much one module's elements belong together; coupling = how much modules depend on each other. 3
  2. A good design keeps modules easy to understand, test, reuse and change: a change in one hardly affects the others. 2
  3. Cohesion, best → worst: functional, sequential, communicational, procedural, temporal, logical, coincidental. 2
  4. Coupling: data, stamp, control, external, common, content. 3
