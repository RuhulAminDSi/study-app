SE · Testing & MaintenanceLevels of testing

1Verification vs Validation

high-yield
The distinction Verification asks "are we building the product right?" — is it being built to the design? Validation asks "are we building the right product?" — is it what the user wants? Verification is internal, done by the team; validation needs the customer.
AspectVerificationValidation
Tested againstthe design / build specificationthe SRS and user needs
Done bydevelopers: reviews, unit teststesters with the customer
Where CMMI puts it The Verification process area was introduced at CMMI level 3 (Defined) — not required at level 2. In CMMI 1.1 the area was called Verification and Validation. Levels: 1 Initial · 2 Repeated · 3 Defined · 4 Managed · 5 Optimizing.
Exam trap Verification is against the design, validation against the requirements. Testing can show the presence of defects, never their absence — so a green validation suite does not "prove" the system right.

2The Four Testing Levels, in Order

MCQ + Written
LevelThe question it answersTested by
Unit testingdo the parts work right?developers (JUnit, xUnit)
Integration testingdo the parts work together?developers + testers
Validation testingare we building the right product?customer, at acceptance
System testingdoes the whole system work?testers, in a test environment
Unit One module, class or method, in isolation — normally automated. Test-first (TDD): write the failing test before the method.
Integration Catches the classic fault: every module passes alone, but the interfaces disagree on data format, order or timing.
System The integrated whole run as a product: does it do what it promises, and how well? Non-functional types on the next sheet.
Memory trick The four questions ask about breadth: parts → together → right thing → whole. Unit asks "does the engine work?", integration "do the wheels turn?", validation "is it my car?", system "does it drive on the road?" V-model: business req ↔ acceptance · system req ↔ system test · architecture ↔ integration · design ↔ unit.

SE · Testing & MaintenanceIntegration strategies

3Integration Testing: Four Strategies

MCQ favourite
The problem Modules tested in isolation all passed; assembled, they fail. Integration testing exposes the fault that lives in the interfaces. The strategy decides in which order modules are joined.
StrategyOrder of joiningMain weakness
Big Bangall modules integrated at onceone failure, and the culprit is hard to isolate
Top-downstarts at the main control module, then downwardmany stubs; the real lower modules are tested late
Bottom-upstarts at the lowest leaf modules, upwardthe main control module is written last
Sandwich (hybrid)top-down above, bottom-up below, meeting in the middlemore up-front work; broadest practical coverage
Stub A dummy replacement for a module that is called but not yet written; it returns a canned value. Top-down uses it. int add(int a,int b){ return 0; }
Driver A small main routine written to call the module under test and display the result. Bottom-up uses it. main(){ printf("%d", sq(4)); }
Memory trick The word tells you the stand-in. A stub is called → go top-down. A driver calls → go bottom-up. If you remember nothing else: top-down = stub, bottom-up = driver.
Exam trap Big Bang is not a level of testing — it is one of the four joining strategies, and the least useful of them. In bottom-up testing the temporary piece is the driver, not the stub.
Exam trap Sandwich (hybrid) is top-down for the upper layers and bottom-up for the lower ones, joined in the middle. Some books also list threaded integration: each module is integrated as soon as it is ready.

SE · Testing & MaintenanceSystem & non-functional

4Validation & System Testing

written favourite
Validation testing Confirms the system does what the SRS says, with the customer in the loop. Its final stage is acceptance testing: alpha — on the developer's own site, staff as users; beta — on the customer's site, with real users. Cases are traced back to requirements in a traceability matrix.
System testing The integrated system exercised as a complete product. It has two halves: functional testing (does it do what it promises?) and non-functional testing (how well, how fast, how safely?).

The seven non-functional / system testing types

TypeWhat it provesTypical question
Load testingbehaviour under the expected and peak workloadresponse time at 500 users?
Stress testingbehaviour beyond capacity, up to breakingat what load does it collapse?
Security testingauthentication, authorisation, data privacySQL injection? XSS?
Compatibility testingworks on the required browsers, OS, devicesrenders in every browser?
Usability testinga real user can learn and use it unaidedeffort to learn?
Installation testinginstalls, upgrades, uninstalls on a clean machinesetup succeeds on Windows 11?
Recovery testingrestored from failure within tolerancehow long to restore?
Exam trap Load = the load you expect; stress = more than you can bear. Meeting the load target while failing under stress is still a passing system; passing stress but missing the load SLA is a failure.
Memory trick Seven letters, seven types: Load, Stress, Security, Compatibility, Usability, Installation, Recovery. Volume and configuration testing are their near neighbours.
Also listed with system testing Performance (speed, resource use) · Volume (very large or very small data sets) · Configuration (every supported setting) · Documentation · Localization (language, currency, dates).

SE · Testing & MaintenanceDebugging

5Debugging: Finding and Removing the Cause

MCQ + Written
Definition Debugging is the process of locating, analysing and removing the cause of a defect — not of removing the symptom. In classic studies it takes 50–60 % of a programmer's time.

The five steps, in order

  1. Reproduce the failure deterministically — a bug you cannot reproduce is a bug you cannot close.
  2. Locate the symptom: trace, logs, stack dump, breakpoints.
  3. Diagnose the root cause — keep asking why until the answer stops blaming code.
  4. Fix the cause, so the same class of bug cannot recur.
  5. Re-test: the original case plus a regression suite, to prove nothing else broke.
TechniqueHow it works
Brute forceprint statements, dumps, traces — let the program shout
Backtrackingstart at the point of failure, work backwards to the last good state
Cause eliminationlist candidate causes, test each; halve the data set
Program slicingcompute the slice of statements that can affect a point
Differentialcompare a known-good version with the faulty one
Modern tools Breakpoints, watch windows, single-step; logging; profilers; git bisect — backtracking through the commit history.

5b Debugging anti-patterns (Glass)

Anti-patternWhat it looks likeRight move
Mysterious changethe defect "moved" when you fixed something elseone change at a time; keep a record
Dynamic changethe fix works here and breaks thereregression-test the whole suite
Cut-and-pastepaste a corrected copy of a block somewhere elsefind out why the first copy was wrong
Shotgunchange everything at random until the symptom goesstop, revert, bisect
Dormant bugintermittent — "works most of the time"a shared-state race: instrument, do not hope
Assumption"the compiler / library will do what I think"check the contract, write the assertion
Exam trap Debugging is not testing. Testing reveals that a defect exists; debugging finds and removes its cause. The defect has been in the code since it was written — it is the latent condition, and the failure is only the symptom that exposed it.
IT link The chain error → defect → failure: the developer misreads the fee rule (error), ships the wrong rate (defect), and the statement is wrong (failure).

SE · Testing & MaintenanceMaintenance

6Software Maintenance: Why It Dominates

high-yield
Definition Software maintenance (IEEE Std 1219) is modification of a delivered system to correct faults, improve performance or other attributes, or adapt it to a changed environment. Delivery is not the end of the project — it is the start of its longest phase.
The number to remember 60–80 % of the total life-cycle cost of a software system is spent in maintenance; most surveys put it nearer two thirds. A system that is never maintained becomes obsolete; one maintained badly becomes expensive.

Why maintenance dominates

  • the system stays in service for years; development lasts months;
  • the environment moves on — hardware, OS, database, third-party APIs, laws;
  • the original developers have left; nobody remembers the intent;
  • real users find requirements that analysis missed;
  • a defect that escapes costs 20–100× more to fix here than in requirements.

7The Four Types of Maintenance

most tested fact
TypePurposeExample
Corrective (remedial, repair)fix faults found after deliveryan off-by-one in the payroll calculation; a tax rate hard-coded for last year
Adaptive (environmental)make the software work in a new environmentporting an app from Windows to Linux; adopting a payment gateway's new API
Perfective (improvement)add or improve functionality or performancea new MIS report; a faster index; a friendlier screen
Preventiverestructure now to prevent future faultsrefactoring a legacy module; deleting unreachable code; adding regression tests
Exam trap Adaptive is about the environment changing, not a new user requirement. A new OS, database or law is adaptive; a report the user asked for is perfective; fixing a crash is corrective; rewriting a module so future change is safer is preventive.
Where the effort goes Field studies (Lientz & Swanson) report perfective ≈ half of all maintenance effort, adaptive ≈ 25 %, corrective ≈ 20 %, preventive only a few per cent — the smallest slice, and the one that pays for itself.

SE · Testing & MaintenanceProcess & cost

8The Maintenance Process

written favourite
Inputs A change request is logged, classified and costed before anything is touched, then passes change control: small fixes take a one-step approval, larger ones two-step.
  1. Receive & log the change request / problem report
  2. Classify and estimate — type (corrective, adaptive, …), effort, cost, risk
  3. Impact analysis — which modules, interfaces and documents does this touch?
  4. Design & implement the change; keep every change versioned
  5. Regression-test the changed and the dependent modules
  6. Release, update the documentation, close the request with a record

What makes maintenance expensive

  • Size and age — more code, more interfaces, more ways to break.
  • Cruciality — the core banking system cannot be down for a week.
  • Contractual duty — a support period in the contract.
  • Documentation — stale documents make each change a fresh investigation.
  • Staff turnover — knowledge leaves with the developers.
Lehman's Law of Continuing Change (Lehman, 1972, refined 1980): software must be changed or become obsolete. In E-type systems complexity increases with every change unless maintenance is deliberate — hence preventive work.
Boehm's maintenance cost model Annual effort rises with the age of the system: more users, data, interconnections, faults. A young system is cheap to keep; an old one is not.
Documentation is the precondition Four documents must stay alive: requirements, design, test cases and the user / operational manual — the first three serve the maintainer, the last the operator. Maintenance without documentation is archaeology.
Memory trick: the four types Corrective = it is broken · Adaptive = the world around it moved · Perfective = it could be prettier · Preventive = stop it breaking later. CAPPP, in the order every syllabus prints it.
Exam trap Re-engineering (rebuilding the system from the existing one) and forward maintenance are maintenance activities, not a fifth type — re-engineering is a perfective / preventive decision. The four types were classified by IEEE Std 1219, not by one author.

SE · Testing & MaintenanceSQA

9Software Quality Assurance

MCQ + Written
Definition Software Quality Assurance (SQA) is the set of planned and systematic activities that provide confidence that quality requirements will be fulfilled. It is not a phase: it is a set of activities that span the entire SDLC, from requirements to maintenance.
Standards & procedures Documented processes, guidelines and checklists the team must follow. Without them "quality" is only an opinion.
Reviews & inspections Structured checking of artefacts at requirements, design and code — the cheapest defects in the life cycle. IEEE Std 1028 gives the review model.
Audits Check that the process is really being followed — "are the reviews happening and recorded?"
Testing at every level Unit → integration → validation → system, plus defect tracking and closure from first report to final fix.
Configuration management Control of code, documents and versions, so the right item is changed and the change is traceable.
Measurement & records Defect density, review efficiency, coverage, cycle time — kept as quality records.
Standard / modelWhat it is
ISO/IEC 9001the international quality management system requirements
ISO/IEC 12207the software life-cycle processes; part 8 covers V&V
CMMIprocess improvement model, 5 levels; Verification at level 3
IEEE Std 730the classic software quality assurance standard
Exam trap SQA ≠ quality control. QA is the planned, preventive, process-wide activity; QC is the inspection part — the tests themselves. "SQA is only testing" is the commonest wrong option.

10McCall's Quality Factors

CategoryFactors
Product operation — correctness of useCorrectness · Reliability · Efficiency · Integrity · Usability
Product revision — changeabilityMaintainability · Flexibility · Testability
Product transition — portabilityPortability · Reusability · Interoperability
Exam trap McCall's model (McCall, Richards & Walters) is a software product quality model. Do not confuse it with ISO/IEC 9126 (1991), whose six characteristics are functionality, reliability, usability, efficiency, maintainability and portability — later extended by ISO/IEC 25010 with compatibility and security. Eleven factors, six characteristics: do not mix the counts.

11Software Metrics: Three Families

written favourite
FamilyMeasured onExamples
Productthe software product itselfsize (LOC, function points), complexity, defect density, MTBF, MTTR
Processthe way the work was doneDRE, effort variance, review efficiency, defect-removal rate
Projectthe project, planned vs deliveredschedule variance, cost variance, delivered size
Size, line-based LOC / KLOC — simple and cheap, but style-dependent: the same job can be 200 or 2,000 LOC.
Size, function-based (FP) Function Point Analysis (Albrecht, IBM, 1979) counts the functionality delivered, so it is language-independent. Five components: External Inputs, External Outputs, External Inquiries, Internal Logical Files, External Interface Files. Unweighted EI 3, EO 4, EQ 3, ILF 7, EIF 5.
Complexity, line-based Cyclomatic V(G) (see the GRASP notes) and BANG: Branch + Assignment + Number of loops + Global variables. A higher BANG means harder to test and maintain.

SE · Testing & MaintenanceMetrics

12Defect, Reliability & Availability Metrics

The formulas Defect density = defects ÷ KLOC (or ÷ function points). DRE (Defect Removal Efficiency) = errors found before release ÷ total errors, × 100 %. Availability = MTBF ÷ (MTBF + MTTR).
Worked ✍ MTBF = 1000 h, MTTR = 2 h ⇒ 1000 ÷ (1000 + 2) = 1000/1002 = 0.998 = 99.8 %. Halving MTTR to 1 h gives 99.9 %: doubling reliability is worth little while repair still takes hours.
Reliability · Availability · Safety Reliability = probability of failure-free operation over a stated period (MTBF). Availability = probability the system is operable when required. Safety = does no harm even when it fails — the concern for medical, aviation and nuclear systems.

Phase-specific metrics

PhaseMetrics
Analysis & designNOC classes · NOR requirements · DIT inheritance depth · NOM methods · use-case size
Source codeLOC · cyclomatic V(G) · BANG · coverage %
Testingdefect density · DRE · coverage · MTBF
MaintenanceMTTR · post-release defects · code churn
Exam trap Defect density is a product metric; DRE is a process metric. DRE is always a percentage — "pre-release ÷ total" without × 100 % is incomplete. A high DRE is good; a high defect density is bad.

Cost of a defect found late

Found inRequirementsDesignCodingTestingProduction
Relative cost to fix1×5×10×15–25×100×+

Boehm's field study in Software Engineering Economics (1981) is the classic source; ratios differ from study to study, so quote the shape, not the digits as a law. The mechanism is what matters: a requirements defect is one line of a document; a production defect is that line plus the code, the test, the release, the rollback and the customer's trust.
