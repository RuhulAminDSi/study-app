SE · GRASP & DCDGRASP

1GRASP: the Responsibility-Assignment Problem

MCQ + Written
Definition GRASP = General Responsibility Assignment Software Patterns: guidelines for deciding which object gets which responsibility, so that the result is loosely coupled, cohesive, maintainable and reusable. Proposed by James Carell and Martin Fowler, 1991 (Toward Unified Design Methodologies, IEEE Computer).

Two kinds of responsibility

  • Knowing — the object's own attributes and the objects linked to it.
  • Doing — the actions it performs (its operations).

A pattern (Singleton, Strategy, Observer …) is a named solution with structure. A GRASP guideline is one sentence with no class diagram attached — it tells you where to put a responsibility, not what to build.

The nine guidelines, in one line each

#GuidelineThe principle, in one line
1Information ExpertGive it to the class that has the information
2CreatorThe class that contains, aggregates or initialises it creates it
3Low CouplingAssign to the class least dependent on others
4High CohesionOne class, maximum related responsibility
5PolymorphismDo not re-implement superclass behaviour in a subclass
6Pure ArbitersThe object that arbitrates between two or more others
7Don't Talk to StrangersAsk only immediate associates for information
8ControllerThe first non-UI object to receive a system event
9Intermediary (Pure Fabrication)An invented, non-domain class breaks the dependency
Three more often listed with GRASP Indirection — an intermediary links objects that must not know each other. Protected Variations — wrap every point of predicted change in an interface. Known / Unknown Dependencies — name a known dependency concretely; an interface in front of a changeable one.
Exam trap GRASP is guidelines for assigning responsibilities by Carell & Fowler (1991) — not a pattern catalogue, and not the GoF patterns. Pure Arbiters is sometimes printed as "Pure Arbiters / Information Expert": do not count it twice.

SE · GRASP & DCDInfo Expert & Creator

2Information Expert & Creator — Worked

high-yield
Information Expert Assign the responsibility to the object that has the information needed to carry it out. Example: the Invoice should compute getTotal(), because the Invoice is the only class holding its list of LineItems.
class LineItem { Product product; int quantity; double getSubTotal() { return product.price * quantity; } } class Invoice { List<LineItem> items; double getTotal() { return items.stream() .mapToDouble(LineItem::getSubTotal) .sum(); } }

Why this is the right answer

  • Only the Invoice holds the line items, so only it can sum them.
  • No parameters have to be passed in and no LineItem needs a back-pointer.
  • The knowledge stays inside the class that owns the data: coupling falls, cohesion rises.
Exam trap Information Expert is not "the class with the most methods". It is the class with the data needed. If the data lives elsewhere, the responsibility goes elsewhere.

2b Creator — Worked

Creator Assign to class B the job of creating instances of class A if any one of these holds: B contains A · B aggregates A · B records A · B closely uses A · B holds the data that would initialise A.
class Sale { List<SalesLineItem> lines; SalesLineItem addLine(Product p, int q) { SalesLineItem l = new SalesLineItem(p, q); lines.add(l); return l; } }
Memory trick Creator = "C for Container". Even when B does not contain A, if B can name the values that initialise every field of A, B is a natural Creator — creating A there reduces the arguments the caller must supply.
Exam trap Creator is not "the class that uses it". In a POS, Sale — not Register, ProductCatalog or Payment — creates SalesLineItem, because Sale contains the line items.

3Low Coupling & High Cohesion — Worked

written favourite
Low Coupling Assign responsibilities so that unnecessary dependencies are minimised. The rule to quote: give the responsibility to the class least dependent on other classes. Dependence is measured by how much of another object's state a class must know.

Bad — high coupling

class Customer { String name; void saveToDatabase() { // opens a JDBC connection, // builds SQL, commits a tx } }

Cost: Customer now knows the DB, SQL, the driver and the network.

Good — low coupling

class CustomerRepository { void save(Customer c) { // all DB logic lives here } } class Customer { String name; // no DB knowledge }

Gain: Customer is reusable, the repository replaceable, the two unit-test separately.

3b High Cohesion — Worked

// LOW COHESION — the "god class" class CustomerManager { void browseShop() { } void chargeCard() { } void shipOrder() { } void sendEmail() { } void updateDatabase(){ } }

Five unrelated jobs: no single reason to change it, and every change risks all five.

// HIGH COHESION — split it class Customer { /* customer data */ } class Cart { /* cart operations */ } class Payment { /* payment logic */ } class Shipping { /* delivery */ } class Notifier { /* e-mail */ }

Each has one clear reason to change — SRP restated.

Memory trick Coupling is how many strings are tied to this balloon — four strings and it cannot fly. Cohesion is how tightly its own parts stick together: five unrelated jobs is gravel, not rock.
Exam trap The two are different axes: coupling is between classes, cohesion within one. A class can be cohesive yet coupled to three others.
IT link A bank core hides its ledger rules behind an interface: the SQL is swappable without touching the business classes.

SE · GRASP & DCDOther guidelines

4Polymorphism, Controller, Intermediary & the Rest

high-yield
Polymorphism Do not assign to a subclass a behaviour its superclass already covers. Put it in the superclass or interface and let polymorphism choose the version at run time. CashPayment · CardPayment · MobileBanking share process().
Pure Arbiters Assign a responsibility to the object that arbitrates between two or more others — it holds the rules both sides need and neither owns. A TaxPolicy that Invoice and Refund both consult.
Don't Talk to Strangers If a method knows too much about, or depends on, too many others, it breaks the rule. Ask only immediate associates. Never reach through Order to touch Order.getCustomer().getAddress().
Controller The first object beyond the UI layer to receive a system event such as enterItem and coordinate it. Two kinds: facade controller (the whole system) and use-case / session controller (one scenario). Never in the UI class.
Intermediary (Pure Fabrication) A class that represents no domain concept at all, invented only to break an awkward dependency; normally placed in the common low-level packages. A ReportService between the invoice and the database.
Protected Variations Identify the points of predicted change and put an interface or abstract class in front of each, so the unstable part can vary without touching the rest. Open/Closed Principle; usually the Strategy pattern.

How the guidelines stack up against SOLID

Exam trap The Controller guideline is not "the class the user clicks" — a UI class that receives the event is precisely what GRASP forbids. A Pure Fabrication differs from a Domain Model class: it has no domain meaning at all.

5The Design Class Diagram (DCD)

MCQ + Written
Definition The Design Class Diagram is the UML class diagram drawn at the design level: the domain-model class diagram extended with everything an implementer needs — operations with signatures, types, visibility markers and navigability arrows.
Domain / analysis modelDesign class diagram
Conceptual view of the domainSoftware view
Classes, attributes, associations, multiplicitiesthose plus methods and return types
Plural domain nouns (Sales)Singular nouns (Sale)
No software-specific typesConcrete: String, double, List
No visibility markers+ public · − private · # protected
Associations are undirectedNavigability — who holds the reference
No interface or packages<<interface>>, <<abstract>>, packages

Mapping design to code: the one-to-one rules

Element in the DCDBecomes in the code
One class boxOne class — or an interface, if stereotyped <<interface>>
An attribute − price : doubleOne field / property of that type
An operation + total() : doubleOne method with that return type
An association 1 → * with navigabilityA reference field plus a collection (array / List / Set)
Aggregation ◇ or composition ◆A whole–part reference owned by the whole
A generalisation △ / realisation ▷inheritance / composition by delegation
Exam trap The one thing a DCD shows and a domain model does not is methods (operations) and navigability. Conceptual classes, associations and multiplicities appear in both.
Memory trick Domain model = what exists. DCD = what exists, plus what it does. A method signature with a return type means you are looking at a DCD.
Four steps to build a DCD ① Make every concept-class name singular (Sales → Sale). ② Give attributes software types (age: Integer → int). ③ Write each class's responsibilities as operations with return types. ④ Mark every association that holds a reference with a navigability arrow.

SE · GRASP & DCDDCD worked example

6A DCD Worked Through, and the Code It Becomes

written favourite
class Customer { String name; String email; Cart cart = new Cart(); void checkout() { Order o = cart.createOrder(); o.confirm(); } } class Line { Product product; // navigable ▸ int qty; double subTotal() { return product.price * qty; } }
class Cart { List<Line> items = new ArrayList<>(); void add(Product p, int q) { items.add(new Line(p, q)); } double calculateTotal() { return items.stream() .mapToDouble(Line::subTotal) .sum(); } Order createOrder() { return new Order(items); } }
Read the mapping off the picture Cart.items : List<Line> → the field List<Line> items; Line.product : Product → the field Product product; Line.subTotal() : double → the method. Nothing in the DCD has to be re-invented in the code — the class names, attribute names, types and method names already are the identifiers the programmer needs.
Exam trap A DCD is not the same artefact as the CRC card: CRC is how you discover responsibilities, the DCD is how you record them. "Design maps directly to code" means a one-to-one mapping — not one file per diagram element.

7Structural vs Functional Testing, EP and BVA

MCQ + Written
AspectWhite-box (structural, glass-box)Black-box (functional, behavioural)
Test cases derived fromthe internal structure of the codethe specification, not the code
Tester's knowledgeknows the program internalsdoes not know how it is written
Also calledstructural, clear-box, glass-boxfunctional, specification-based
Main question"is every statement / branch executed?""is the output right for every valid input?"
Techniquesbasis-path testing, coverage analysisequivalence partitioning, BVA, cause-effect graphing
Best at findingdead code, unexecuted branches, wrong loop limitsmissing requirements, wrong outputs
Test basis The document a test is derived from: for a white-box test the design model / code, for a black-box test the requirement specification. Testing can show the presence of defects, never their absence.
Exam trap Testing cannot prove a program correct; it only raises confidence. A test that has never failed is not yet known to be a good test. Unit → integration → validation → system levels, debugging, maintenance and test metrics belong to Testing Strategies, Maintenance, Quality & Metrics.

7b Equivalence Partitioning & Boundary-Value Analysis

Equivalence class (age)KindEP pick
age < 18invalid10
18 ≤ age ≤ 60valid35
age > 60invalid70

EP splits the input domain into classes handled the same way and tests one representative of each — few cases, wide coverage. Valid and invalid classes are counted separately.

BoundaryBVA picks
lower, 1817 · 18 · 19
upper, 6059 · 60 · 61

BVA tests just below, exactly at and just above each boundary. Off-by-one errors live at the edge — exactly where EP takes one arbitrary sample.

When to use which ✍ EP alone is enough for a small input domain. With a wide domain (years, amounts, dates) EP on its own grows risky, so add BVA: EP keeps the representative, BVA keeps the extreme, and a fault inside a class slips past EP, which always aims at the middle.

8Coverage, Cyclomatic Complexity & Basis-Path Testing

written favourite
Coverage criterionHow it is measuredStrength
Statementexecuted ÷ total executable statements × 100 %weakest — misses unexecuted branches
Branch / decisionoutcomes taken ÷ total outcomes × 100 %the usual minimum target
Conditionatomic conditions evaluated ÷ total × 100 %both ways for each part of a && b
Multiple conditionevery truth-value combination — 2ⁿvery strong, very costly
Pathexecuted paths ÷ total paths × 100 %strongest, exponential effort
Cyclomatic complexity (McCabe, 1976)  M = E − N + 2P — E = edges of the control-flow graph, N = nodes, P = connected components. A normal module gives P = 1, so the familiar form is M = E − N + 2. M is exactly the number of independent paths — the regions of the flow graph — and for straight-line conditionals M = (independent conditions) + 1. No decision at all ⇒ M = 1.
double total(int qty, double price, boolean member) { if (qty > 0 && price > 0) { double t = qty * price; if (member && t > 1000) t = t * 0.90; return t; } return 0.0; }
  1. Draw the flow graph
  2. Compute M
  3. Find the M independent paths
  4. One test case per path
Worked example ✍ Four atomic conditions give M = 4 + 1 = 5, matching E − N + 2 = 12 − 9 + 2 = 5. Basis set: P1 qty=0 → 0.0 · P2 price=0 → 0.0 · P3 2×100, not member → 200 · P4 2×100, member, t≤1000 → 200 · P5 20×100, member → 2000×0.9 = 1800.
Independent path A path introducing at least one new node or new condition no earlier path used. The count equals M.
Design in the V-model Business req ↔ acceptance · system req ↔ system test · architecture ↔ integration · design ↔ unit test.
Nesting & limits statement ⊂ branch ⊂ condition ⊂ path; McCabe's traditional limit is 10.
Specialised test targets real-time → timing, stress · distributed → latency, partial failure · web → SQL injection, XSS · mobile → devices, screens · embedded → CPU, memory. Full path coverage grows exponentially, so "100 % path coverage" is never a realistic goal.
