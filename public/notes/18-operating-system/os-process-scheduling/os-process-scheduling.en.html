1Program vs Process & the PCB

definition ★
Definition A program is a passive file of instructions on disk. A process is that program loaded into memory and executing, with its code, data, program counter, the CPU registers it owns and its open files. A program is static, a process is dynamic — one program may be many processes at once.
PointProgramProcess
Naturepassive, staticactive, dynamic
Memorydisk is enoughneeds main memory
Identityone file namePID, many instances
Lifeas long as the filenew → running → terminated
PCB fieldContentsWhy the OS keeps it
Process stateNew · Ready · Running · Waiting · Terminatedpicks the queue
Program counteraddress of the next instructionresume exactly
CPU registersaccumulator, base, limit, stack, R0…Rnunfinished arithmetic
CPU-scheduling infopriority, queue pointerswho runs next
Memory-management infopage-table base, segment-table pointeraddress translation
Accounting infouser & kernel time, I/O counts, childrenbilling, quotas, cleanup
Memory trick The PCB is the process's passport: the PID says who it is, the state says where it is, the PC and registers remember exactly where it stopped; the rest says what it owns.
Exam trap (i) The PCB is a kernel structure made by the OS; the process never writes into it. (ii) A process is not its PCB — terminating frees both. (iii) A PID is unique among running processes and may be reused afterwards.
Worked example ✍ read a PCB dump PID 4217, state Waiting, PC 121, base 240, limit 460, user time 128, kernel time 12. (a) It is not in the ready queue — it waits for an I/O event. (b) Legal addresses = 240 … 459. (c) CPU used = 128 + 12 = 140 units. (d) The PID is not a scheduling key by itself; priority is.

2The Five-State Model & the Queues

most tested ★
Definition A process is in exactly one of five states: new (being created), ready (in memory, waiting for the CPU), running (holds the CPU), waiting / blocked (waiting for an event that is not the CPU) and terminated (finished, resources reclaimed).
From → ToTriggerBy whom
New → Readyadmittedlong-term scheduler
Ready → RunningCPU allocatedshort-term scheduler
Running → Readyinterrupt, slice ended, higher priority readyshort-term scheduler
Running → WaitingI/O request or event waitthe process itself
Waiting → ReadyI/O done, event occurredinterrupt handler
Running → Terminatedfinished, fatal error, killedthe process itself
New → Terminatedadmission refusedlong-term scheduler
QueueHolds / drained by
Job queuenot yet admitted; long-term scheduler
Ready queuein memory, waiting for the CPU; short-term scheduler
Device queueswaiting for that I/O; the device controller
Exam trap Three schedulers exist: long-term (job queue), medium-term (swapping a process out and in) and short-term (the CPU). Only the CPU scheduler runs constantly.
Memory trick "Ready asks for the CPU, waiting asks for something else." Both return the same way — the event ends and the process goes back to the ready queue, never straight to the CPU.
Exam trap Waiting only for the CPU means ready, not waiting — the single most asked state question. A process in the device queue is waiting even though it is in memory.
Worked example ✍ trace one process You type a command. (a) new → ready when the long-term scheduler admits it. (b) ready → running when the CPU scheduler dispatches it. (c) running → waiting the moment it issues the print request. (d) waiting → ready when the printer finishes. (e) Earlier a clock interrupt ended its slice: that is running → ready, not running → waiting.

3Process Creation & Termination

written question ★
Definition Creation: the OS takes a PID, allocates and fills a PCB, sets up an address space, attaches open files, and puts the PCB in the ready queue. Termination: the state is marked terminated, memory and files are released, and the exit status goes to the parent.
Step of creationWhat happens
1. Get a PIDfrom the PID table; reused after release
2. Allocate the PCBmemory reserved for the control block
3. Initialise itstate, PC at the entry point, accounts = 0, queue pointers
4. Address spacecopy the parent's image; build page/segment table
5. Open filesdescriptors point at the same inodes
6. ResourcesI/O, memory and CPU quota
7. Ready the contextstack and registers for the first dispatch
8. EnqueuePCB → ready queue, never straight to running
Way a process endsTypical cause
Normal exitmain() returns or exit(0); the value becomes the exit status
Error exitfatal error — divide by zero, invalid memory reference
Killed by another processa signal such as SIGKILL, which cannot be caught
Killed by the OSmemory limit exceeded, protection fault, shutdown
Exam trap A child that finished before its parent collected it stays as a zombie: finished, but its exit status and table entries remain until the parent waits. A child whose parent dies first is an orphan, adopted by init.
Memory trick "Born ready, die finished." Creation ends in the ready queue; termination frees the PID and the PCB. Because init adopts orphans, no zombie is left uncollected.
Worked example ✍ a shell session You type ls > out.txt. (a) The shell forks twice — once for ls, once for the right-hand side of the redirection. (b) The child opens the file before exec; the inode is shared, not copied. (c) exec replaces the image but keeps the PID. (d) When ls exits, the shell's wait() reaps it, so the zombie lives milliseconds.

4Threads: Sharing One Address Space

high-yield ★
Definition A thread is the unit of execution inside a process. Threads of one process share the address space, code, data, open files and signals; each keeps its own stack, registers, program counter and thread-local storage.
PointProcessThread
Address spaceits own, protectedshared with siblings
Private stateeverythingstack, registers, PC, TLS
Creation costheavy: the image is copiedcheap: a thread control block
Communicationneeds IPCjust read the shared variables
Failure effectcontaineda bad write can kill all threads
In the scheduleralways a separate entitydepends on the model below
LevelWhere it livesWhat it gives
User-levela library inside the processcheap switch, but one blocking call blocks the whole process
Kernel-levelthe OS keeps a real thread per entitya blocking call blocks one thread; true parallelism on many cores
Exam trap In many-to-one a blocking call stops all threads and there is no parallelism; in one-to-one parallelism is real but every thread costs a PCB and a kernel stack. Thread scheduling ≠ process scheduling in the first two models: the kernel schedules kernel threads, the library schedules user threads.
Memory trick "Threads share, they do not copy." If you have to say fork() it is a process; if you can simply assign to a global it is a thread.

5Inter-Process Communication

frequently tested ★
Definition IPC lets one process send data to another and coordinate with it. Two families: message passing (copies move through the kernel) and shared memory (fastest — no copy — but it carries no synchronisation at all).
MechanismKindNotes
Shared memorysharedfastest; you add your own locking
Anonymous pipemessagebyte stream, only related processes
Named pipe (FIFO)messagefilesystem name, unrelated processes
Message queuemessagekernel list of discrete messages
Socketmessagenamed endpoint, local or TCP/IP
Signalmessageone-way notice; SIGKILL uncatchable
Mailboxmessageindirect: a named drop box
Choose it whenCost
Shared memory for huge buffers — video frames, indexesevery lock is yours to write
Pipe / FIFO for a stream of bytes, filtered in flightbuffer-limited, no message boundaries
Message queue for discrete jobs that keep their orderfixed maximum queue length
Socket to reach another machine or a serviceserialisation, an address space per connection
Signal for "something changed — re-read your state"no payload; handler runs at an odd moment
Exam trap Pipes serve related processes only — a shell pipeline, a parent and its child. Two unrelated programs need a named FIFO, a socket or shared memory. Shared memory gives no mutual exclusion: two racing writers lose data.
Memory trick "Copy means message passing, map means shared memory, named means unrelated." If the data never moves, a mutex's job is to make it safe.
Worked example ✍ pick the mechanism (a) sort < file | head — anonymous pipe. (b) A logger daemon and 40 unrelated services — named FIFO or socket. (c) A video server writing 4 MB frames to two decoders — shared memory plus a mutex. (d) "Your config file changed" — a signal, then the process re-reads the file itself: a signal is a nudge, not a transfer.

6Semaphores, Mutexes & Producer–Consumer

written question ★
Definition A semaphore (Dijkstra, 1965) is a non-negative integer plus a waiting queue, touched only by two atomic operations: P (wait): if S = 0 block, then S ← S − 1 and V (signal): S ← S + 1, wake one waiter. A binary semaphore — a mutex — stays at 0 or 1.
ConstructValueOwner?Best for
Semaphoreinteger ≥ 0no — any process may V itcounting resources, ordering
Mutex0 or 1yes — only the holder unlocksa critical section
Monitorimplicit, one thread insideautomaticdata + procedures + condition variables
The solution ✍ three semaphores For a buffer of N slots: mutex = 1 (one process inside the buffer code), empty = N (free slots), full = 0 (filled slots).
producer: consumer: wait(empty); wait(full); wait(mutex); wait(mutex); put item; take item signal(mutex); signal(mutex); signal(full); signal(empty);
The order of the two outer waits is the whole problem: a producer claims a free slot before the mutex, a consumer a filled slot before the mutex. Reverse them and both can sit on the mutex for ever.
Trace, buffer of 2Operationmutexemptyfullbuffer (in → out)
—start120empty
1P1 puts x111x
2P2 puts y102x y
3P3 wants to put z102P3 blocks
4C1 takes x111y
5C2 takes y120empty
6P3 wakes, puts z111z
Memory trick "empty counts spaces, full counts items, mutex counts permission, and empty + full always = N." In every row above empty + full = 2; if it is not, the trace is wrong.
Exam trap P decreases, V increases — the semaphore pays out on P. A counting semaphore starting at 7 with 10 P and 6 V ends at 7 − 10 + 6 = 3. Unlocking a mutex you do not own is meaningless.

7Scheduling Criteria & Preemption

formulas ★
Definition CPU scheduling chooses which ready process runs next and for how long. No algorithm wins on every measure, so scheduling is judged against five criteria — and the algorithm a system picks depends on which one that system cares about.
CriterionDefinition & formulaWanted
CPU utilisationbusy fraction = 1 − idle fractionas high as possible
Throughputprocesses completed per unit timeas high as possible
Turnaround timecompletion − arrival, the whole lifeas low as possible
Waiting timeturnaround − CPU burstas low as possible
Response timefirst response − arrivallow — what an interactive user feels
PointNon-preemptivePreemptive
A running processkeeps the CPU till it finishes or blockscan be interrupted and requeued
Needsnothing speciala timer interrupt, OS support
Overheadlow — few switchesone switch per preemption
Response timecan be poor: a long job blocks allgood, bounded by q
Trapnever preempt inside a critical sectiondoing so corrupts the state
Multiprocessing vs time-sharing — the distinction the syllabus asks for

Multiprogramming: several programs in memory, the CPU switches between them

Multiprocessing: several processors, genuine parallelism

Time-sharing: one CPU shared in time slices — the classic time-sharing OS is round robin

Multitasking: several tasks on one CPU, the idea behind time-sharing

Real-time: deadlines matter more than throughput

Batch: throughput maximised, response ignored

Exam trap Waiting time is not turnaround time, and response time is not waiting time. Burst 10, arrival 2, completion 20: TAT = 18, WT = 8, response uses the first dispatch.
Memory trick "Turnaround = arribal to finish. Waiting = turnaround minus burst. Response = arrival to first run."
Worked example ✍ all three times A job arrives at t = 2, is first dispatched at t = 5, blocks for I/O at t = 9, is dispatched again at t = 12 and completes at t = 24; its CPU burst totals 12. (a) Turnaround = 24 − 2 = 22. (b) Waiting = 22 − 12 = 10; the gaps confirm it — (5−2) + (12−9) = 6 while queued, plus 4 in its last dispatch. (c) Response = 5 − 2 = 3. (d) Non-preemptively its response would be 0 — but its neighbours would pay.

OS · Process & SchedulingFCFS, SJF, priority

8Non-Preemptive: FCFS, SJF & Priority

most tested ★
Definition A process keeps the CPU until it finishes or blocks. FCFS serves arrival order, SJF always picks the shortest CPU burst, priority scheduling picks the highest-priority process and breaks ties by FCFS.
AlgorithmRuleGoodBad
FCFSarrival orderfair in CPU time, simple, no starvationconvoy effect: one long job delays every short one
SJFshortest burst firstminimum average waiting time, provably optimalneeds bursts in advance; long jobs may starve
SRTF (preemptive)shortest remaining timealso optimal for average waitingfrequent switches; needs burst estimates
Priorityhighest priority firstexpresses importance; quick response for urgent workstarvation for low-priority processes
Round robin (preemptive)one time quantum each, in turnfair CPU share, bounded response timeswitch overhead if the quantum is small
Worked example 1 ✍ FCFS Bursts 24, 3, 3, all at t = 0. P1 0–24, P2 24–27, P3 27–30. Waiting 0, 24, 27 → average 51/3 = 17 ms. Two 3 ms jobs sat behind a 24 ms job — the convoy.
Worked example 2 ✍ SJF Bursts P1 = 6, P2 = 8, P3 = 7, P4 = 3. Order P4 0–3, P1 3–9, P3 9–16, P2 16–24. Waiting 0, 3, 9, 16 → average 28/4 = 7 ms. FCFS gives 0, 6, 14, 21 → 10.25 ms.
Exam trap SJF is optimal for average waiting time — not for turnaround or response, and not for weighted combinations. It also needs the burst known; in practice the OS estimates it from the process's history, which is why SRTF is really "shortest remaining time next".
Memory trick "Short first, long last" for SJF; the convoy is FCFS's disease; starvation is priority's, and its cure is ageing — the effective priority rises with waiting time.
Ageing, precisely After each wait interval the OS may raise a process's effective priority, or treat "waited too long" as a promotion. Ageing cures starvation only: it has no effect on a deadlock, where nothing is progressing and no priority is ever re-evaluated. A pure priority queue without ageing is rejected in nearly every real design.

OS · Process & SchedulingSRTF & round robin

9Preemptive: SRTF & Round Robin

Gantt charts ★
Definition SRTF preempts the running process whenever a newly arrived job has a shorter remaining time. Round Robin keeps a circular ready queue and preempts after every time quantum q; a process with time left goes to the back of the queue.
Worked example 1 ✍ round robin, q = 4 P1 = 24, P2 = 3, P3 = 3, all arriving at 0. Gantt: P1 0–4, P2 4–7, P3 7–10, then P1 alone 10–30. Waiting = completion − burst: P1 = 30 − 24 = 6, P2 = 7 − 3 = 4, P3 = 10 − 3 = 7 → average 17/3 = 5.67 ms. On this set SJF would give 0, 3, 6 → 3 ms; FCFS 17 ms.
Worked example 2 ✍ SRTF, staggered arrivals P1 (0, 8), P2 (1, 4), P3 (2, 9), P4 (3, 5). At t = 1, P2 (4) beats P1's remaining 7 → preempt; at t = 5 P4 (5) beats P1 (7) and P3 (9); at t = 10 P1 (7) beats P3 (9). Gantt: P1 0–1 | P2 1–5 | P4 5–10 | P1 10–17 | P3 17–26. Completion 17, 5, 26, 10 → turnaround 17, 4, 24, 7 → average 13 ms; waiting 9, 0, 15, 2 → average 6.5 ms.
Time quantum qBehaviour
q → large (q ≥ burst)no preemption in practice → RR degenerates into FCFS
q → smallmany context switches; most time is spent switching, throughput falls
q just above the average burstthe usual choice — fast enough to be interactive, slow enough to batch most work in a few turns
Worst-case responsebounded by (n − 1) × q for n ready processes
Memory trick "The quantum is a promise about waiting: small q promises fairness and a quick first response and pays in switches; large q promises efficiency and pays in response time."
Exam trap (i) In RR, waiting time is completion − arrival − burst, not "time in the queue" counted per quantum. (ii) A process that finishes inside its quantum never waits again. (iii) RR is preemptive; "run to completion in slices" describes FCFS.
Thread vs process scheduling, once more If each process holds one thread, RR gives each process a turn — unfair when one process owns fifty threads. Modern kernels therefore schedule threads, so every runnable thread gets its own slice.

10Multilevel Queues, Feedback & Real-Time

advanced ★
Definition A multilevel queue keeps permanent classes — system processes with a short quantum and round robin, user processes with FCFS or SJF. A multilevel feedback queue (MLFQ) allows movement: a process that burns its whole quantum is demoted, one that waits long enough is promoted.
PointMultilevel queueMultilevel feedback queue
Movementnone — the class is fixeda process is promoted or demoted
Quantum per queueone per classgrows as priority falls
Strengthsimple and cheap; a different admission policy per classseparates interactive from CPU-bound automatically
Weaknessa low class can starveneeds promotion rules to avoid starvation
Real-time policyPriority rule
Rate monotonicstatic: shorter period → higher priority
EDFdynamic: earliest deadline first
Hard real-time in one line A periodic set of n tasks on one processor needs C ≤ T for every task and total utilisation ≤ n(2^(1/n) − 1): 1 task 100 %, 2 tasks 83 %, 3 tasks 78 %.
Exam trap EDF is optimal — it misses a deadline only when no feasible schedule exists. Rate monotonic is optimal only for static priorities and loses to EDF above about 76 % utilisation.
Memory trick "Fixed classes don't move; feedback queues teach the scheduler." And "rate is fixed, deadline is re-read every instant."
Exam trap The long scheduler services only the highest queue when it is non-empty, so low classes can wait for ever — a starvation failure that ageing or promotion fixes.
Worked example ✍ two periodic tasks A control loop needs 10 ms every 40 ms; a logger needs 5 ms every 100 ms. (a) Utilisation = 10/40 + 5/100 = 0.25 + 0.05 = 0.30. (b) Two tasks, so the rate-monotonic bound is 2(2^(1/2) − 1) ≈ 0.828; 0.30 < 0.828, so the set is feasible under rate monotonic. (c) EDF meets the same deadlines and could absorb far more load. (d) If the loop's period shrank to 12 ms, utilisation ≈ 0.883 > 0.828, so rate monotonic can no longer guarantee it and EDF must be used.
