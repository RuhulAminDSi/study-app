DBMS · Concepts & Data ModelsDatabase, DBMS, system

1Database, DBMS and Database System

foundation ★
Definition A database is an organised collection of related data. A DBMS is the software that stores, retrieves and protects it. The database system is the whole assembly: database + DBMS + application programs + users + hardware. Every "which one is X?" question turns on which of those five a name denotes.
DB = data, DBMS = software
TermWhat it actually isExamples
Databasethe data itself, in an organised persistent formstudents, courses, exams of a university
DBMSsoftware sitting between the application and the dataMySQL, Oracle, PostgreSQL, SQL Server; MongoDB is NoSQL
Database systemall five parts togetherwhat a university actually installs and runs
File systemthe OS's files: no rules, no shared accesswhat the database replaced
Why databases replaced files Four failures, four answers: redundancy (a fact stored in several files) → one schema; inconsistency (copies disagree) → constraints; poor sharing → views and a query language; program–data dependence (change the file layout, rewrite every program) → the DBMS owns the storage.
Memory trick "Data, software, everything." Is the DBMS the database? No — the DBMS is the manager. Is the database the DBMS? Also no. Only database system means the whole assembly.
Exam trap A database is not a table, and a file system is not a database: files enforce no schema, no transactions, no concurrency. "Which one enforces integrity?" → the DBMS.
Worked example ✍ an ATM The database is the account table. The DBMS decrypts the PIN, locks the row so nobody withdraws at the same instant, checks the balance and writes the new one. The application is the screen menu; the database system is bank software + core server + card machine + network + customer.

2The Three-Level Architecture

most tested ★
Definition The three-level (three-schema) architecture of ANSI/SPARC splits the database into an external level (what each user sees), a conceptual level (the logical structure of the whole organisation's data) and an internal level (how it is physically stored). Mappings join them — and the mappings are what make data independence possible.
ANSI / SPARC
LevelQuestion it answersWho sees it
External"What does this user see?"one user or application; many views
Conceptual"What data exists, and what does it mean?"the whole organisation's logical view
Internal"Where and how is it stored?"the DBMS alone
Worked example ✍ schema vs instance, one table The schema is Student(id, name, dept) — the blueprint, changed rarely, kept in the data dictionary. The instance is (101,"Alice","CSE"), (102,"Bob","ECE") — the values right now. Schema changes slowly; instance changes constantly.
PointSchemaInstance
Also calledlogical design, metadatasnapshot, current state
Containsnames, columns, types, constraintsthe actual rows stored
Changedrarely, by the designer (DDL)constantly, by every insert (DML)
Stored inthe data dictionary / cataloguethe data files
Memory trick "Outside, Concept, Inside." E = Every user, C = Community view of all data, I = Internal plumbing. Read the stack top down: from the user's words to the bytes on disk.
Exam trap The external level is not one view — there are normally several. The internal level is private to the DBMS; no program is written against it. The conceptual level is logical: no file names, no block sizes.

DBMS · Concepts & Data ModelsData independence

3Why Three Levels? Data Independence

the reason it exists ★
Definition Data independence is the ability to change one level of the schema without changing the level above. There are exactly two kinds; a paper offering "three levels of independence" is testing this. Logical is conceptual → external; physical is internal → conceptual.
The two kinds, precisely Logical data independence — change the conceptual schema (add a column, split a table, add a table) and the external views and programs stay as they were. Harder, because the meaning of data changes.
Physical data independence — change the internal schema (add an index, split a file, reorganise pages, change compression) and the conceptual schema and programs stay as they were. Easier, because the meaning does not change.
Both are delivered by the two mappings: external/conceptual and conceptual/internal.
Logical data independencePhysical data independence
Betweenconceptual level and external levelinternal level and conceptual level
You changethe logical schema: add phone, split a tablethe storage: add a B+ tree index, reorganise pages
Unaffectedexternal views and application programsconceptual schema and application programs
Holds becausethe external/conceptual mapping is rewrittenthe conceptual/internal mapping is rewritten
Typical exampleadding a column without touching any querydropping an index changes speed, not meaning
Difficultyharder — the meaning changeseasier — only the layout changes
Memory trick "Logical is on top, physical is underneath." Read the arrow upwards in each pair: logical independence changes the level above, physical the level below.
Exam trap There are two kinds, not three. Adding an index is physical; adding a column is logical; reformatting a file without touching the schema is the classic physical example.
Worked example ✍ name the change "The admin rebuilds the table with a hash index on dept." → physical: the queries still mean the same. "A column nationality is added to Student." → logical: the conceptual schema changed.
IT link This is the reason a dump from one engine can be reloaded into another, and the reason `ALTER TABLE … ADD COLUMN` on a big table is operationally cheaper than rewriting every program that reads that table. A view is the external level made real: it stores a query, not a copy of the data.

4The Entity-Relationship Model in Chen's Notation

draw it from memory ★
Definition The E-R model (Peter Chen, 1976) is a high-level conceptual model used to design a database before any table is built. It has three primitive components — entity, attribute, relationship — and every one has a fixed symbol.
Chen, 1976
ComponentSymbolExample
Strong entityrectangleEmployee
Weak entitydouble rectangleDependent
Attributeellipsename, id
Key attributeunderlinedid
Deriveddashed ellipseage
Multivalueddouble ellipsephones
RelationshipdiamondEnrolls
Identifyingdouble diamondowns
Cardinality1, N, M on arms1:N, M:N
Total particip.double lineevery emp has a dept
Exam trap A weak entity set is a double rectangle — not a diamond (relationship), not an ellipse (attribute), not a dashed ellipse (derived attribute). Its identifying relationship is a double diamond. A weak entity has no key of its own: it is identified by the owner's key + its own partial key.
Memory trick "Rectangle entity, ellipse attribute, diamond relationship, underlined = key." Then one letter per exception: double rectangle = weak, dashed ellipse = derived, double ellipse = multivalued, double diamond = identifying. A composite attribute is an ellipse with sub-ellipses (address = house, street, city).
Worked example ✍ reading an E-R diagram "Every DEPARTMENT rectangle has one name underlined and a dashed ellipse no_of_staff. A double rectangle ASSIGNMENT joins PROJECT to it." — name is a key attribute; no_of_staff is derived; ASSIGNMENT is a weak entity, meaningless until you know which project and which employee it belongs to.

DBMS · Concepts & Data ModelsCardinality

5Cardinality: 1:1, 1:N and M:N

highest-yield ★
Definition Cardinality states how many instances of one entity may be associated with one instance of the other. There are only three shapes — 1:1, 1:N, M:N — and the shape decides how many relations the design needs.
CardinalityMeaningExampleMapping to relations
1:1one A, at most one BPerson ↔ Passportno new table: put the "one" side's PK as an FK in the other table
1:None A, many BDepartment ↔ Studentsno new table: the "one" side's PK as an FK in the "many" side
M:Nmany A, many BStudent ↔ Coursesits own relation whose FKs point to both sides
1:N with datathe relationship itself carries since, gradeStudent ↔ Enrolsthe junction table becomes necessary even for 1:N
Exam trap For 1:N the foreign key goes on the N side; on the "one" side it would need several ids in one cell, which breaks 1NF. An M:N cannot be written with any single foreign key: a student has many courses and a course has many students, so neither table can hold the other's list. Only M:N forces a new relation.
Worked example ✍ why M:N needs a table Try to put the link in Student: the column courses would hold {CSE101, MAT201} — a multi-valued cell, so one student gives one value per column, exactly what 1NF forbids. Put it in Course and the same problem appears. Therefore ENROLLS(student_id, course_code), with an FK to each side; the pair is usually the composite key too.
Choosing the side for a 1:1 Put the foreign key on the side that may be missing: the employee table gets passport_no, so an employee without a passport stores NULL, whereas putting it on Passport would demand a passport row for every employee. For 1:N the side is not a choice — the key always goes on the N side.

6The Relational Model

vocabulary test ★
Definition The relational model (E. F. Codd, 1970) represents data as relations — mathematical sets of tuples over named attributes. A relation is shown as a table: tuples are rows, attributes are columns. Two properties matter in every answer: a relation has no duplicate tuples and no order.
Codd, 1970
Formal termEveryday nameMeaning
Relationtablea set of tuples with the same attributes
Tuplerow / recordone fact: (101,"Alice","CSE")
Attributecolumn / fielda named property: name, dept
Domainallowed value setintegers 1–999 for id
Degreearity, #columnsStudent has degree 3
Cardinality#rowsStudent holds 3 tuples
Relation schematable definitionStudent(id, name, dept)
Formal properties Cells hold atomic values only · tuples are unique · tuple and attribute order does not matter · every tuple has the same attributes in the same domains.
Memory trick "Table–Row–Column–Set." "Is degree rows or columns?" → columns. "Is cardinality rows or columns?" → rows. Degree and cardinality are the pair examiners swap.
Exam trap A table may be sorted on screen, but the relation is a set, so row order is not part of the data. Degree does not change when rows are added. Two identical rows are not allowed — that is what the primary key prevents.
Worked example ✍ describe one table formally Student(id, name, dept) holding (101,"Alice","CSE"), (102,"Bob","ECE"), (103,"Carol","CSE"). Relation name Student; degree 3 (three attributes); cardinality 3 (three tuples); domain of id = integers 1–999; id underlined, so it is the key attribute. Adding a fourth student raises cardinality to 4 and leaves degree at 3.

7Keys: Super, Candidate, Primary, Foreign, Composite

most tested ★
Definition A superkey is any set of attributes that uniquely identifies a tuple. A candidate key is a superkey that is minimal — remove one attribute and it no longer identifies. The primary key is the single candidate key chosen as the official identifier. A foreign key points at another relation's candidate key. A composite key is built from two or more attributes.
KeyWhat it isRuleExample
Superkeyidentifies a rowmay be larger{id, name}
Candidate keyminimal superkeynothing extra{id}
Primary keythe chosen keyone per table; never NULLPRIMARY KEY (id)
Foreign keypoints at another keyreferential integritydept_id REFERENCES Dept(id)
Composite key2 or more attributesa PK may be composite(StudentID, CourseID)
Alternate keya key not chosenstill UNIQUE{passport_no}
Memory trick "Every candidate key is a superkey; every primary key is a candidate key; a foreign key is somebody else's primary key." The nesting runs one way: superkey ⊇ candidate key ⊇ primary key.
Exam trap A table has exactly one primary key but many candidate keys and many superkeys. A primary key may be composite — it need not be one column. A foreign key column may hold NULL; only its non-NULL values must match.
Worked example ✍ classify the keys of one table Person(pid, passport_no, phone). {pid} unique → superkey; remove pid and it fails → minimal → candidate key; chosen → primary key. {passport_no} is minimal too → alternate key. {pid, phone} is unique but not a candidate key, since phone can be dropped.

8Constraints and the Two Integrity Rules

why constraints exist ★
Definition A constraint is a rule declared on a column or a table that restricts what may be stored, so the data stays correct however it is written. SQL gives six constraint forms, and they exist to protect two named properties: entity integrity and referential integrity.
two integrity rules
ConstraintWhat it forbidsSQL
NOT NULLa NULL in the columnname VARCHAR(50) NOT NULL
UNIQUEtwo rows sharing a value (NULL excepted)email VARCHAR(100) UNIQUE
PRIMARY KEYNULLs and duplicates — implies the two aboveid INT PRIMARY KEY
FOREIGN KEYa value matching no key of the referenced tabledept_id INT REFERENCES Dept(id)
CHECKa value failing a stated conditionCHECK (Age >= 18)
DEFAULTnothing — supplies a value when none is givenstatus VARCHAR(20) DEFAULT 'active'
The two integrity rules constraints protect Entity integrity — the primary key is never NULL and is unique in every row. A relation must be addressable: a row with no identity cannot be pointed at. Enforced by PRIMARY KEY.
Referential integrity — every non-NULL foreign key value must match an existing key value in the table it references. No orphans. Enforced by FOREIGN KEY; on deleting the parent you must choose CASCADE, SET NULL, SET DEFAULT or RESTRICT.
CREATE TABLE Enrolls ( student_id INT NOT NULL REFERENCES Student(id), course_code CHAR(7) NOT NULL REFERENCES Course(code), grade CHAR(2) CHECK (grade IN ('A','B','C','F')), enrolled_on DATE DEFAULT CURRENT_DATE );
Exam traps ✍ two of them 1. A foreign key exists to enforce referential integrity — not entity integrity, encryption or faster sorting; entity integrity is the primary key's job. A FK column may hold NULL. 2. DROP removes the table's structure and its data; DELETE removes rows (optionally by WHERE) and TRUNCATE removes all rows, but both keep the structure; ALTER changes the structure and keeps the data.

9Triggers, and E-R Model vs Relational Model

wraps up ★
Definition A trigger is stored logic the DBMS executes automatically when an event happens on a table — before, after, or instead of an INSERT, UPDATE or DELETE. The application never calls a trigger; the engine fires it, which is why it cannot be bypassed by any client.
TimingFires
BEFOREbefore the row is written; may change NEW
AFTERafter the row is written; OLD and NEW both available
FOR EACH ROWonce per affected row, not per statement
INSTEAD OFon a view, to make it updatable
Exam trap A trigger is not a stored procedure: nobody executes it by name, it fires on an event. It is not a substitute for a constraint — a CHECK is cheaper and clearer. Foreign-key enforcement is done by the constraint, not by a trigger.
CREATE TRIGGER trg_student_count AFTER INSERT ON Student FOR EACH ROW BEGIN UPDATE Department SET StudentCount = StudentCount + 1 WHERE DeptID = NEW.DeptID; END;
Worked example ✍ three uses 1. Maintain a count: the trigger above adds 1 to that department's head-count after every insert. 2. Audit: after any update of salary, copy the old and new value into Salary_Log. 3. Validate: before inserting, reject a booking dated in the past — though a CHECK is preferred.

  1. Definition (1) — database = the data; DBMS = the managing software; database system = database + DBMS + applications + users + hardware. Schema = the blueprint, kept in the data dictionary; instance = the rows now. 1
  2. Three levels (2) — external (user views, one per application), conceptual (logical structure of all data: tables, relations, constraints), internal (files, pages, indexes). ANSI/SPARC. 2
