1The Binary Heap: a Complete Tree Stored in an Array

shape + order ★
Definition A binary heap is a binary tree that satisfies two properties at once. Shape: it is a complete binary tree — every level is full except possibly the last, which is filled from the left. Order (heap property): in a max-heap every parent ≥ its children, so the maximum is at the root; in a min-heap every parent ≤ its children, so the minimum is at the root. Nothing is said about left versus right child — a heap is not a binary search tree.

Shape facts ✍ the numbers Height of an n-node heap = ⌊log₂ n⌋. A heap of height h holds between 2^h and 2^(h+1) − 1 nodes. There are ⌈n/2⌉ leaves, and at most ⌈n / 2^(h+1)⌉ nodes of height h. Because the tree is complete, the array has no gaps — that is the only reason the index arithmetic works.
Memory trick "Double to go down, halve to go up." With the root at 1, a left child is the parent doubled and the right child is one more; the parent is the child halved and floored. For a 0-based array "shift by one": add 1 before you double, subtract 1 before you halve.
Exam trap ✍ three 1. Read the question's indexing first: 2i, 2i+1 is the answer only for a root at index 1; for a root at 0 it is 2i+1, 2i+2. 2. In a max-heap the minimum is in one of the leaves (positions ⌊n/2⌋+1 … n), not necessarily the last array cell. 3. An array sorted in descending order is always a valid max-heap, but a valid max-heap is not in general sorted.
Generalisation: the d-ary heap Same complete-tree-in-an-array idea, but every node has d children. 0-based: children of i are d·i + 1 … d·i + d, parent is ⌊(i − 1)/d⌋. Height ≈ log_d n, so insert / decrease-key = O(log_d n) (fewer levels to climb) but extract-min = O(d · log_d n) (d children compared per level). A large d suits many decrease-keys and few extracts — e.g. Dijkstra on a dense graph.

2Heap Operations: Sift-Up, Sift-Down and What Each Costs

all O(log n) ★
Insert = sift-up (bubble-up) Put the new key in the next free slot (index n+1) so the tree stays complete, then swap it with its parent while it is larger (max-heap). At most one swap per level ⇒ O(log n). Increase-key in a max-heap (decrease-key in a min-heap) is the same sift-up.
Extract-max = sift-down (heapify) Save the root, move the last element to the root, shrink n, then swap it with its larger child until both children are smaller. Two comparisons per level ⇒ O(log n). This sift-down is called MAX-HEAPIFY.

Exam trap ✍ heapify vs build-heap "Heapify takes O(n)" is a classic muddle. HEAPIFY (one sift-down from one node) is O(log n). BUILD-HEAP (heapify every internal node, bottom-up) is O(n). Read which one the question means. Also: a heap gives the max in O(1), but searching for any other key is O(n).

3Build-Heap in O(n), Heapsort, and the Priority Queue

the proof they ask for ★
BUILD-MAX-HEAP Copy the n keys into the array as they are, then call MAX-HEAPIFY(A, i) for i = ⌊n/2⌋ down to 1. Leaves (⌊n/2⌋+1 … n) are already one-node heaps, so they are skipped; going bottom-up guarantees both subtrees of i are heaps when i is heapified.
Why O(n), not O(n log n) ✍ 4 marks Heapify at a node of height h costs O(h), and there are at most ⌈n / 2^(h+1)⌉ such nodes. So
T(n) = Σ_(h=0..⌊log n⌋) ⌈n/2^(h+1)⌉ · O(h) = O(n · Σ h/2^h).
Since Σ_(h≥0) h/2^h = 2, T(n) = O(2n) = O(n). Intuition: half the nodes are leaves and do no work, a quarter sink at most one level, an eighth at most two — the expensive nodes are rare.
Worked example ✍ Build a max-heap from [3, 9, 2, 1, 4, 5], n = 6, so start at ⌊6/2⌋ = 3.
i = 3: 2 vs child 5 → swap → [3, 9, 5, 1, 4, 2]
i = 2: 9 vs 1, 4 → no swap
i = 1: 3 vs 9, 5 → swap with 9 → [9, 3, 5, 1, 4, 2]; 3 now at 2, vs 1, 4 → swap with 4 → [9, 4, 5, 1, 3, 2]
Check: 9 ≥ 4, 5 · 4 ≥ 1, 3 · 5 ≥ 2 ✓ — 3 swaps.
Exam trap ✍ two ways to build Inserting the n keys one by one (top-down, sift-up each) costs O(n log n) in the worst case — e.g. keys arriving in increasing order into a max-heap, each rising to the root. The bottom-up BUILD-HEAP is O(n). Both give a valid heap, but not necessarily the same array; a question that asks for "the heap after building" means the bottom-up method unless it says "insert one at a time".
Heapsort — the link to sorting Build a max-heap, then repeat n − 1 times: swap A[1] ↔ A[k], shrink the heap by one, MAX-HEAPIFY(A, 1). The array is a heap on the left and a growing sorted run on the right. Build-heap O(n) + (n − 1) extract-max at O(log n) each ⇒ O(n log n) in best, average and worst case. In-place (O(1) extra space) but not stable. A max-heap sorts ascending. The full comparison with quicksort and merge sort is in the sorting lesson of this chapter.
Priority queue (ADT) A collection where each element has a priority and the operations are insert, find-max, extract-max, increase-key (max-PQ) or their min versions. The heap is its standard implementation: an unsorted array gives O(1) insert but O(n) extract; a sorted array the reverse; a heap gives O(log n) for both.

4Mergeable Heaps: the Binomial Heap and the Fibonacci Heap

union is the point ★
Binomial heap B0 is one node; Bk = two Bk−1, one root hung under the other. Bk has 2k nodes, height k, C(k, i) nodes at depth i and a root of degree k. A binomial heap is a list of heap-ordered binomial trees with at most one Bk per k — the trees match the 1-bits of n: 13 = 1101₂ ⇒ B3, B2, B0, so at most ⌊log₂ n⌋ + 1 trees.
Memory trick "A binomial heap is n written in binary; union is binary addition." Two Bk are two 1-bits in one column: link them into a Bk+1 and carry — union is O(log n). Insert is "add 1": a long carry chain makes its worst case O(log n), but like a binary counter it is O(1) amortized.
Fibonacci heap (Fredman & Tarjan, 1984) A collection of heap-ordered trees whose roots sit in a circular, doubly-linked root list, with a pointer H.min to the smallest root. The trees need not be binomial and several may share a degree — the structure is lazy: it postpones tidying until an extract-min forces it. Each node stores its key, degree, parent, one child pointer, left/right sibling pointers (children form their own circular list, so any splice or list concatenation is O(1)) and a boolean mark = "has lost a child since it last became a child of another node".
The cheap operations Insert: make a one-node tree, splice it into the root list, update H.min — O(1), no tidying. Union: concatenate the two root lists, keep the smaller min — O(1). Find-min: read H.min — O(1).
Extract-min = the cleanup Remove H.min, move its children to the root list, then consolidate: link two roots of equal degree (larger key under smaller) until all degrees differ, using an array indexed by degree; then scan the roots for the new min.
Decrease-key = cut + cascading cut Lower x's key. If it is now smaller than its parent y, cut x: move it (with its subtree) to the root list and unmark it. Then: if y is unmarked, mark it and stop; if y is already marked, cut y too and repeat on y's parent — the cascading cut — until an unmarked node or a root is reached. In one line: a non-root node may lose one child; losing a second gets it cut.
Exam trap ✍ Why these heaps exist: a binary heap cannot merge faster than O(n). Binomial and Fibonacci heaps are pointer-based mergeable heaps (so are leftist and skew heaps).

5Heap Costs Compared, and Why Dijkstra Wants a Fibonacci Heap

amortized ≠ worst case ★
Worked example ✍ a cascading cut In the tree on the previous sheet, 24 and 18 are marked. Decrease 46 → 15: 15 < parent 24 ⇒ cut 15 to the root list; 24 is marked ⇒ cut 24 (with 26) as well; its parent 7 is a root ⇒ stop. Decrease 39 → 1: 1 < 18 ⇒ cut 1; 18 is marked ⇒ cut 18; its parent 3 is a root ⇒ stop; H.min = 1. Each cut is O(1); the cascade is paid for by the marks it clears.
Potential function Φ(H) = t(H) + 2·m(H): t = trees in the root list, m = marked nodes. Consolidation is paid for by the trees it removes; each cascading cut unmarks a node (−2) and adds a tree (+1), so it pays for itself ⇒ decrease-key is O(1) amortized.
Where "Fibonacci" comes from Since a node loses at most one child before it is cut, a node of degree k roots a subtree of at least Fk+2 ≥ φk nodes (φ ≈ 1.618). So the maximum degree is D(n) ≤ ⌊logφ n⌋ ≈ 1.44 log₂ n — which makes extract-min O(log n) amortized.

Dijkstra / Prim: count the heap calls ✍ On a graph with V vertices and E edges both algorithms do V inserts, V extract-mins and up to E decrease-keys. Array (no heap): V × O(V) ⇒ O(V²) — best for dense graphs. Binary heap: (V + E) × O(log V) ⇒ O((V + E) log V). Fibonacci heap: V × O(log V) + E × O(1) ⇒ O(E + V log V). The gain is in the E decrease-keys: O(log V) → O(1). (Algorithms: graph-algorithms lesson.)
Exam trap ✍ two 1. Fibonacci bounds are amortized: one extract-min can really cost O(n) (n roots after n inserts), one decrease-key O(log n). 2. Extract-min is never O(1) here.
Memory trick "Fibonacci is lazy: everything is O(1) except taking the minimum out." Insert, union, find-min, decrease-key — O(1); extract-min and delete — O(log n), because that is when the lazy heap tidies its root list. And "lose one child, get marked; lose two, get cut." In practice a binary heap is often faster.

6B-Trees: Order m, Minimum Degree t, and the Height Bound

two conventions ★
Definition A B-tree (Bayer & McCreight, 1972) is a balanced multiway search tree designed for disks: one node = one disk block, holding many sorted keys. A node with k keys has k + 1 children, and the keys separate the key ranges of the children. All leaves are at the same level, so every search reads the same number of blocks. Because the fan-out is large, the height is tiny, and search, insert and delete are all O(log n).
Order m (Knuth) — the exam convention 1. Every node has at most m children ⇒ at most m − 1 keys.
2. Every internal node except the root has at least ⌈m/2⌉ children ⇒ at least ⌈m/2⌉ − 1 keys (non-root leaves keep the same key minimum).
3. The root has at least 2 children unless it is a leaf ⇒ at least 1 key.
4. All leaves on the same level.
Minimum degree t (CLRS) t ≥ 2. Every non-root node has t − 1 to 2t − 1 keys, i.e. t to 2t children if internal. The root has at least 1 key. A node with 2t − 1 keys is full.
Translation: order m = 2t, so CLRS trees always have an even order. t = 2 ⇒ order 4 ⇒ the 2-3-4 tree.

Height bound ✍ derivation Fewest keys for height h (CLRS): root 1 key, then 2 nodes, 2t, 2t², … , 2th−1 nodes with t − 1 keys each:
n ≥ 1 + (t−1)·Σ 2t^(i−1) = 2t^h − 1
⇒ h ≤ log_t((n + 1)/2). In order-m form: h ≤ log_⌈m/2⌉((n+1)/2). Most keys at height h: every node full ⇒ m^(h+1) − 1.
Cost of a search Descend from the root, choosing the child between the two keys that bracket the target. Disk reads = O(h) = O(log_t n). CPU work is O(t) per node by linear scan (O(log t) with binary search) ⇒ O(t log_t n) CPU in total. Disk reads dominate, which is why t is chosen so one node fills one block.
Exam trap ✍ which "order"? "Order" in an MCQ almost always means Knuth's maximum number of children: order 5 ⇒ max 4 keys, min 2 keys in a non-root node. Do not answer "5 keys". If the question gives a minimum degree t instead, use t − 1 … 2t − 1 keys. And the minimum is ⌈m/2⌉ children — so ⌈m/2⌉ − 1 keys.

7B-Tree Insertion (Split) and Deletion (Borrow / Merge)

the worked example ★
Insertion Search down to the correct leaf and insert the key in sorted position. If the leaf now has m keys (overflow), split it: the median key moves up into the parent, the keys left of it form one node and those right of it another. If the parent overflows, split it too. A split of the root makes a new root — the tree grows only at the root, which is why all leaves stay on one level.
Deletion 1. Key in a leaf with more than the minimum ⇒ just remove it. 2. Key in an internal node ⇒ replace it by its in-order predecessor (largest key of the left subtree) or successor, then delete that key from its leaf. 3. A leaf underflows (below ⌈m/2⌉ − 1 keys) ⇒ borrow from an adjacent sibling that has spare keys (rotate through the parent), else merge with a sibling plus the parent's separator key. A merge can make the parent underflow; if the root empties, the tree shrinks by one level.
Worked deletions on that tree ✍ order 5, min 2 keys Delete 40 (borrow): leaf [40, 50] → [50] underflows. Left sibling [10, 20] has only the minimum, right sibling [70, 80, 90] has a spare ⇒ rotate: separator 60 comes down, 70 goes up. Result: root [30 | 70], leaves [10, 20] [50, 60] [80, 90].
Delete 20 from the original tree (merge): [10, 20] → [10] underflows; its only sibling [40, 50] has no spare ⇒ merge [10] + separator 30 + [40, 50] = [10, 30, 40, 50]. Root becomes [60] with leaves [10, 30, 40, 50] and [70, 80, 90] — still valid (root ≥ 1 key).
Memory trick "Too full? Split and push the middle up. Too empty? Borrow from a rich sibling, else merge and pull the separator down." Insert pushes keys up; delete pulls keys down. Height changes only at the root, in both directions.
Exam trap ✍ 1. A B-tree never grows at the leaves — new levels appear above the old root. 2. With an even order the overflowing node has an even count, so there are two middles; textbooks differ (left- or right-biased) — state your choice. 3. CLRS inserts in one pass, splitting every full node on the way down, so it never has to back up.

8The B+ Tree, Database Indexes, and the Big Comparison

linked leaves ★
Definition A B+ tree is a B-tree variant in which all records (or record pointers) live in the leaves; internal nodes hold only copies of keys as signposts, and the leaves are linked in key order (the sequence set).

Fan-out arithmetic ✍ 4 KB page, 8-byte key + 8-byte child pointer ⇒ about 4096 ÷ 16 = 256 children per node. Three levels reach 256³ = 16,777,216 leaves. Root cached in RAM ⇒ any of ~16 million keys in 2–3 disk reads.
Where they are used Databases: MySQL InnoDB, PostgreSQL, Oracle and SQL Server use B+ trees for ordinary indexes. File systems: NTFS directory indexes (B+ tree), ext4 directories (HTree, a hashed B-tree), XFS and Btrfs (B-trees). B+ tree vs hash index: see the database chapter.

  1. (a) Build-heap (3) — heapify i = ⌊n/2⌋ … 1; a node of height h costs O(h) and there are ≤ ⌈n/2^(h+1)⌉ of them; Σ ⌈n/2^(h+1)⌉·O(h) = O(n Σ h/2^h) = O(2n) = O(n). 3
  2. (b) Splits (3) — order 5 ⇒ max 4 keys, min 2. 10–40 fill one leaf; 50 overflows ⇒ median 30 up: [30] / [10 20] [40 50]. 60, 70 ⇒ [40 50 60 70]; 80 overflows ⇒ 60 up: [30 60] / [10 20] [40 50] [70 80]; 90 ⇒ [70 80 90]. 3
  3. (b) Delete 40 (2) — [50] underflows; left sibling at minimum, right sibling [70 80 90] has a spare ⇒ borrow: 60 down, 70 up ⇒ [30 70] / [10 20] [50 60] [80 90]. 2
  4. (c) Fibonacci heap (2) — insert, union, find-min, decrease-key O(1); extract-min, delete O(log n) amortized. Dijkstra = V extract-min + E decrease-key = O(V log V + E). 2
