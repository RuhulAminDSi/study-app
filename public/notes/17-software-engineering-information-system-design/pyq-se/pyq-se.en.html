Viva What are the levels of software testing? What is unit / integration / system / acceptance testing?

bank IT viva boards (asked one by one and again as "levels")

LevelWhat is testedBy · against
Unitone function / class alone (stubs, drivers, mocks)developer · module design
Integrationinterfaces and data flow between modulesdeveloper, tester · architecture
Systemwhole system, functional and non-functionalindependent testers · SRS

2Name the Testing Type: Functional or Not?

written ×3
Q4(b) Identify the testing type in each scenario and say whether it is Functional, Non-Functional or Both: (1) verifying the smallest testable unit; (2) re-running tests to check the application still works after code changes; (3) performance and responsiveness under a specific amount of traffic; (4) preliminary testing of basic functions before detailed testing; (5) verifying that integrated modules work together.

Petrobangla AM (CSE) · 31.05.2024  ·  BOGMC (Petrobangla) AM · 2024  ·  also set in another recruitment paper

Functional vs non-functional Functional = what the system does (input → expected output). Non-functional = how well: performance, load, stress, security, usability, reliability.
Exam trap Regression re-runs functional and non-functional tests (a release can also get slower), so "Both". Re-testing re-runs only the failed case. Smoke = broad, shallow; sanity = narrow, deep.

4White-box = Structural Testing

MCQ ×2
Asked MCQs ✍ Q86 Which technique is called structural testing? → White box.  Q21 Which is not a focus of white-box testing: code coverage / data flow / user perspective / code logic? → User perspective (that is black-box). 49th BCS ICT paper 2 · 2025

Coverage, weakest → strongest: statement → branch (decision) → condition → MC/DC → path. 100% branch ⇒ 100% statement, not the reverse.

Cyclomatic complexity V(G) = E − N + 2 = decisions + 1 = regions = number of basis paths = minimum test cases for basis-path testing.
int f(int x){ int s = 0; while (x > 0) { // decision 1 if (x % 2) s += x; // decision 2 x--; } return s; }

Tests x = 0 (loop skipped), x = 1 (odd branch), x = 2 (even, then odd) cover every edge: 3 cases = V(G).

5Equivalence Classes & Boundary Values

written
Q3 What is black box testing? A program computes the square root of an input integer between 0 and 5000. Determine the equivalence class test cases, and the test cases using boundary value analysis.

Petrobangla AM (IT) · 16.09.2022 (BUET)

Black-box testing tests the program only through its inputs and outputs, against the specification, without looking at the code (behavioural testing).

Equivalence classes: one representative per class → {−5, 500, 6000}. Every value in a class should behave alike.

Boundary values: errors cluster at the edges 0 and 5000 → {−1, 0, 5000, 5001}; the robust set adds 1, 4999 and a nominal 2500.

InputExpected output
−1, 5001rejected: "invalid input"
0 · 1 · 25000 · 1 · 50
4999 · 500070.70 · 70.71
Exam trap A test case is an input plus its expected output: give both. For n inputs, normal BVA needs 4n + 1 cases (min, min+, nominal, max−, max), robust BVA 6n + 1 (adds min− and max+): here 5 and 7.

6Verification & Validation (CMMI Level 3)

written
Q9 Verification and validation are two process areas at CMMI level 3. For both: (a) give a definition; (b) describe how you can fulfil these areas in your software testing activities.

Bangladesh Bank, Assistant Maintenance Engineer · 04.02.2023 (BIBM)

(a) Verification (VER) ensures work products meet their specified requirements: "Are we building the product right?" Peer reviews, inspections, walkthroughs, static analysis, tests against the spec.
(a) Validation (VAL) shows the product fulfils its intended use in its real environment: "Are we building the right product?" UAT, alpha/beta, prototypes, usability tests.
  1. Plan: pick work products and methods; build a traceability matrix (requirement → test cases)
  2. VER: review SRS, design and test cases; code review, static analysis; unit, integration and system tests against the spec
  3. VAL: users set acceptance criteria; UAT in a production-like environment; beta or pilot run
  4. Analyse: log defects, find root causes, fix, re-test, regression; report coverage, defect density; sign-off

7The Software Development Life Cycle

10 marks
Q2 Explain the concept of the Software Development Life Cycle (SDLC) and describe its main phases. 10 marks

bank Assistant Programmer, written

Concept SDLC is a structured framework of phases to plan, build, test, deploy and maintain software that meets its requirements on time and within budget. Each phase has set activities and a deliverable that feeds the next; process models (waterfall, incremental, spiral, agile) differ in how they order and repeat the phases.
PhaseKey activitiesOutput
1 Planning, feasibilityscope, cost, schedule; technical, economic, operational feasibilityfeasibility report
2 Requirementsinterviews, questionnaires, JAD sessions, prototypesSRS
3 Designarchitecture (HLD), modules (LLD), DB, UI; DFD, ERD, UMLdesign document
4 Codingcode to standards, version control, unit testssource code
5 Testingintegration, system and acceptance tests; fix defectstest report
6 Deploymentinstall, convert data, train users, change overlive system
7 Maintenancecorrective, adaptive, perfective, preventive changesnew versions
Memory trick "Please Read, Design, Code, Test, Deploy, Maintain": P-R-D-C-T-D-M.
Exam trap Over a product's life, maintenance is the costliest phase, and most of it is perfective (new features), not bug fixing.

10Project Scheduling & the Gantt Chart

MCQ ×2
Asked MCQs ✍ Q9 Main goal of project scheduling? → allocate resources and set deadlines.  Q11 Which is used for project scheduling: pie chart / bar chart / Gantt chart / all? → Gantt chart. 49th BCS · 2025

Gantt chart: tasks as horizontal bars on a time axis, showing start, duration, overlap and progress. It shows dependencies poorly, so pair it with a PERT/CPM network.

Critical path = longest path = shortest project time; its tasks have zero slack. B and C need A, D needs B and C: A–C–D = 3 + 4 + 1 = 8 weeks; B may slip 2 weeks.

Exam trap A Gantt chart is drawn with bars, but the standard answer is Gantt chart; a pie chart shows shares, not time, so "all" is wrong.

11CI/CD: Stages & Benefits

written
Q7 What is the CI/CD development model? Explain its major stages and benefits.

Islamic Bank PLC, SQA Senior Officer (Network) · 14.03.2025

CI (continuous integration): developers merge small changes into the shared main branch several times a day; every merge triggers an automatic build and test run. CD = continuous delivery (every green build is releasable; going live needs one manual approval) or continuous deployment (it goes live automatically).

  1. Source: a push or pull request starts the pipeline
  2. Build: compile, fetch dependencies, make an artifact or container image
  3. Test: unit and integration tests, static analysis, security scans
  4. Release: deploy to staging; smoke, acceptance, performance tests
  5. Deploy: to production by rolling, blue-green or canary release
  6. Monitor: logs, metrics, alerts, rollback
Benefits bugs caught minutes after they are written · small, low-risk releases · faster delivery · repeatable builds, fewer manual errors · quick rollback · constant feedback. Tools: Git, Jenkins, GitHub Actions, GitLab CI, Docker, Kubernetes.
Git: commit vs push commit saves a snapshot in your local repository (works offline); push uploads local commits to the remote so the team and CI see them. bank Assistant Programmer, Q5
Memory trick add → stage · commit → my desk · push → the team's shelf · pull = fetch + merge. CI = "merge often, test always"; CD = "always ready to ship".

12Coupling & Cohesion

written
Q3 Explain the concepts of Coupling and Cohesion with examples.

Bangladesh Satellite Company PLC, Assistant Engineer (CSE) · 23.08.2025

Coupling = how much modules depend on each other; aim low, so a change does not ripple. Cohesion = how strongly the parts inside one module serve one task; aim high, so the module is easy to understand, test and reuse.

Exam trap Good design = low coupling, high cohesion. "High coupling" is never a design principle.

13Code Smells: Examples & Fixes

written ×4
Q11 Give examples of the following code smells: (a) Feature Envy (b) Dead Code (c) Duplicate Code (d) Shotgun Surgery.

asked in a recruitment paper

(a) Feature Envy: a method uses another object's data more than its own.

class ShippingCalc { double cost(Order o) { return o.getWeight() * o.getZone().getRate(); } }

Fix: Move Method → Order.shippingCost().

(b) Dead Code: never runs, or its result is never used.

double price(double p) { double old = p * 0.95; // never used if (LEGACY_V1) { ... } // always false return p * 0.90; }

Fix: delete it; version control keeps the history.

(c) Duplicate Code: the same logic pasted in several places.

// in register() AND updateProfile() if (email == null || !email.contains("@")) throw new IllegalArgumentException();

Fix: Extract Method validateEmail().

(d) Shotgun Surgery: one change forces small edits in many classes.

// VAT 0.15 typed into Cart, Invoice, // Receipt and Report: new rate = 4 edits

Fix: one TaxPolicy class or constant (Move Field).

Exam trap Shotgun surgery = one change → many classes. Divergent change is the opposite: one class changed for many different reasons.

14Architecture & Patterns: a Monitoring System

written
Q2 A third-party cloud service is used for continuous system monitoring through APIs. (a) Which software architecture would you recommend? (b) Which design patterns would be appropriate? (c) Explain why you selected them.

Bangladesh Satellite Company PLC, Assistant Engineer (CSE) · 21.08.2026

(a) Architecture: an event-driven architecture of small services (microservices; or modules of one app for a small team), with a message broker in the middle and an adapter layer facing the third-party API.

(b) PatternWhere it is used
Adapter / Facadewrap each vendor API behind our own MetricsSource interface
Observer / Publish–Subscriberule engine, alerting and dashboard subscribe to metric events
Circuit Breaker + Retryvendor outages, timeouts, rate limits (exponential backoff)
Strategy · Factoryswappable alert rules and channels · a collector per provider
(c) Justification ① Loose coupling to the vendor: the adapter isolates API changes; a new provider touches one class. ② Scalability: collectors and processors scale separately; the broker absorbs bursts. ③ Reliability: the circuit breaker and the queue stop one failure from cascading, and no event is lost. ④ Real-time: events are pushed to subscribers at once. ⑤ Extensibility: a new alert channel is one more subscriber or strategy (open–closed principle). ⑥ Testability: every part can be tested against a mock API.
Exam trap State the trade-off: microservices add deployment and monitoring overhead; for a small team a modular monolith with the same patterns is a valid answer. The justification earns more marks than the label.

16COCOMO: Development Time

MCQ, math
Q96 An organic software has 32 KLOC. The nominal development time (in months) using the COCOMO model is: (a) 6 (b) 7 (c) 14 (d) 21

49th BCS ICT paper 2 · 2025

Basic COCOMO (Boehm, 1981)
Effort E = a(KLOC)b person-months
Time T = c(E)d months
Staff = E / T · productivity = LOC / E
Modeabcd
Organic2.41.052.50.38
Semi-detached3.01.122.50.35
Embedded3.61.202.50.32
Solution ✍
  1. 321.05 = 38.05
  2. E = 2.4 × 38.05 = 91.3 PM
  3. 91.30.38 = 5.56
  4. T = 2.5 × 5.56 = 13.9 ≈ 14 months → (c)
  5. Staff = 91.3 / 13.9 ≈ 6.6 ≈ 7 people; productivity ≈ 350 LOC/PM
  6. Same 32 KLOC: semi-detached 145.5 PM, embedded 230.4 PM, both ≈ 14.3 months
Exam trap Intermediate COCOMO uses a = 3.2 for organic (then × EAF from 15 cost drivers). Putting 3.2 into the basic formula gives E ≈ 121.8 PM and T ≈ 15.5 months, not 14. Option (b) 7 is the staff figure, not months.

17Risk Analysis Techniques

written
Q9(a) Describe the different techniques used in risk analysis of software development.

38th BCS Written · 2018

Risk management = identify → analyse → prioritise → plan → monitor. The analysis techniques:

  1. Identification: risk checklists, brainstorming, Delphi (anonymous experts), interviews, SWOT, assumption analysis, past-project lessons
  2. Categorising: project, product, business risks; or five impact areas: new technology, requirements, architecture, performance, organisation
  3. Qualitative: rate probability and impact (negligible → catastrophic) on a probability–impact matrix
  4. Quantitative: risk exposure RE = P × L; decision trees (expected value), sensitivity analysis, Monte Carlo simulation
  5. Prioritise & respond: rank by RE; avoid, mitigate, transfer or accept (RMMM plan)
Worked examplePLoss LRE = P × LRank
requirements keep changing0.6Tk 5 lakhTk 3.0 lakh1
key developer leaves0.3Tk 6 lakhTk 1.8 lakh2
third-party API changes0.5Tk 2 lakhTk 1.0 lakh3
Exam trap The question asks for techniques. Listing only risk categories (technology, requirements …) earns part marks; add identification methods, the matrix and RE = P × L.

18Viva Rapid-Fire

bank IT viva

Q. What is an API?
→ Application Programming Interface: a contract (endpoints, formats, rules) that lets one program use another's services or data without knowing its internals.

Q. How does an API work?
→ The client sends a request (HTTP method, URL, headers with an auth token, JSON body) → the API authenticates, runs the logic, reads the DB → returns a status code (200, 201, 400, 401, 404, 500) and JSON. Styles: REST, SOAP, GraphQL, gRPC.

Q. What is an Information System?
→ people, hardware, software, data and procedures (plus network) that collect, process, store and distribute information.

Q. Role of IS in an organisation?
→ runs daily transactions (TPS), supports decisions (MIS, DSS, ESS), communication, records and compliance, competitive advantage.

Q. Management software? Examples?
→ software to plan, run and control resources and processes: ERP (SAP, Oracle, Microsoft Dynamics 365, Odoo), Tally (accounting), CRM, HRM/payroll, Jira; in banks, core banking (Temenos T24, Finacle).

Q. Do you know app development?
→ Android: Kotlin/Java; iOS: Swift; cross-platform: Flutter (Dart), React Native; the app talks to the server through REST APIs. Name an app you built.

Q. What is ERP? Why is it used?
→ Enterprise Resource Planning: one integrated suite on a single database for finance, HR, procurement, inventory, sales, production. Gives one source of truth, no double entry, automated workflows, real-time reports, an audit trail.

Q. What is MRP? MRP vs ERP?
→ Material Requirements Planning: from the production schedule, bill of materials and stock it decides what material, how much, when. MRP = manufacturing materials only; MRP II added capacity and finance; ERP = the whole enterprise.

Q. System vs solution?
→ System: interacting components doing one function (a core banking system). Solution: the full answer to a business problem: one or more systems plus process change, integration, training, support.

Q. How is ISO applied in software?
→ ISO 9001 (quality management), ISO/IEC 12207 (life-cycle processes), ISO/IEC 25010 (product quality), ISO/IEC/IEEE 29119 (testing), ISO/IEC 27001 (security); through defined processes and certification audits.

Q. Levels and methods of testing? Acceptance testing?
→ unit, integration, system, acceptance (sheet 2); black, white, grey box (sheet 3). Acceptance = users confirm business fit before go-live.
