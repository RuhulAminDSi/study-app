1What Is Software Engineering?

MCQ + Written
Definition The systematic, disciplined and quantifiable application of engineering method to software: how it is specified, designed, built, verified, deployed, maintained and evolved. Coined at the NATO, Garmisch 1968 conference, which also named the software crisis.

Why a process is unavoidable

Attribute of softwareWhy it forces a process
Complexityno physical law limits it
Conformityobeys contracts, standards, law
Changeabilityneeds move while being built
Invisibilityprogress shown only by artefacts
Memory trick C-C-C-I — Complexity, Conformity, Changeability, Invisibility. A "which is not an attribute?" question is answered with rigidity or fatigue.

3The Process, Its Framework, Its Universal Practices

high-yield
Software process The set of activities, their order, roles, inputs and outputs, that turns a requirement into an operating product. A model / paradigm is one particular arrangement of it — real teams work hybrid.
TermMeans
Processactivities + order + roles + artefacts
Methodologya process plus its rules and paperwork
Model / paradigmthe shape of the process
Toolautomates an activity (CASE, IDE)

6Process Models I — Waterfall, V-Model

model level
Common ground Every model performs the same activities. What differs is the order, the feedback and the timing of tests. Never memorise a model as a list of phases — memorise its shape.

6.1 Waterfall (linear / sequential) model

  • Origin: Benington, IBM, 1956; Royce, 1970 drew it and listed its defects.
  • Shape: phases in strict order, each signed off before the next.
  • Fits: requirements understood and frozen; fixed-price contracts; regulated work.
  • Strengths: discipline, a document at every gate, easy budgeting, contract-friendly.
  • Weaknesses: no working software until late, wrong requirements found very late, inflexible to change.
Exam trap Royce did not propose the waterfall as a recipe for success — his 1970 paper presents it as a model with serious problems, to be cured by feeding verification results back into every phase.

6.2 V-Model (verification & validation model)

Left arm — developmentRight arm — the matching test level
RequirementsAcceptance testing (the user's view)
System designSystem testing (whole system)
Architectural designIntegration testing (modules)
Module designUnit testing (by the developer)
Memory trick Read the V-model from the bottom up for the pairings: module→unit, architecture→integration, system→system, requirements→acceptance. "The smaller the design box, the smaller the test."

7Process Models II — Prototyping, Incremental, Big Bang

high-yield

7.1 Prototyping model

  • Use when requirements are unclear and must be explored with the user before the build.
  • 1st gen / throw-away: a paper or screen model used only to find requirements, then discarded.
  • 2nd gen / evolutionary: improved repeatedly until it becomes the product.
  • Strength: kills requirements ambiguity early; the user sees a working thing fast.
  • Weakness: users may mistake a prototype for the product, so quality shortcuts survive.
  • Trap: prototyping is not "build it twice and keep the worse version".

7.2 Incremental (evolutionary delivery) model

  • Shape: the system grows in working, releasable increments; each runs the whole SDLC. Increment 1 is the core product, not a stub.
  • Fits: requirements can be listed and prioritised; the customer can use the system early.
  • Strength: usable software early, feedback per release, risk spread over time.
  • Weakness: total cost can exceed waterfall; a later increment re-does requirements and design.
  • Trap: iterative ≠ incremental — iterative repeats a process; incremental adds a slice.

7.3 Big Bang model (build-and-ship, no process)

  • Shape: no phases at all — requirements, design, coding and testing all at once; one release.
  • Fits: tiny, low-risk, throwaway experiments where the schedule beats the method.
  • Strength: zero process overhead, fastest possible first build.
  • Weakness: massive late risk — no feedback, no intermediate release, unmaintainable afterwards.
Exam trap Big Bang is not "the waterfall done badly" — it is the absence of a process.

8Process Models III — Spiral (Boehm) & RAD

most-asked

8.1 Spiral model

  • Author: Boehm, 1986, adapting risk-management practice for large projects.
  • Shape: risk-driven — each loop does planning → risk analysis → engineering → evaluation; the product grows progressively from a prototype.
  • Quadrants: 1 objectives, alternatives, constraints · 2 evaluate and resolve risks · 3 develop and verify the next-level product · 4 plan the next iteration.
  • Fits: large, high-risk, expensive-to-fail projects — defence, banking core, safety-critical.
  • Strengths: makes risk explicit and front-loaded; combines cyclic work with reuse.
  • Weaknesses: expensive; needs trained risk analysts; without discipline it is "chaotic waterfall".
Memory trick Clockwise from the top-left: Objectives → Risk → build → Plan (ORBP) — one full round per loop.

8.2 RAD — Rapid Application Development

RAD A time-boxed, small-team, component-reuse approach: analysis, design and prototyping are fused into one round and the product is built in about 90 days. Popularised in the 1980s by James Martin.
  • Fits: small teams, GUI/business applications, requirements understood by both sides.
  • Does not fit: large mission-critical back-end systems, heavy safety demands, distributed teams.
  • Strength: extremely short cycle; the user works with the system continuously.
  • Weakness: narrow fit; time-boxing pushes testing and documentation out.
Memory trick The three R's of RAD: Rapid, Requirements already known, Reuse. RAD is what you do once prototyping has made the requirements clear.
Agile: iterative + incremental + prototyping (Manifesto, 2001).

10The SDLC Phases: Activity and Deliverable of Each

most-asked table
SDLC Software Development Life Cycle — the ordered phases from feasibility study to retirement. A written answer must give, for each phase, the main activity and the artefact it produces.
PhaseMain activitiesDeliverable (artefact)
0 FeasibilityTELOS check — technically, economically, legally, operationally possible?Feasibility report, project charter
1 Requirements analysis & specificationelicit (interviews, questionnaires, observation, prototyping), analyse, specify, validate, manage changeSRS, use cases, user & system requirements
2 System designarchitecture, modules, interfaces, data design; HLD then LLD; UML diagramsdesign document (HLD/LLD), UML class & sequence diagrams
3 Implementation / codingwrite the code, unit-test as written, code review, integrate modulessource code, unit-test results, build
4 Testingverification and validation; unit → integration → system → acceptancetest plan & cases, defect log, report
5 Deploymentinstall, data migration, user training, transition, post-deployment reviewrelease package, installation & user manual

Memory trick: maintenance Corrective = bug · Adaptive = new OS · Perfective = new feature · Preventive = stop future bugs (CAPP). About 60–80% of the life-cycle cost is spent here.
Memory trick: cost of a late fix The later a defect is caught, the dearer the repair: ×1 → ×5 → ×10 → ×15–50 → ×100.

Memory trick Each model answers one question. Waterfall: "is it finished?" · V-model: "is it tested?" · Prototyping: "is it the right thing?" · Incremental: "is some of it shipped?" · Spiral: "is it safe?" · RAD: "is it fast?"
Exam trap "In which model does testing begin first?" — if the option says "at the design of the unit", the answer is the V-model. "Which model has no phases?" → Big Bang; "which repeats the entire life cycle?" → incremental / iterative / spiral, never waterfall.
Iterative = repeat the process; incremental = add a slice.
