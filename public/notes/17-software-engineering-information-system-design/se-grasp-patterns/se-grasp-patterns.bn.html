১গ্র্যাস্প: দায়িত্ব বরাদ্দের সমস্যা

MCQ + লিখিত
সংজ্ঞা গ্র্যাস্প (GRASP) = জিeneral আরesponsibility এssignment এসoftware পিatterns: কোন অবজেক্টের ওপর কোন দায়িত্ব বসবে তা ঠিক করার নির্দেশিকা, যাতে ফলাফল কম কাপলড, বেশি কোহেজিভ, রক্ষণাবেক্ষণযোগ্য ও পুনর্ব্যবহারযোগ্য হয়। প্রস্তাবক জেমস ক্যারেল ও মার্টিন ফাউলার, ১৯৯১ (Toward Unified Design Methodologies, IEEE Computer)।

দায়িত্বের দুই প্রকার

  • জানা (knowing) — নিজের অ্যাট্রিবিউট ও সঙ্গে যুক্ত অবজেক্ট।
  • করা (doing) — যে কাজগুলো অবজেক্টটি করে (তার অপারেশন)।

একটি প্যাটার্ন (Singleton, Strategy, Observer …) হলো কাঠামোসহ একটি নামকরা সমাধান। আর একটি গ্র্যাস্প নির্দেশিকা হলো মাত্র একটি বাক্য, যা বলে দায়িত্ব কোথায় রাখতে হবে — এর সঙ্গে কোনো ক্লাস ডায়াগ্রাম বা কোড টেমপ্লেট থাকে না।

নয়টি নির্দেশিকা, প্রতিটি এক লাইনে

#নির্দেশিকানীতি, এক লাইনে
১Information Expertতথ্য যার কাছে আছে, তাকেই দায়িত্ব
২Creatorযে ক্লাস অন্যকে ধারণ বা একত্রিত করে, সে-ই তৈরি করে
৩Low Couplingযে ক্লাস অন্যদের ওপর সবচেয়ে কম নির্ভরশীল, তাকে
৪High Cohesionএক ক্লাসে সর্বোচ্চ সম্পর্কযুক্ত দায়িত্ব
৫Polymorphismসাবক্লাসে সুপারক্লাসের আচরণ নতুন করে লিখবেন না
৬Pure Arbitersযে অবজেক্ট দুই বা ততোধিকের মধ্যে সালিশ করে
৭Don't Talk to Strangersশুধু নিজের সরাসরি সহযোগীর কাছে জিজ্ঞাসা করুন
৮Controllerসিস্টেম ইভেন্ট পাওয়া প্রথম non-UI অবজেক্ট
৯Intermediary (Pure Fabrication)নির্ভরতা ভাঙতে বানানো কাল্পনিক, ডোমেন-নিরপেক্ষ ক্লাস
গ্র্যাস্পের সঙ্গে আরও যে তিনটি আসে Indirection — এমন একটি মধ্যবর্তী অবজেক্ট যা পরস্পর অচেনা অবজেক্টগুলোকে যুক্ত করে। Protected Variations — অনুমিত পরিবর্তনের প্রতিটি বিন্দুকে একটি ইন্টারফেসের ভেতরে রাখুন। Known / Unknown Dependencies — জানা নির্ভরতা সরাসরি উল্লেখ করুন; বদলানো যায় এমন নির্ভরতার সামনে ইন্টারফেস।
পরীক্ষার ফাঁদ গ্র্যাস্প হলো দায়িত্ব বরাদ্দের নির্দেশিকা, প্রস্তাবক Carell ও Fowler (১৯৯১) — এটি প্যাটার্নের তালিকা নয়, GoF ডিজাইন প্যাটার্নও নয়। Pure Arbiters কখনো "Pure Arbiters / Information Expert" হিসেবে ছাপা হয়: দুটি করে গণনা করবেন না।

SE · গ্র্যাস্প ও ডিসিডিইনফো এক্সপার্ট ও ক্রিয়েটর

২ইনফরমেশন এক্সপার্ট ও ক্রিয়েটর — উদাহরণসহ

হাই-ইল্ড
Information Expert (ইনফরমেশন এক্সপার্ট) সেই অবজেক্টকে দায়িত্ব দিন যার কাছে কাজটি করার জন্য প্রয়োজনীয় তথ্য আছে। উদাহরণ: Invoice-ই getTotal() হিসাব করবে, কারণ LineItem-এর তালিকা কেবল Invoice-এর কাছেই আছে।
class LineItem { Product product; int quantity; double getSubTotal() { return product.price * quantity; } } class Invoice { List<LineItem> items; double getTotal() { return items.stream() .mapToDouble(LineItem::getSubTotal) .sum(); } }

এই উত্তরটি কেন সঠিক

  • লাইন আইটেমগুলো কেবল Invoice-এর কাছে, তাই যোগফল করতে পারে কেবল সেই।
  • কোনো প্যারামিটার পাঠাতে হয় না, কোনো LineItem-এর ব্যাক-পয়েন্টার লাগে না।
  • জ্ঞান থাকে যে ক্লাসের কাছে ডেটা, তার ভেতরেই: কাপলিং কমে, কোহেশন বাড়ে।
পরীক্ষার ফাঁদ Information Expert মানে "সবচেয়ে বেশি মেথড থাকা ক্লাস" নয়। এটি সেই ক্লাস যার কাছে প্রয়োজনীয় ডেটা আছে। ডেটা অন্যত্র থাকলে দায়িত্ব সেখানেই যাবে।

২ক ক্রিয়েটর (Creator) — উদাহরণসহ

Creator ক্লাস B-কে ক্লাস A-এর ইনস্ট্যান্স তৈরির দায়িত্ব দিন, যদি যেকোনো একটি শর্ত সত্য হয়: B ধারণ করে A · B একত্রিত করে A · B-তে A রেকর্ড আছে · B ঘনিষ্ঠভাবে ব্যবহার করে A · B-এর কাছে A-কে initialise করার ডেটা আছে।
class Sale { List<SalesLineItem> lines; SalesLineItem addLine(Product p, int q) { SalesLineItem l = new SalesLineItem(p, q); lines.add(l); return l; } }
মনে রাখার কৌশল Creator = "C for Container"। B যদি A ধারণ না করেও A-এর প্রতিটি ফিল্ডের initial মান বলতে পারে, তবে সেও স্বাভাবিক Creator — কারণ ওখানে তৈরি করলে কলকারকে যে আর্গুমেন্ট দিতে হয় কমে যায়।
পরীক্ষার ফাঁদ Creator মানে "যে ক্লাস ব্যবহার করে" তা নয়। POS সিস্টেমে Sale — Register, ProductCatalog বা Payment নয় — SalesLineItem তৈরি করে, কারণ Sale সেগুলোকে ধারণ করে।

৩লো কাপলিং ও হাই কোহেশন — উদাহরণসহ

লিখিতে প্রিয়
Low Coupling (লো কাপলিং) এমনভাবে দায়িত্ব বরাদ্দ করুন যাতে অপ্রয়োজনীয় নির্ভরতা সর্বনিম্ন থাকে। পরীক্ষায় বলার নিয়ম: দায়িত্ব সেই ক্লাসকে দিন যা অন্য ক্লাসের ওপর সবচেয়ে কম নির্ভরশীল। নির্ভরতা মাপা হয় কতটা পরিমাণ অন্য অবজেক্টের স্টেট জানতে হয় তা দিয়ে।

খারাপ — হাই কাপলিং

class Customer { String name; void saveToDatabase() { // opens a JDBC connection, // builds SQL, commits a tx } }

ক্ষতি: Customer এখন DB, SQL, ড্রাইভার ও নেটওয়ার্ক জানে।

ভালো — লো কাপলিং

class CustomerRepository { void save(Customer c) { // all DB logic lives here } } class Customer { String name; // no DB knowledge }

লাভ: Customer পুনর্ব্যবহারযোগ্য, repository বদলানো যায়, দুটি আলাদা ইউনিট টেস্ট করা যায়।

৩ক হাই কোহেশন — উদাহরণসহ

// LOW COHESION — the "god class" class CustomerManager { void browseShop() { } void chargeCard() { } void shipOrder() { } void sendEmail() { } void updateDatabase(){ } }

পাঁচটি অসম্পর্কিত কাজ: পরিবর্তনের কোনো একটি কারণ নেই, আর প্রতিটি পরিবর্তন পাঁচটিকেই ঝুঁকিতে ফেলে।

// HIGH COHESION — split it class Customer { /* customer data */ } class Cart { /* cart operations */ } class Payment { /* payment logic */ } class Shipping { /* delivery */ } class Notifier { /* e-mail */ }

প্রতিটির পরিবর্তনের একটিমাত্র স্পষ্ট কারণ আছে — SRP-রই আরেক রূপ।

মনে রাখার কৌশল কাপলিং হলো এই বেলুনে কতগুলো সুতো বাঁধা — চারটি সুতো আর ওড়ে না। কোহেশন হলো তার নিজের অংশগুলো কতটা জোরে জোড়া লেগে আছে: পাঁচটি অসম্পর্কিত কাজ = নুড়ির ঢেলি, পাথর নয়।
পরীক্ষার ফাঁদ দুটি আলাদা মাপকাঠি: কাপলিং হলো ক্লাসগুলোর মধ্যে, কোহেশন এক ক্লাসের ভেতরে। একটি ক্লাস অত্যন্ত কোহেজিভ হয়েও তিনটি অপ্রয়োজনীয় ক্লাসের সঙ্গে কাপলড হতে পারে।
IT link ব্যাংক কোর তার লেজার নিয়মগুলো ইন্টারফেসের পেছনে রাখে: ব্যবসায়িক ক্লাসগুলো না ছুঁয়েই SQL বদলানো যায়।

৪পলিমরফিজম, কন্ট্রোলার, ইন্টারমিডিয়ারি ও বাকিগুলো

হাই-ইল্ড
Polymorphism (পলিমরফিজম) সাবক্লাসকে এমন আচরণ দেবেন না যা সুপারক্লাসে আগে থেকেই আছে। দায়িত্বটি সুপারক্লাস বা ইন্টারফেসে রাখুন, রান টাইমে সঠিকটি বেছে নিতে পলিমরফিজম দিয়ে হবে। CashPayment · CardPayment · MobileBanking — সবাই process() ভাগ করে।
Pure Arbiters (পিওর আর্বাইটার্স) এমন অবজেক্টকে দায়িত্ব দিন যা দুই বা ততোধিকের মধ্যে সালিস করে — যে নিয়ম দুপাশের দুজনেরই দরকার কিন্তু কারও নিজের নয়। যে TaxPolicy Invoice ও Refund দুজনই জিজ্ঞাসা করে।
Don't Talk to Strangers কোনো মেথড অন্যের ওপর অতিরিক্ত নির্ভরতা রাখলে নিয়ম ভাঙে। শুধু নিজের সরাসরি সহযোগীর কাছে জিজ্ঞাসা করুন। কখনো Order-এর ভেতর দিয়ে Order.getCustomer().getAddress() ধরবেন না।
Controller (কন্ট্রোলার) enterItem-এর মতো সিস্টেম ইভেন্ট যে অবজেক্ট UI স্তরের পরে প্রথম গ্রহণ করে ও সমন্বয় করে। দুই প্রকার: ফ্যাসেড কন্ট্রোলার (গোটা সিস্টেমের প্রতিনিধি) ও ইউজ-কেস / সেশন কন্ট্রোলার (একটি পরিস্থিতি)। UI ক্লাসে কখনো নয়।
