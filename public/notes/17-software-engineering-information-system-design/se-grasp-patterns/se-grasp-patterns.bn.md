# গ্র্যাস্প প্যাটার্ন, ডিসিডি ও টেস্টিং কৌশল: রিভিশন নোট (সরকারি আইটি পরীক্ষা)

> `notes/src/17-software-engineering-information-system-design/se-grasp-patterns.bn.html`-এর প্লেইন-টেক্সট সঙ্গী (হাতে-লেখা-ধাঁচের PDF: `notes/pdf/17-software-engineering-information-system-design/se-grasp-patterns.bn.pdf`)।
> শ্রোতা: বাংলাদেশের সরকারি আইটি নিয়োগ পরীক্ষা (বিএসপিএস অ্যাসিস্ট্যান্ট প্রোগ্রামার, বাংলাদেশ ব্যাংক অ্যাসিস্ট্যান্ট প্রোগ্রামার/AME, ব্যাংকার্স সিলেকশন কমিটি অফিসার (IT))। MCQ + লিখিত।

**সিলেবাসের যে অংশ (সফটওয়্যার ইঞ্জিনিয়ারিং ও তথ্য সিস্টেম ডিজাইন):** "…Object Oriented software development and design … **Designing Objects with responsibilities**। **GRASP patterns with General Principles in assigning responsibilities**: Information expert, Creator, Low Coupling and High Cohesion, **Creating design class diagrams and mapping design to codes**। Software Testing: **White Box and Black Box testing**। **Basis Path Testing**। Testing for specialized environment." পাশের লেসন: ভি-মডেল, ইউজ কেস মডেল ও CRC কার্ড → *ওয়াটারফল, ইনসেপশন, ইউজ কেস ও UML*; ইউনিট → ইন্টিগ্রেশন → ভ্যালিডেশন → সিস্টেম লেভেল, ডিবাগিং, রক্ষণাবেক্ষণ, SQA ও মানের মেট্রিক্স → *টেস্টিং কৌশল, রক্ষণাবেক্ষণ, মান ও মেট্রিক্স*।

**হাই-ইল্ড:**

1. **গ্র্যাস্প (GRASP)** = **জি**eneral **আর**esponsibility **এ**ssignment **এস**oftware **পি**atterns — কোন অবজেক্টের ওপর কোন দায়িত্ব বসবে তা ঠিক করার **নির্দেশিকা**। প্রস্তাবক **জেমস ক্যারেল ও মার্টিন ফাউলার, ১৯৯১** (*Toward Unified Design Methodologies*, *IEEE Computer*)।
2. গ্র্যাস্প হলো **দায়িত্ব বরাদ্দের নির্দেশিকা** — প্যাটার্নের তালিকা নয়, GoF ডিজাইন প্যাটার্নও নয়।
3. দায়িত্বের দুই প্রকার: **জানা** (নিজের অ্যাট্রিবিউট ও যুক্ত অবজেক্ট) ও **করা** (অপারেশন)।
4. **Information Expert** (ইনফরমেশন এক্সপার্ট) → যে ক্লাসের কাছে **তথ্য আছে**। *Sale* তার লাইন আইটেম জানে, তাই মোট হিসাব করার দায়িত্ব *Sale*-এর।
5. **Creator** (ক্রিয়েটর) → যে ক্লাস অন্যকে ধারণ করে, একত্রিত করে, রেকর্ড রাখে, ঘনিষ্ঠভাবে ব্যবহার করে বা initialise করার ডেটা রাখে, সে তৈরি করে। POS সিস্টেমে **Sale** — Register, ProductCatalog বা Payment নয় — **SalesLineItem** তৈরি করে।
6. **Low Coupling** (লো কাপলিং) → দায়িত্ব যে ক্লাস অন্যদের ওপর **সবচেয়ে কম নির্ভরশীল**, তাকে; নির্ভরতা মাপা হয় কতটা অন্যের **স্টেট** জানতে হয় তা দিয়ে।
7. **High Cohesion** (হাই কোহেশন) → **পরিবর্তনের একটিমাত্র স্পষ্ট কারণ**; এটি মূলত Single Responsibility নীতিই।
8. **Polymorphism** (পলিমরফিজম) → সাবক্লাসে সুপারক্লাসের আগে থেকেই থাকা আচরণ নতুন করে লেখা নয়; দায়িত্বটি অ্যাবস্ট্রাকশনে রাখুন, রান টাইমে বহুরূপতা ঠিক করবে।
9. **Pure Arbiters** (পিওর আর্বাইটার্স) → যে অবজেক্ট **দুই বা ততোধিকের মধ্যে সালিস করে**।
10. **Don't Talk to Strangers** → শুধু **নিজের সরাসরি সহযোগীর** কাছে জিজ্ঞাসা করুন; A-এর ভেতর দিয়ে B-এর ভেরিয়েবলে হাত দেবেন না।
11. **Controller** (কন্ট্রোলার) → সিস্টেম ইভেন্ট গ্রহণকারী **প্রথম non-UI অবজেক্ট**; দুই প্রকার — ফ্যাসেড কন্ট্রোলার ও ইউজ-কেস/সেশন কন্ট্রোলার।
12. **Intermediary / Pure Fabrication** → **কাল্পনিক**, **ডোমেন অর্হহীন** ক্লাস, সাধারণত নিম্ন-স্তরের প্যাকেজে, নির্ভরতা ভাঙতে।
13. **Protected Variations** → প্রতিটি **অনুমিত পরিবর্তনের** বিন্দুর সামনে ইন্টারফেস; **Known / Unknown Dependencies** → **জানা** নির্ভরতা সরাসরি উল্লেখ করুন, বদলানো **যায় এমন** নির্ভরতার সামনে ইন্টারফেস।
14. গ্র্যাস্প ↔ SOLID: **High Cohesion ≈ SRP** · **Low Coupling ≈ Dependency Inversion / OCP** · **Protected Variations ≈ OCP + Strategy** · **Polymorphism ≈ LSP** · **Indirection / Intermediary ≈ DIP**।
15. **ডোমেন মডেল** একটি *ধারণাগত* দৃষ্টিভঙ্গি: ক্লাস, অ্যাট্রিবিউট, অ্যাসোসিয়েশন, মাল্টিপ্লিসিটি — কিন্তু **অপারেশন নেই**। **ডিসিডি** একটি *সফটওয়্যার* দৃষ্টিভঙ্গি, যাতে যোগ হয় **অপারেশন (স্বাক্ষরসহ), অ্যাট্রিবিউট ও রিটার্ন টাইপ, ভিজিবিলিটি চিহ্ন ও নেভিগেবিলিটি**। ডোমেন মডেলের ক্লাসের নাম **বহুবচন**, ডিজাইন ক্লাসের নাম **একবচন**।
16. ডিসিডি ↔ কোড ম্যাপিং **এক-এক-এক**: একটি ক্লাস বক্স → একটি ক্লাস; অ্যাট্রিবিউট → একটি ফিল্ড; অপারেশন → একটি মেথড; নেভিগেবিলিটিসহ অ্যাসোসিয়েশন **1 → \*** → একটি রেফারেন্স ফিল্ড ও একটি **কালেকশন**; ◇/◆ → whole–part রেফারেন্স; △ → ইনহেরিট্যান্স।
17. **হোয়াইট বক্স** কেস বের করে কোডের **অভ্যন্তরীণ কাঠামো** থেকে (টেস্ট বেসিস = ডিজাইন মডেল/কোড); **ব্ল্যাক বক্স** **স্পেসিফিকেশন** থেকে (টেস্ট বেসিস = প্রয়োজনীয়তা)। টেস্টিং ত্রুটের **উপস্থিতি** দেখাতে পারে, অনুপস্থিতি কখনো নয়।
18. কভারেজ, দুর্বল থেকে শক্তিশালী: **স্টেটমেন্ট ⊂ ব্রাঞ্চ ⊂ কন্ডিশন ⊂ পাথ**; মাল্টিপল-কন্ডিশন কভারেজে প্রতিটি সত্য-মিথ্যা সংমিশ্রণ লাগে, মোট **2ⁿ**। "১০০ % পাথ কভারেজ" কখনোই বাস্তবসম্মত লক্ষ্য নয়।
19. **সাইক্লোম্যাটিক জটিলতা** (McCabe, ১৯৭৬): **M = E − N + 2P**; সাধারণ মডিউলে **P = 1**, তাই পরিচিত রূপ **M = E − N + 2**। সরল শর্তীয় কোডে **M = (স্বাধীন শর্ত) + 1**, আর কোনো শর্ত না থাকলে **M = 1**। McCabe-এর ঐতিহাসিক সীমা **10**।
20. **M** আসলে **স্বাধীন পাথের** সংখ্যাই — ফ্লো গ্রাফের ক্ষেত্রসমূহ। একটি **স্বাধীন পাথ** অন্তত একটি **নতুন নোড** বা **নতুন শর্ত** আনে। বেসিস পাথ টেস্টিংয়ে ঠিক **M**টি টেস্ট কেস দরকার।
21. **সমতুল্য বিভাজন (EP)** প্রতি শ্রেণি থেকে একটি প্রতিনিধি নেয়; **সীমানা মান বিশ্লেষণ (BVA)** প্রতিটি সীমানার ঠিক নিচে, ওপরে ও মাঝে পরীক্ষা করে — বৈধ মাতা ১৮–৬০ হলে **17, 18, 19** ও **59, 60, 61**।
22. **ভি-মডেলে** ডিজাইন লেভেল: ব্যবসায়িক প্রয়োজন ↔ গ্রহণযোগ্যতা · সিস্টেম প্রয়োজন ↔ সিস্টেম টেস্ট · **আর্কিটেকচার ↔ ইন্টিগ্রেশন টেস্ট** · **বিস্তারিত ডিজাইন ↔ ইউনিট টেস্ট**।

**সংকেত:** হলুদ = মূল শব্দ · লাল বৃত্ত = মুখস্থ রাখার তথ্য · বেগুনি বক্স = মনে রাখার কৌশল · লাল বক্স = পরীক্ষার ফাঁদ · সবুজ = সমাধানকৃত উদাহরণ।

**সূচিপত্র:** গ্র্যাস্প: উৎস ও নির্দেশিকা … পৃ. ২ · ইনফো এক্সপার্ট ও ক্রিয়েটর … পৃ. ৩ · লো কাপলিং ও হাই কোহেশন … পৃ. ৪ · বাকি নির্দেশিকাগুলো … পৃ. ৫ · ডিসিডি: ডোমেন মডেল বনাম ডিজাইন মডেল … পৃ. ৬ · ডিসিডি উদাহরণ ও কোড … পৃ. ৭ · হোয়াইট বনাম ব্ল্যাক বক্স, ইপি ও বিভিএ … পৃ. ৮ · কভারেজ, সাইক্লোম্যাটিক, বেসিস পাথ … পৃ. ৯ · পরীক্ষার আগের রাতের পাতা … পৃ. ১০ · অনুশীলন MCQ + লিখিত … পৃ. ১১।

## ১. পুরো টপিক এক পাতায় (কভার)

*(চিত্র: কেন্দ্রে হলুদ দীর্ঘচক্র "গ্র্যাস্প · ডিসিডি / টপিক মাইন্ড ম্যাপ", আটটি রেখা টেনে আটটি বাক্সে ছড়ানো — দায়িত্ব বরাদ্দ (নীল), Carell ও Fowler, ১৯৯১ ★ (লাল), ডিসিডি বনাম ডোমেন মডেল ★ (লাল), ইনফো এক্সপার্ট · ক্রিয়েটর ★ (লাল), কাপলিং ↔ কোহেশন ★ (লাল), পলিমরফিজম · কন্ট্রোলার (সবুজ), M = E − N + 2P ★ (লাল), ইপি · বিভিএ · ভি-মডেল (সবুজ)। লাল = বেশি আসে, সবুজ = পদ্ধতি / প্রয়োগ।)*

পুরো টপিক এক বাক্যে: **গ্র্যাস্প ঠিক করে কার ওপর কোন দায়িত্ব** → **ডিসিডি সেই সিদ্ধান্ত ডায়াগ্রামে লিখে রাখে** → **ডিসিডি এক-এক-এক কোডে ম্যাপ হয়** → **টেস্টিং কৌশল সেই ডিজাইন লেভেলই যাচাই করে** (স্ট্রাকচারাল বনাম ফাংশনাল, সাইক্লোম্যাটিক জটিলতা, বেসিস পাথ)।

**কভারের হাই-ইল্ড তালিকা**

1. গ্র্যাস্প = **Carell ও Fowler, ১৯৯১**
2. Information Expert = **ডেটা থাকা ক্লাস**
3. Creator = **ধারণকারী ক্লাস**
4. **সবচেয়ে কম নির্ভরশীল** ক্লাস জেতে
5. ডিসিডি যোগ করে **অপারেশন ও নেভিগেবিলিটি**
6. **M = শর্ত + ১**

| পৃ. ২ | গ্র্যাস্পের উৎস, দায়িত্বের দুই প্রকার, নয়টি নির্দেশিকা |

## ২. গ্র্যাস্প: দায়িত্ব বরাদ্দের সমস্যা

**সংজ্ঞা।** **গ্র্যাস্প (GRASP)** = **জি**eneral **আর**esponsibility **এ**ssignment **এস**oftware **পি**atterns: কোন অবজেক্টের ওপর কোন দায়িত্ব বসবে তা ঠিক করার **নির্দেশিকা**, যাতে ফলাফল কম কাপলড, বেশি কোহেজিভ, রক্ষণাবেক্ষণযোগ্য ও পুনর্ব্যবহারযোগ্য হয়। প্রস্তাবক **জেমস ক্যারেল ও মার্টিন ফাউলার, ১৯৯১** (*Toward Unified Design Methodologies*, *IEEE Computer*)।

**দায়িত্বের দুই প্রকার**

- **জানা (knowing)** — নিজের অ্যাট্রিবিউট ও সঙ্গে যুক্ত অবজেক্ট।
- **করা (doing)** — যে কাজগুলো অবজেক্টটি করে (তার অপারেশন)।

একটি **প্যাটার্ন** (Singleton, Strategy, Observer …) হলো কাঠামোসহ একটি নামকরা সমাধান। আর একটি গ্র্যাস্প নির্দেশিকা হলো মাত্র একটি বাক্য, যা বলে দায়িত্ব কোথায় রাখতে হবে — এর সঙ্গে কোনো ক্লাস ডায়াগ্রাম বা কোড টেমপ্লেট থাকে না।

*(চিত্র: তিনটি রঙিন প্যানেল — "তথ্য কোথায়?" ধরনে Information Expert ও Creator; "কতটা জট?" ধরনে Low Coupling, High Cohesion, Don't Talk to Strangers ও Indirection; "কী বদলাতে পারে?" ধরনে Polymorphism, Protected Variations ও Known / Unknown Deps।)*

| # | নির্দেশিকা | নীতি, এক লাইনে |
|---|---|---|
| ১ | **Information Expert** | তথ্য যার কাছে **আছে**, তাকেই দায়িত্ব |
| ২ | **Creator** | যে ক্লাস অন্যকে ধারণ বা একত্রিত করে, সে-ই তৈরি করে |
| ৩ | **Low Coupling** | যে ক্লাস অন্যদের ওপর **সবচেয়ে কম নির্ভরশীল**, তাকে |
| ৪ | **High Cohesion** | এক ক্লাসে **সর্বোচ্চ সম্পর্কযুক্ত** দায়িত্ব |
| ৫ | **Polymorphism** | সাবক্লাসে সুপারক্লাসের আচরণ নতুন করে লিখবেন না |
| ৬ | **Pure Arbiters** | যে অবজেক্ট দুই বা ততোধিকের মধ্যে **সালিশ করে** |
| ৭ | **Don't Talk to Strangers** | শুধু **নিজের সরাসরি সহযোগীর** কাছে জিজ্ঞাসা করুন |
| ৮ | **Controller** | সিস্টেম ইভেন্ট পাওয়া **প্রথম non-UI** অবজেক্ট |
| ৯ | **Intermediary** (Pure Fabrication) | নির্ভরতা ভাঙতে বানানো **কাল্পনিক**, ডোমেন-নিরপেক্ষ ক্লাস |

**গ্র্যাস্পের সঙ্গে আরও যে তিনটি আসে:** **Indirection** — এমন একটি মধ্যবর্তী অবজেক্ট যা পরস্পর অচেনা অবজেক্টগুলোকে যুক্ত করে। **Protected Variations** — **অনুমিত পরিবর্তনের** প্রতিটি বিন্দুকে একটি ইন্টারফেসের ভেতরে রাখুন। **Known / Unknown Dependencies** — **জানা** নির্ভরতা সরাসরি উল্লেখ করুন; বদলানো **যায় এমন** নির্ভরতার সামনে ইন্টারফেস।

- ⚠️ **ফাঁদ:** গ্র্যাস্প হলো **দায়িত্ব বরাদ্দের নির্দেশিকা**, প্রস্তাবক **Carell ও Fowler (১৯৯১)** — এটি প্যাটার্নের তালিকা নয়, GoF ডিজাইন প্যাটার্নও নয়। **Pure Arbiters** কখনো "Pure Arbiters / Information Expert" হিসেবে ছাপা হয়: দুটি করে গণনা করবেন না।

## ৩. ইনফরমেশন এক্সপার্ট ও ক্রিয়েটর — উদাহরণসহ

**Information Expert.** সেই অবজেক্টকে দায়িত্ব দিন যার কাছে কাজটি করার জন্য প্রয়োজনীয় **তথ্য** আছে। **উদাহরণ:** *Invoice*-ই `getTotal()` হিসাব করবে, কারণ LineItem-এর তালিকা কেবল Invoice-এর কাছেই আছে।

```java
class LineItem {
    Product product;
    int quantity;
    double getSubTotal() {
        return product.price * quantity;
    }
}
class Invoice {
    List<LineItem> items;
    double getTotal() {
        return items.stream()
            .mapToDouble(LineItem::getSubTotal)
            .sum();
    }
}
```

**এই উত্তরটি কেন সঠিক**

- লাইন আইটেমগুলো কেবল **Invoice**-এর কাছে, তাই যোগফল করতে পারে কেবল সেই।
- কোনো প্যারামিটার পাঠাতে হয় না, কোনো *LineItem*-এর ব্যাক-পয়েন্টার লাগে না।
- জ্ঞান থাকে **যে ক্লাসের কাছে ডেটা, তার ভেতরেই**: কাপলিং কমে, কোহেশন বাড়ে।

- ⚠️ **ফাঁদ:** Information Expert মানে "সবচেয়ে বেশি মেথড থাকা ক্লাস" **নয়**। এটি সেই ক্লাস যার কাছে **প্রয়োজনীয় ডেটা** আছে। ডেটা অন্যত্র থাকলে দায়িত্ব সেখানেই যাবে।

**Creator.** ক্লাস **B**-কে ক্লাস **A**-এর ইনস্ট্যান্স তৈরির দায়িত্ব দিন, যদি **যেকোনো একটি** শর্ত সত্য হয়: B **ধারণ** করে A · B **একত্রিত** করে A · B-তে A **রেকর্ড** আছে · B **ঘনিষ্ঠভাবে ব্যবহার** করে A · B-এর কাছে A-কে **initialise** করার ডেটা আছে।

```java
class Sale {
    List<SalesLineItem> lines;
    SalesLineItem addLine(Product p, int q) {
        SalesLineItem l = new SalesLineItem(p, q);
        lines.add(l);
        return l;
    }
}
```

*(চিত্র: উপরে নীল "Sale" বক্স, নিচে তিনটি সবুজ "SalesLine" বক্স; Sale থেকে তিনটি তীর নামিয়ে "creates (1 .. *)" লেখা।)*

- 💡 **কৌশল:** **Creator = "C for Container"**। B যদি A ধারণ না করেও A-এর প্রতিটি ফিল্ডের initial মান বলতে পারে, তবে সেও স্বাভাবিক Creator — কারণ ওখানে তৈরি করলে কলকারকে যে আর্গুমেন্ট দিতে হয় **কমে যায়**।
- ⚠️ **ফাঁদ:** Creator মানে "যে ক্লাস ব্যবহার করে" তা নয়। POS সিস্টেমে **Sale** — Register, ProductCatalog বা Payment নয় — **SalesLineItem** তৈরি করে, কারণ Sale সেগুলোকে *ধারণ* করে।

## ৪. লো কাপলিং ও হাই কোহেশন — উদাহরণসহ

**Low Coupling.** এমনভাবে দায়িত্ব বরাদ্দ করুন যাতে **অপ্রয়োজনীয় নির্ভরতা সর্বনিম্ন** থাকে। পরীক্ষায় বলার নিয়ম: **দায়িত্ব সেই ক্লাসকে দিন যা অন্য ক্লাসের ওপর সবচেয়ে কম নির্ভরশীল**। নির্ভরতা মাপা হয় কতটা পরিমাণ অন্য অবজেক্টের **স্টেট** জানতে হয় তা দিয়ে।

**খারাপ — হাই কাপলিং**

```java
class Customer {
    String name;
    void saveToDatabase() {
        // opens a JDBC connection,
        // builds SQL, commits a tx
    }
}
```

**ক্ষতি:** *Customer* এখন DB, SQL, ড্রাইভার ও নেটওয়ার্ক জানে।

**ভালো — লো কাপলিং**

```java
class CustomerRepository {
    void save(Customer c) {
        // all DB logic lives here
    }
}
class Customer {
    String name;  // no DB knowledge
}
```

**লাভ:** *Customer* পুনর্ব্যবহারযোগ্য, repository বদলানো যায়, দুটি আলাদা ইউনিট টেস্ট করা যায়।

**হাই কোহেশন — গড ক্লাস ও তার ভাঙা**

```java
// LOW COHESION — the "god class"
class CustomerManager {
    void browseShop()  { }
    void chargeCard()  { }
    void shipOrder()   { }
    void sendEmail()   { }
    void updateDatabase(){ }
}

// HIGH COHESION — split it
class Customer { /* customer data */ }
class Cart     { /* cart operations */ }
class Payment  { /* payment logic  */ }
class Shipping { /* delivery       */ }
class Notifier { /* e-mail         */ }
```

পাঁচটি অসম্পর্কিত কাজে **পরিবর্তনের কোনো একটি কারণ নেই**, আর প্রতিটি পরিবর্তন পাঁচটিকেই ঝুঁকিতে ফেলে; ভাঙার পর প্রতিটির **পরিবর্তনের একটিমাত্র স্পষ্ট কারণ** আছে — SRP-রই আরেক রূপ।

*(চিত্র: বামে চারটি লাল বৃত্ত পুরো জালের মতো লাল রেখায় যুক্ত, "হাই কাপলিং — প্রতিটি নোড সবাইকে জানে"; ডানে চারটি লাল বৃত্ত কেন্দ্রীয় সবুজ হাবের মাধ্যমে যুক্ত, "লো কাপলিং — একটি কেন্দ্র, আলাদা স্পোক"।)*

- 💡 **কৌশল:** **কাপলিং হলো এই বেলুনে কতগুলো সুতো বাঁধা** — চারটি সুতো আর ওড়ে না। **কোহেশন হলো তার নিজের অংশগুলো কতটা জোরে জোড়া লেগে আছে**: পাঁচটি অসম্পর্কিত কাজ = নুড়ির ঢেলি, পাথর নয়।
- ⚠️ **ফাঁদ:** দুটি আলাদা মাপকাঠি: কাপলিং হলো ক্লাসগুলোর *মধ্যে*, কোহেশন এক ক্লাসের *ভেতরে*। একটি ক্লাস অত্যন্ত কোহেজিভ হয়েও তিনটি অপ্রয়োজনীয় ক্লাসের সঙ্গে কাপলড হতে পারে।
- 📌 **IT link:** ব্যাংক কোর তার লেজার নিয়মগুলো ইন্টারফেসের পেছনে রাখে: ব্যবসায়িক ক্লাসগুলো না ছুঁয়েই SQL বদলানো যায়।

## ৫. পলিমরফিজম, কন্ট্রোলার, ইন্টারমিডিয়ারি ও বাকিগুলো

**Polymorphism (পলিমরফিজম).** সাবক্লাসকে এমন আচরণ দেবেন না যা সুপারক্লাসে **আগে থেকেই** আছে। দায়িত্বটি সুপারক্লাস বা ইন্টারফেসে রাখুন, রান টাইমে সঠিকটি বেছে নিতে **পলিমরফিজম** দিয়ে হবে। *CashPayment · CardPayment · MobileBanking* সবাই `process()` ভাগ করে।

**Pure Arbiters (পিওর আর্বাইটার্স).** এমন অবজেক্টকে দায়িত্ব দিন যা **দুই বা ততোধিকের মধ্যে সালিস করে** — যে নিয়ম দুপাশের দুজনেরই দরকার কিন্তু কারও নিজের নয়। যে *TaxPolicy* *Invoice* ও *Refund* দুজনই জিজ্ঞাসা করে।

**Don't Talk to Strangers.** কোনো মেথড অন্যের ওপর অতিরিক্ত নির্ভরতা রাখলে নিয়ম ভাঙে। শুধু **নিজের সরাসরি সহযোগীর** কাছে জিজ্ঞাসা করুন। কখনো *Order*-এর ভেতর দিয়ে `Order.getCustomer().getAddress()` ধরবেন না।

**Controller (কন্ট্রোলার).** *enterItem*-এর মতো সিস্টেম ইভেন্ট যে অবজেক্ট **UI স্তরের পরে প্রথম** গ্রহণ করে ও সমন্বয় করে। দুই প্রকার: **ফ্যাসেড কন্ট্রোলার** (গোটা সিস্টেমের প্রতিনিধি) ও **ইউজ-কেস / সেশন কন্ট্রোলার** (একটি পরিস্থিতি)। **UI ক্লাসে কখনো নয়।**

**Intermediary (Pure Fabrication).** এমন ক্লাস যা **কোনো ডোমেন ধারণাই প্রতিনিধিত্ব করে না**, শুধু অস্বাভাবিক নির্ভরতা ভাঙতে বানানো; সাধারণত **নিম্ন-স্তরের সাধারণ প্যাকেজে** রাখা হয়। ইনভয়েস আর ডেটাবেসের মাঝে একটি *ReportService*।

**Protected Variations.** **অনুমিত পরিবর্তনের** বিন্দুগুলো চিহ্নিত করে প্রতিটির সামনে ইন্টারফেস বা অ্যাবস্ট্রাক্ট ক্লাস রাখুন, যাতে অস্থির অংশ বাকিটা না ছুঁয়েই বদলায়। Open/Closed নীতি; সাধারণত Strategy প্যাটার্ন।

| গ্র্যাস্প নির্দেশিকা | আসলে এই নীতি |
|---|---|
| **High Cohesion** | Single Responsibility নীতি |
| **Low Coupling** | Dependency Inversion · Open/Closed |
| **Protected Variations** | Open/Closed নীতি · Strategy |
| **Polymorphism** | Liskov Substitution |
| **Indirection / Intermediary** | Dependency Inversion নীতি |

*(চিত্র: উপরের সারি "UI → Controller → Domain", ডোমেন থেকে UI-তে ফিরে যাওয়া ডটেড লাল তীর ও তার ওপর লাল ক্রস, "UI নিজে ইভেন্ট সামলাবে না"; নিচের সারি সবুজ "A → mediator → B", "অচেনা বন্ধুর সঙ্গে কথা নয়: A কেবল সহযোগীকে জিজ্ঞাসা করে"।)*

- ⚠️ **ফাঁদ:** **Controller** নির্দেশিকা মানে "ব্যবহারকারী যে ক্লাসে ক্লিক করেন" **নয়** — ইভেন্ট গ্রহণকারী UI ক্লাস তো গ্র্যাস্প নিষিদ্ধ করে। আর **Pure Fabrication** ডোমেন মডেল ক্লাস থেকে আলাদা: এর **কোনো ডোমেন অর্থ নেই**।

## ৬. ডিজাইন ক্লাস ডায়াগ্রাম (DCD)

**সংজ্ঞা।** **ডিজাইন ক্লাস ডায়াগ্রাম (DCD)** হলো **ডিজাইন লেভেলে** আঁকা UML ক্লাস ডায়াগ্রাম: বিশ্লেষণ/ডোমেন মডেলের ক্লাস ডায়াগ্রামের সঙ্গে বাস্তবায়নকারীর দরকারি সবকিছু যোগ করা — স্বাক্ষরসহ **অপারেশন**, **টাইপ**, **ভিজিবিলিটি** চিহ্ন এবং **নেভিগেবিলিটি** তীর।

| ডোমেন / বিশ্লেষণ মডেল | ডিজাইন ক্লাস ডায়াগ্রাম |
|---|---|
| ডোমেনের **ধারণাগত** দৃষ্টিভঙ্গি | বাস্তবায়নের **সফটওয়্যার** দৃষ্টিভঙ্গি |
| ক্লাস, অ্যাট্রিবিউট, অ্যাসোসিয়েশন, মাল্টিপ্লিসিটি | সেগুলো **মেথড ও রিটার্ন টাইপ**সহ |
| **বহুবচন** ডোমেন নাম (Sales) | **একবচন** নাম (Sale) |
| সফটওয়্যার-নির্দিষ্ট টাইপ নেই | সুনির্দিষ্ট টাইপ: **String, double, List** |
| ভিজিবিলিটি চিহ্ন নেই | **+ public · − private · # protected** |
| অ্যাসোসিয়েশন দিকহীন | **নেভিগেবিলিটি** — রেফারেন্স কে রাখে |
| ইন্টারফেস বা প্যাকেজ নেই | **<<interface>>**, **<<abstract>>**, প্যাকেজ |

*(চিত্র: পাশাপাশি দুটি ক্লাস বক্স। বাঁয়ে শিরোনাম "DOMAIN", ভেতরে *Customer*, *− name*, *− email* এবং লাল "no methods"। ডানে লাল শিরোনাম "DESIGN", একই দুটি অ্যাট্রিবিউট কিন্তু সবুজ "+ register()"। মাঝে "+" চিহ্নিত তীর। নিচে বেগুনি প্যানেলে "ডিজাইন লেভেল যা যোগ করে": স্বাক্ষরসহ মেথড, অ্যাট্রিবিউট ও রিটার্ন টাইপ, ভিজিবিলিটি চিহ্ন, নেভিগেবিলিটি তীর — "ডোমেন মডেলে এর কোনোটিই নেই"।)*

**ডিজাইন থেকে কোডে ম্যাপিং: এক-এক-এক নিয়ম**

| ডিসিডির উপাদান | কোডে পরিণত হয় |
|---|---|
| একটি ক্লাস বক্স | একটি **ক্লাস** — বা স্টেরিওটাইপ <<interface>> হলে ইন্টারফেস |
| অ্যাট্রিবিউট `− price : double` | ওই টাইপের একটি **ফিল্ড** / প্রপার্টি |
| অপারেশন `+ total() : double` | ওই রিটার্ন টাইপের একটি **মেথড** |
| নেভিগেবিলিটিসহ অ্যাসোসিয়েশন **1 → \*** | একটি রেফারেন্স ফিল্ড ও একটি **কালেকশন** (অ্যারে / *List* / *Set*) |
| অ্যাগ্রিগেশন ◇ বা কম্পোজিশন ◆ | পূর্ণাংশের দ্বারা ধারণ করা whole–part রেফারেন্স |
| জেনারালাইজেশন △ / রিয়ালাইজেশন ▷ | **ইনহেরিট্যান্স** / ডেলিগেশনে কম্পোজিশন |

**ডিসিডি তৈরির চার ধাপ।** ① প্রতিটি কনসেপ্ট ক্লাসের নাম **একবচনে** করুন (Sales → *Sale*)। ② অ্যাট্রিবিউটে **সফটওয়্যার টাইপ** দিন (age: Integer → *int*)। ③ প্রতিটি ক্লাসের দায়িত্বগুলো রিটার্ন টাইপসহ অপারেশন হিসেবে লিখুন। ④ যে অ্যাসোসিয়েশনে রেফারেন্স রাখতে হবে, সেখানে **নেভিগেবিলিটি তীর** আঁকুন।

- ⚠️ **ফাঁদ:** ডোমেন মডেলে যা নেই কিন্তু ডিসিডিতে আছে, তা হলো একটাই জিনিস: **মেথড (অপারেশন) ও নেভিগেবিলিটি**। কনসেপ্ট ক্লাস, অ্যাসোসিয়েশন ও মাল্টিপ্লিসিটি **দুটোতেই** থাকে।
- 💡 **কৌশল:** ডোমেন মডেল = **কী আছে**। ডিসিডি = **কী আছে, আর সেটি কী করে**। রিটার্ন টাইপসহ মেথড স্বাক্ষর দেখলেই বুঝে যাবেন, এটি ডিসিডি।

## ৭. একটি ডিসিডি ধাপে ধাপে, আর যে কোড হয়ে দাঁড়ায়

*(চিত্র: ছয়টি বাক্সের একটি ডিজাইন ক্লাস ডায়াগ্রাম, প্রতিটি তিনটি ভাগে বিভক্ত — নাম / অ্যাট্রিবিউট / অপারেশন। উপরের সারি **Customer** (`− name : String`, `− email : String`, `+ register() : void`, `+ checkout() : Order`), **Cart** (`− items : List<Line>`, `− customer : Customer`, `+ add(p : Product) : void`, `+ createOrder() : Order`), **Product** (`− sku : String`, `− price : double`, `+ inStock() : bool`)। নিচের সারি **Order** (`− id : int`, `− lines : List<Line>`, `+ confirm() : void`, `+ total() : double`), **Line** (`− qty : int`, `− product : Product`, `+ subTotal() : double`), **Payment** (`− method : String`, `− amount : double`, `+ process() : boolean`)। সবুজ তীর: Customer 1 — \* Cart, Cart 1 — \* Order, এবং Order তৈরি করে Line; নিচে "navigable: Cart ▸ Order ▸ Line ▸ Product"।)*

ডিজাইনের পঠন: **Customer 1 — \* Cart — \* Order — \* Line — \* Product**, সঙ্গে একটি *Payment* সহযোগী। প্রতিটি বাক্সে এখন রিটার্ন টাইপসহ অপারেশন।

```java
class Customer {
    String name;
    String email;
    Cart cart = new Cart();

    void checkout() {
        Order o = cart.createOrder();
        o.confirm();
    }
}
class Line {
    Product product;   // navigable ▸
    int qty;
    double subTotal() {
        return product.price * qty;
    }
}
class Cart {
    List<Line> items = new ArrayList<>();

    void add(Product p, int q) {
        items.add(new Line(p, q));
    }
    double calculateTotal() {
        return items.stream()
            .mapToDouble(Line::subTotal)
            .sum();
    }
    Order createOrder() {
        return new Order(items);
    }
}
```

**ছবি থেকে ম্যাপিং পড়ুন।** `Cart.items : List<Line>` → ফিল্ড `List<Line> items`; `Line.product : Product` → ফিল্ড `Product product`; `Line.subTotal() : double` → মেথড। **ডিসিডির কোথাও কিছু নতুন করে বানাতে হয় না** — ক্লাসের নাম, অ্যাট্রিবিউটের নাম, টাইপ ও মেথডের নামই প্রোগ্রামারের প্রয়োজনীয় শনাক্তকারী।

- ⚠️ **ফাঁদ:** ডিসিডি CRC কার্ড থেকে আলাদা জিনিস: CRC দিয়ে দায়িত্ব *আবিষ্কার* করা হয়, ডিসিডিতে তা *লিখে রাখা* হয়। "ডিজাইন সরাসরি কোডে যায়" মানে **এক-এক-এক ম্যাপিং** — প্রতিটি ডায়াগ্রাম উপাদানের আলাদা ফাইল নয়।

## ৮. স্ট্রাকচারাল বনাম ফাংশনাল টেস্টিং, ইপি ও বিভিএ

| বিষয় | হোয়াইট বক্স (স্ট্রাকচারাল, গ্লাস-বক্স) | ব্ল্যাক বক্স (ফাংশনাল, বিহেভিয়ারাল) |
|---|---|---|
| টেস্ট কেস কীস থেকে | কোডের **অভ্যন্তরীণ কাঠামো** থেকে | **স্পেসিফিকেশন** থেকে, কোড থেকে নয় |
| টেস্টারের জ্ঞান | প্রোগ্রামের ভেতরের বিষয় জানেন | কীভাবে লেখা হয়েছে তা **জানেন না** |
| আরেক নাম | স্ট্রাকচারাল, ক্লিয়ার-বক্স, গ্লাস-বক্স | ফাংশনাল, স্পেসিফিকেশন-ভিত্তিক |
| মূল প্রশ্ন | "প্রতিটি স্টেটমেন্ট / ব্রাঞ্চ **চলেছে** কি?" | "প্রতিটি বৈধ ইনপুটে **আউটপুট** ঠিক আছে কি?" |
| পদ্ধতি | বেসিস পাথ টেস্টিং, কভারেজ বিশ্লেষণ | সমতুল্য বিভাজন, বিভিএ, কজ-ইফেক্ট গ্রাফিং |
| সবচেয়ে ভালো ধরে | ডেড কোড, চালানো হয়নি এমন ব্রাঞ্চ | বাদ পড়া প্রয়োজন, ভুল আউটপুট |

**টেস্ট বেসিস।** যে নথি থেকে টেস্ট বের করা হয়: **হোয়াইট বক্স** টেস্টের বেসিস **ডিজাইন মডেল / কোড**, **ব্ল্যাক বক্স** টেস্টের বেসিস **প্রয়োজনীয়তার স্পেসিফিকেশন**। টেস্টিং ত্রুটের **উপস্থিতি** দেখাতে পারে, অনুপস্থিতি কখনো নয়।

- ⚠️ **ফাঁদ:** টেস্টিং প্রোগ্রাম **সঠিক প্রমাণ করতে পারে না**; শুধু আস্থা বাড়ায়। যে টেস্ট **কখনো ব্যর্থ হয়নি**, তাকে ভালো টেস্ট বলা এখনো প্রমাণিত নয়। ইউনিট → ইন্টিগ্রেশন → ভ্যালিডেশন → সিস্টেম লেভেল, ডিবাগিং, রক্ষণাবেক্ষণ ও টেস্ট মেট্রিক্স *টেস্টিং কৌশল, রক্ষণাবেক্ষণ, মান ও মেট্রিক্স* নোটে আছে।

**সমতুল্য বিভাজন ও সীমানা মান বিশ্লেষণ**

| সমতুল্য শ্রেণি (বয়স) | ধরন | ইপি বাছাই |
|---|---|---|
| বয়স < ১৮ | অবৈধ | ১০ |
| ১৮ ≤ বয়স ≤ ৬০ | **বৈধ** | ৩৫ |
| বয়স > ৬০ | অবৈধ | ৭০ |

**সমতুল্য বিভাজন (EP)** ইনপুট ডোমেনকে এমন শ্রেণিতে ভাগ করে যেগুলো একইভাবে ব্যবস্থিত হয়, তারপর প্রতিটি থেকে **একটি প্রতিনিধি** পরীক্ষা করে — কম টেস্ট, বড় কভারেজ। বৈধ ও অবৈধ শ্রেণি **আলাদা করে** গোনা হয়।

| সীমানা | বিভিএ বাছাই |
|---|---|
| নিম্ন, ১৮ | ১৭ · **১৮** · ১৯ |
| উচ্চ, ৬০ | ৫৯ · **৬০** · ৬১ |

**বিভিএ (BVA)** প্রতিটি সীমানার **ঠিক নিচে, ঠিক ওপরে ও ঠিক মাঝে** পরীক্ষা করে। অফ-বাই-ওয়ান ত্রুটি থাকে **ধারের কাছে** — ঠিক যেখানে ইপি মাত্র একটি নমুনা নেয়।

✍ **কখন কোনটি ব্যবহার করবেন।** ছোট ইনপুট ডোমেনে শুধু ইপিই যথেষ্ট। ডোমেন বড় হলে (বছর, পরিমাণ, তারিখ) একাই ইপি ঝুঁকি বাড়ায়, তখন **বিভিএ** যোগ করুন: ইপি ধরে রাখে *প্রতিনিধি*, বিভিএ ধরে রাখে *প্রান্তিক মান* — শ্রেণির ভেতরের মান ভুল হলে ইপি ধরতে পারে না, কারণ সে মাঝের মানের কাছাকাছি যায়।

*(চিত্র: সংখ্যারেখা তিনটি ব্যান্ডে বিভক্ত — ১৮-এর নিচে লাল "অবৈধ", ১৮–৬০ সবুজ "বৈধ", ৬০-এর ওপরে লাল "অবৈধ"; রেখার ওপর হলুদ বিন্দুতে ইপি ১০, ৩৫, ৭০; দুই ধারের নিচে বিভিএ-র ত্রিগুণ ১৭ ১৮ ১৯ ও ৫৯ ৬০ ৬১; লাল চিহ্ন ১৮ ও ৬০।)*

## ৯. কভারেজ, সাইক্লোম্যাটিক জটিলতা ও বেসিস-পাথ টেস্টিং

| কভারেজ মানদণ্ড | কীভাবে মাপা হয় | শক্তি |
|---|---|---|
| **স্টেটমেন্ট** | চলা ÷ মোট এক্সিকিউটেবল স্টেটমেন্ট × ১০০ % | সবচেয়ে দুর্বল — ব্রাঞ্প ফাঁকা থাকে |
| **ব্রাঞ্চ / ডিসিশন** | নেওয়া আউটকাম ÷ মোট আউটকাম × ১০০ % | **সাধারণ ন্যূনতম লক্ষ্য** |
| **কন্ডিশন** | মূল্যায়িত শর্ত ÷ মোট শর্ত × ১০০ % | `a && b`-এর প্রতিটি অংশ দুইভাবে |
| **মাল্টিপল কন্ডিশন** | n শর্তের সব সত্য-মিথ্যা সংমিশ্রণ — **2ⁿ** | খুব শক্তিশালী, খুব ব্যয়বহুল |
| **পাথ** | চলা পাথ ÷ মোট পাথ × ১০০ % | সবচেয়ে শক্তিশালী, প্রচেষ্টা সূচকীয় |

**সাইক্লোম্যাটিক জটিলতা (McCabe, ১৯৭৬).** **M = E − N + 2P** — **E** = কন্ট্রোল-ফ্লো গ্রাফের শিখা, **N** = নোড, **P** = সংযুক্ত অংশ। সাধারণ মডিউলে **P = 1**, তাই পরিচিত রূপ **M = E − N + 2**। **M** আসলে স্বাধীন পাথের সংখ্যাই — ফ্লো গ্রাফের ক্ষেত্রসমূহ — এবং সরল শর্তীয় কোডে **M = (স্বাধীন শর্ত) + 1**। কোনো শর্তই না থাকলে **M = 1**।

```java
double total(int qty, double price, boolean member) {
  if (qty > 0 && price > 0) {
    double t = qty * price;
    if (member && t > 1000)
      t = t * 0.90;
    return t;
  }
  return 0.0;
}
```

1. ফ্লো গ্রাফ আঁকুন
2. **M** গণনা করুন
3. **M**টি স্বাধীন পাথ খুঁজুন
4. প্রতি পাথে একটি টেস্ট কেস

*(চিত্র: উপরের মেথডের কন্ট্রোল-ফ্লো গ্রাফ — এন্ট্রি বৃত্ত, চারটি ডিসিশন বৃত্ত `qty>0?`, `price>0?`, `member?`, `t>1000?`, দুটি ফলস ব্রাঞ্চ থেকে বেগুনি "return 0" বক্স, সবুজ "return t" বক্স, এবং একটি এক্সিট বৃত্ত; প্রতিটি শিখায় T বা F। নিচে "E = 12 edges · N = 9 nodes" ও "M = 12 − 9 + 2 = 5" ও "পাঁচটি স্বাধীন পাথ"।)*

✍ **উদাহরণ।** চারটি মূল শর্তে **M = 4 + 1 = 5**, যা মেলে **E − N + 2 = 12 − 9 + 2 = 5**-এর সঙ্গে। বেসিস সেট: **P1** `qty=0 → 0.0` · **P2** `price=0 → 0.0` · **P3** `2×100, সদস্য নয় → 200` · **P4** `2×100, সদস্য, t≤1000 → 200` · **P5** `20×100, সদস্য → 2000×0.9 = 1800`।

**স্বাধীন পাথ।** এমন পাথ যা অন্তত একটি **নতুন নোড** বা **নতুন শর্ত** আনে, যা আগের কোনো পাথে ছিল না। সংখ্যাটি সবসময় **M**-এর সমান।

**ভি-মডেলে ডিজাইন।** ব্যবসায়িক প্রয়োজন ↔ **গ্রহণযোগ্যতা** · সিস্টেম প্রয়োজন ↔ **সিস্টেম টেস্ট** · **আর্কিটেকচার ↔ ইন্টিগ্রেশন** · **বিস্তারিত ডিজাইন ↔ ইউনিট টেস্ট**।

**বিশেষ পরিবেশের টেস্ট লক্ষ্য।** রিয়েল-টাইম → টাইমিং, স্ট্রেস · ডিস্ট্রিবিউটেড → লেটেন্সি, আংশিক ব্যর্থতা · ওয়েব → SQL ইনজেকশন, XSS · মোবাইল → ডিভাইস, স্ক্রিন · এমবেডেড → CPU, মেমরি। পূর্ণ পাথ কভারেজ প্রচেষ্টা সূচকীয় বেড়ে যায়, তাই "১০০ % পাথ কভারেজ" কখনোই বাস্তবসম্মত লক্ষ্য নয়।

✍ **লিখিত প্রশ্ন ২ (৮ নম্বর)।** একটি মেথডে দুটি নেস্টেড `if` আছে এবং দুটি `&&` শর্ত আছে। এর সাইক্লোম্যাটিক সংখ্যা বের করো এবং কতগুলো বেসিস পাথ টেস্ট কেস লাগবে তা বলো।
