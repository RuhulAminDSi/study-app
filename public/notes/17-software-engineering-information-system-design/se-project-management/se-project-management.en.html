SE · Project ManagementConstraints

1Software Project Management & the Four Constraints

MCQ + Written
Definition Software Project Management (SPM) = the application of management knowledge, skills, tools and techniques to software projects so that they are delivered on time, within budget, and to the required quality. A project is a temporary endeavour producing a unique result — unlike "operations", which repeat.
ConstraintQuestion it answersDriven by
Scopewhat work is in, what is outrequirements, WBS, SRS
Timehow long, by which milestonesestimates, CPM / PERT, Gantt
Costhow much money and effortbudget, COCOMO, rates
Qualityhow good — the result of the other threeSQA, reviews, testing, CM

Most texts state the triple constraint (scope–time–cost, a triangle with the project inside) and then note that quality sits in the middle and is the first casualty. Fix three and the fourth is decided for you.

Exam trap The trade-off is a diagnosis, not an excuse. Shrink scope before you shrink quality; buy time before you buy quality.

2Who Does What — and the Baseline

  • Project Manager — plans, schedules, budgets, reports; owns delivery
  • Sponsor / Owner — funds it, holds the business case
  • Product Owner — owns the backlog and the priority of change
  • PMO — Project Management Office: standards, templates, audits
  • CCB — Change Control Board: the only body that may move the baseline
Scope & change control Scope creep = uncontrolled growth of the work with no change to time or cost. The cure is configuration management (CM): versioning, baselines, change requests, configuration audits, status accounting.
Memory trick The baseline is the approved scope–schedule–cost. Nothing is a "change" until it is approved against a baseline. The PM changes the plan; the CCB approves it; the PO re-prioritises the backlog.

3The Project Activities

written favourite
Activity chain Every project manager runs the same loop: planning → risk analysis → estimation → scheduling → monitoring & control, with configuration / change management wrapping all of it. These are not SDLC phases (that is the SE Concepts lesson); they are the manager's activities across the whole life of the product.
#ActivityWhat it produces
1Planningobjectives, scope statement, WBS, staffing, communication plan
2Risk analysisrisk register: identify → assess → prioritise → respond
3Estimationsize (KLOC / FP), effort, cost — LOC, FP, COCOMO, analogy
4Schedulingnetwork, critical path, Gantt chart, milestones, baseline
5Monitoring & controlprogress vs plan, variance, corrective action
6Configuration / change mgmtbaselines, version control, change requests, CCB
TechniqueHow it works
Analogy (top-down)extrapolate from a finished project; least accurate
Expert judgementexperts estimate from experience — fast, optimistic
Delphisame, but anonymous, seeing only the spread
TechniqueHow it works
Bottom-up (WBS)estimate every work package, add overhead
FP + COCOMOlanguage-free size → effort and schedule
Planning Poker · price-to-winstory points by card mode; tender price
Memory trick: WBS Work Breakdown Structure: the hierarchical decomposition of the project into work packages small enough to estimate, assign and measure (≈ 80 person-hours). Every leaf must be 100 % assigned — no "miscellaneous" leaf.
Exam trap Effort ≠ duration. Effort is person-time (person-months), duration is calendar time. Ten people for one month = 10 person-months of effort but 1 month of schedule. Adding people to a late project usually makes it later (Brooks's law).

4Process & Project Metrics

high-yield
Definition A metric is a quantitative measure of size, process effectiveness, product quality or project performance. A baseline is the agreed value it is compared against.
FamilyQuestion it answersTypical measures
Product (size)how big is the software?LOC, function points, cyclomatic complexity, Halstead
Processhow well are we developing?effort, productivity, defect density, estimation accuracy
Projecthow is the project doing?schedule variance, cost variance, earned value (SPI, CPI)
Qualityhow good is the delivered product?defects per KLOC / per FP, MTBF, MTTR, availability
defect & reliability metrics in depth → Testing & Quality lesson

Size: LOC vs function points, and the derived measures

LOCFunction points
Countslines of source codeuser-visible functions
Languagedependentindependent
Availableonly after codingfrom the spec
Is it size?no — a shortcutyes, FPs are size
Weaknessrewards verbose stylejudgement-heavy
Derived measures — formulas
Productivity = LOC ÷ person-months  ·  Defect density = defects ÷ KLOC  ·  Defect removal efficiency = found before delivery ÷ total
Estimation error = (actual − estimated) ÷ estimated × 100 %  ·  MTBF = 1 ÷ failure rate  ·  Availability A = MTBF ÷ (MTBF + MTTR)
Worked example ✍ 2000 LOC with 10 defects ⇒ KLOC = 2, defect density = 10 ÷ 2 = 5 per KLOC. 12,000 LOC in 15 person-months ⇒ productivity = 800 LOC/person-month. 20 defects over 400 FP ⇒ 0.05 defects/FP, language-free.
Why LOC productivity is contested ★ (i) the same function can take 3× more lines in COBOL than in Java; (ii) verbose code raises LOC and so raises the "productivity" number; (iii) it is unavailable exactly when the estimate is needed. Use FP, feature or use-case points.
Exam trap LOC is a size measure too, but it depends on the language and is known only after coding; FP is language-independent and can be counted from the requirements. And "defects per KLOC" over test code is meaningless — test modules sit inside KLOC but their defects are not product defects.

SE · Project ManagementFunction points

5Function Point Analysis

high-yield
Definition Function Point Analysis (FPA) — A. J. Albrecht, late 1970s — measures a system by the functionality a user can see, not by the code. It counts five element types at the system boundary, weights them, sums to a UFP, adjusts for complexity, and the result is the function point count.
TypeWeightWhat it is
EI external input× 3unique data into the system from outside
EO external output× 4unique data out that is derived (report, calculated screen)
EQ external inquiry× 3a read-only retrieval, no derivation — a search or lookup
ILF internal logical file× 7a user-identifiable group of data inside the boundary
EIF external interface file× 5user-identifiable data outside, maintained elsewhere
Two equations
UFP = Σ (count of each type × its weight) · FP = UFP × VAF
VAF = 0.65 + 0.01 × ΣFi (14 factors, each 0–5) ⇒ 0.65–1.35
Worked example ✍ Payroll system: EI = 20, EO = 8, EQ = 12, ILF = 6, EIF = 3.
  1. UFP = 20×3 + 8×4 + 12×3 + 6×7 + 3×5 = 60 + 32 + 36 + 42 + 15 = 185
  2. ΣFi = 42 ⇒ VAF = 0.65 + 0.42 = 1.07
  3. FP = 185 × 1.07 ≈ 198 FP; at ≈ 40 LOC/FP ≈ 7.9 KLOC
Memory trick Weight order, high to low: ILF 7 > EIF 5 > EO 4 > EI 3 = EQ 3 — "the Internal Logical File is the heavyweight, input and inquiry the lightest". A field that arrives without changing behaviour is not an EI; a report that merely repeats stored data is an EQ, not an EO.
Exam trap There are five element types, not six — "external inquiries" is the third, not an extra one. VAF multiplies and lies in 0.65–1.35. FP counts the user's view, so it must be re-counted whenever the boundary moves.

SE · Project ManagementCOCOMO

6Estimation & COCOMO

written favourite
COCOMO (Boehm, 1981) Constructive Cost Model: a parametric model that turns a size measure into effort and then into schedule. Effort is always person-months; schedule is always months.
The two equations

Effort (E) = a × (KLOC)b × ∏EM

Schedule (TDEV) = c × (E)d

∏EM = product of the effort multipliers

b > 1 ⇒ effort grows faster than size

Project modeBasicFullDet.bcd
Organic2.43.23.21.052.50.38
Semi-detached3.03.03.01.122.50.35
Embedded3.62.82.81.202.50.32

Organic — small, familiar, few rigid rules · Semi-detached — medium, mixed team, some rules · Embedded — tight constraints, hardware and regulations.

Basic = size and mode. Intermediate × ∏EM of 15 cost drivers, own a 3.2 / 3.0 / 2.8. Detailed: same a, b; phase-wise multipliers. COCOMO II (1997) drops the modes for size factors including schedule stretch.

Worked example — organic, 10 KLOC ✍
  1. 101.05 ≈ 11.220; E = 2.4 × 11.220 = 26.93 person-months (a = 2.4, b = 1.05)
  2. TDEV = 2.5 × (26.93)0.38 = 2.5 × 3.495 = 8.74 months; average staffing = 26.93 ÷ 8.74 ≈ 3.1 people
Second example ✍ Intermediate organic (∏EM = 1), a = 3.2: E = 3.2 × 11.220 = 35.90 ≈ 35.9 person-months, TDEV = 2.5 × 35.90.38 ≈ 9.7 months. If the question supplies its own a, use that a.
Memory trick Read the constants as a story: a harder project ⇒ bigger a (more effort per KLOC) and bigger b (effort grows faster). Bigger d = more time per unit effort. And c = 2.5 everywhere.
Worked example 3 — intermediate mode ✍ Embedded project, 8 KLOC; ∏EM = 0.95 × 0.85 × 1.10 × 1.20 = 1.066; 81.20 ≈ 12.13. E = 2.8 × 12.13 × 1.066 = 2.8 × 12.93 ≈ 36.2 person-months; T = 2.5 × (36.2)0.32 ≈ 7.9 months.
Using it in practice Choose the mode from the constraints, not from the wish — only an avionics display is truly embedded. Re-baseline whenever the specification changes: that is normal management, not failure.
Exam trap Basic COCOMO has three modes — organic, semi-detached, embedded; "distributed" is not one. c = 2.5 in every mode; only a, b and d change. The schedule equation takes E (person-months), never KLOC.

7Risk Analysis & Management

high-yield
Definition A risk is an uncertain event that, if it occurs, affects a project objective (scope, schedule, cost, quality). It is characterised by probability × impact. Before it happens it is a risk; after it happens it is an issue.
CategoryTypical risks
Technicalunfamiliar technology, performance shortfall, security flaw
Organisationalkey staff leave, poor training, weak management, legal change
Project mgmtschedule slip, scope creep, cost overrun, staff turnover
Externalmarket shift, vendor price change, currency, natural disaster

Sommerville folds these into three: technical · organisational · project, with external inside organisational.

The five-step loop

  1. Identify — checklist, brain-storm, Delphi, lessons learned
  2. Assess — probability (very low … very high) × impact
  3. Prioritise — sort by RPI / exposure; keep a written risk register
  4. Respond — pick a strategy, name an owner and a trigger
  5. Monitor — review at every status meeting; re-assess and close

The four responses

ResponseMeaning
Avoidremove the threat — change the plan so it cannot happen
Reduce / mitigatelower probability or impact — prototype, extra testing, training
Transferhand the consequence over — insurance, warranty, subcontract
Acceptdo nothing but hold a contingency reserve and a fallback
Worked example ✍ A production server has P = 0.3 and costs Tk 50,000 to replace if it fails. Risk exposure RE = P × C = 0.3 × 50,000 = Tk 15,000 — that is the amount to hold as contingency. Size the contingency reserve from the sum of the exposures of all high-priority risks, not from one big risk.
The two reserves Management reserve covers the known-unknown risks, inside the baseline. Contingency reserve covers the unknown-unknown risks, outside it.
Memory trick The risk score (P × I) ranks; the risk exposure (P × cost) sizes the reserve. Never manage by exposure alone.

8Scheduling I — CPM, Critical Path & Slack

high-yield
CPM (DuPont + IBM, 1957-58) Draw every activity as a node with its duration written inside in an AON network (activity-on-node), then walk it forward for the earliest times and backward from the deadline for the latest times. The path of zero slack is the critical path, and its length is the project duration.
ActDurPredESEFLSLFSlack
A3—03030
B4A376103
C2A35350
D5C5105100
E1B, D101110110

Forward pass: ES = max(EF of all predecessors); EF = ES + duration. Backward pass: LF = min(LS of all successors); LS = LF − duration. Project finish F = max(EF). Total float = LS − ES = LF − EF.

Worked example ✍ Two paths: A–B–E = 3 + 4 + 1 = 8 d; A–C–D–E = 3 + 2 + 5 + 1 = 11 d ⇒ the critical path is A–C–D–E and the project takes 11 days. E must start by day 10, so B's latest finish is 10 while its earliest finish is 3 + 4 = 7 ⇒ float of B = 10 − 7 = 3 days. Delay B by 4 days and the project still finishes on time.

Dependencies between activities

TypeMeans
FS finish-to-startB starts only when A has finished — the default
SS start-to-startB starts only when A has started
FF finish-to-finishB may finish only when A has finished
SF start-to-finishB may finish only when A has started — rare
Memory trick Name it what happens first → what happens next. F = the first activity is finished before the second begins (FS); S = it has only started.
Exam trap Total float = how long an activity may slip without delaying the project; free float = how long it may slip without delaying an immediate successor. Free float ≤ total float. The critical path is the longest path — "fewest activities" is a red herring.
IT link A build pipeline has the same shape: lint → test → package is a critical chain, a documentation job running in parallel has float, and only shortening the critical chain moves the release date.

9Scheduling II — PERT, Gantt & Control

PERT (US Navy, Polaris programme, 1958) The same network as CPM, but every duration is uncertain, so it is given as three estimates — optimistic o, most likely m, pessimistic p — and converted to an expected time plus a standard deviation.
The two PERT equations
te = (o + 4m + p) ÷ 6  (β-type expected value)
σ = (p − o) ÷ 6  ·  variance = σ²
Actompteσ
A25115.51.50

C47168.02.00
D1353.00.67

Network A→B, A→C, B→D, C→D. Path A–B–D = 14.5 d; path A–C–D = 5.5 + 8 + 3 = 16.5 d ⇒ critical path A–C–D, float of B = 2 d. Project σ = √(1.5² + 2.0² + 0.67²) = √6.69 ≈ 2.59 days — the finish is 16.5 ± 2.6 days.

The Gantt chart and monitoring

Gantt chart (Henry Gantt, 1910s) — bars on a time axis, one row per activity: length = duration, position = start. Great for progress tracking, but it shows no dependencies or float, so it can hide a critical path.

ToolBest forBlind to
Ganttwho is doing what, whendependencies, slack
CPMdeterministic dates, critical pathuncertainty
PERTprobabilistic dates, slippage riskresource loading, cost
Earned value (EVM) PV planned value · EV earned value · AC actual cost. SV = EV − PV · CV = EV − AC · SPI = EV ÷ PV · CPI = EV ÷ AC. PV = 100 000, EV = 85 000, AC = 95 000 ⇒ SV = −15 000, CV = −10 000, CPI = 0.89.
Memory trick Control is not inspection: monitor = observe against the baseline, control = correct the deviation.
