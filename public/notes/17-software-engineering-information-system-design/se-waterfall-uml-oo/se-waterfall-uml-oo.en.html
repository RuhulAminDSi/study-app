SE · Waterfall & UMLWaterfall model

1The Waterfall (Linear Sequential) Model

MCQ + Written
Definition Development as a cascade of phases: each phase is completed, reviewed and signed off before the next starts, and the deliverable of one phase is the only input of the next. Phases do not overlap and a finished phase is not re-opened.
output of n =
only input of n+1
#PhaseMain activityDeliverable
1Requirements analysis & specificationElicitation, analysis, SRS, feasibilitySRS (user + system)
2System & software designArchitecture, data, module, UI designsystem + software design docs
3Implementation (coding)Coding, code review, unit testingsource code, build
4Integration & system testingIntegration, functional testing, fixingtest plan, report, defect log
5DeploymentInstallation, migration, trainingreleased system, manual
6MaintenanceCorrection, adaptation, improvementpatches, updated docs
  • Linear and rigid — one active phase, no overlap
  • Documentation-heavy — every phase ends in a reviewed deliverable
  • Requirement freeze — later changes go through change control
  • Verification is late — feedback sits in the testing phase
Memory trick R-D-C-T-D-M: Requirements → Design → Code → Test → Deploy → Maintenance. You may only go down the falls.
Exam trap Royce's 1970 paper drew verification arrows going back to earlier stages — the feedback-free waterfall is a textbook simplification.
IT link A public-sector e-tender (tender → SRS → fixed-price contract → milestones) is classically waterfall: the buyer must own a frozen scope document before money is committed.

SE · Waterfall & UMLStrengths, weaknesses, V-model

2Strengths, Weaknesses & the Feedback Problem

high-yield
Advantages
  • Simple to plan and manage
  • Clear milestones and deliverables → progress measurable
  • Each phase staffed by specialists
  • Thorough documentation — handover, audit, maintenance
  • Fits small projects with stable requirements (BPO, fixed-price tender)
Disadvantages
  • No overlap → long elapsed time, late working software
  • Changes are costly: re-entering a phase voids every later document
  • Requirement errors surface only in testing
  • The user sees nothing running until the end
  • Poor fit for large, novel or fast-changing systems
The feedback problem Waterfall assumes the requirements can be fully and correctly stated before any code exists. But a user can only judge software by running it, so the first real feedback arrives after most of the budget is spent — and a late change means redoing design, code and tests.
cost of fixing a defect: req 1× · design 5× · code 10× · test 15–50× · production 100–1000×
Where it still fitsWhere it fails
small project · stable requirementsambiguous or volatile requirements
proved technology · documented worklarge, distributed, long-lived systems
fixed-price milestone contractinnovation risk · fast market · heavy UI work
The V-model ✍ Put the same sequential development stages on the descending left arm and the matching test level on the ascending right arm. It fixes where testing is planned, not when feedback arrives. Verification = are we building the product right; validation = are we building the right product. Testing finds that errors exist; debugging corrects them.
Exam trap The V-model does not mean "test early every iteration" — it is still sequential; and the counterpart of requirements is acceptance testing.

SE · Waterfall & UMLUP & Inception

3The Unified Process and Its Inception Phase

high-yield
Unified Process (UP) A use-case-driven, architecture-centric, iterative and incremental process framework created at Rational by Booch, Rumbaugh and Jacobson with Cockburn. Each project tailors it; the Rational Unified Process (RUP) is Rational's packaged version.
PhaseWhat happens in itMilestone
Inceptionbusiness case, vision, initial scope, rough estimate, first risk listthe Vision — "is it worth doing?"
Elaborationmost requirements, the domain model, the architecture prototypethe Architecture baseline
Constructionbuild the rest, refine the design, test continuouslyworking increments
Transitiondeployment, migration, training, support handoverthe released product
Inception The first and shortest phase. Its only question is "should this project start at all?" It fixes the vision, business case, initial scope, a rough estimate and an initial risk list.
  1. Decide the scope and size
  2. Document the business case
  3. Rough-estimate cost and duration
  4. Form the initial risk list
  5. Identify the stakeholders
  6. Define the vision and high-level use cases
Inception activityProduces
Stakeholder identificationusers, clients, sponsors
Requirements elicitationhigh-level needs only
Feasibility studytechnical, operational, economic
Initial risk assessmentrisk list, impact, mitigation
High-level use cases~10–20 cases, no detail
Project estimationrough size, cost, schedule
Outputs of inception Vision & business case · initial risk list · initial high-level use-case model · rough size, cost and schedule. Effort guideline: about 10% of the project effort; the estimate is rough, typically ±30%.

4Inception vs the Waterfall Requirements Phase

written favourite
AspectWaterfall requirementsUP Inception
Scope coveredcomplete, detailed, frozenhigh-level only, incomplete by design
Main outputSRSvision, business case, initial use cases
Timingone long phase before any designshort first phase; elaboration continues it
Accuracyclaims to be exactorder of magnitude, ±30%
Changechange request + impact analysisnormal — the use-case model keeps growing
Risknot explicitly addressedan initial risk list is a first-class output
Testinglater, via the V-modelcontinuous, risk-driven, per iteration

Feasibility: five questions

  • Technical — can it be built with the available technology and skills?
  • Economic — does the benefit beat the cost? (cost-benefit, payback, NPV)
  • Operational — will people use it, and can the organisation run it?
  • Legal — data-protection and e-government compliance
  • Schedule — deliverable in the required time?

The study ends in a go / no-go decision — cancelling a weak project is a legitimate result.

Initial risk assessment

A risk is an uncertain future event with a probability and an impact; exposure = probability × impact. The chain is identify → assess → mitigate → monitor, with mitigation by avoid, reduce, transfer or accept. Inception produces only the first risk list; full risk analysis and COCOMO are in the Project Management notes.

Memory trick Inception = "SCOOPE" — Stakeholders, feasibility, Cost/effort estimate, Output = vision & use cases, Project go/no-go, Elicit only high-level needs.
Exam trap Do not write "Inception replaces the requirements phase" — it only frames requirements; the bulk are elaborated later. And do not call UP "waterfall renamed": UP is iterative, each phase holding many iterations, while waterfall is strictly sequential.
IT link A real project does exactly this: a one- or two-week spike produces a vision note, a handful of use cases and a risk list — then the funding decision is taken.
Rough estimation inside inception ✍ Size the work by function points, use-case points (weight each use case by complexity), analogy or expert judgement; then effort × rate ≈ cost. Inception needs only an order of magnitude — the firm figure arrives after elaboration. COCOMO and the full risk matrix are in the Project Management notes.

SE · Waterfall & UMLUse case model

5The Use Case Model for Requirement Writing

MCQ + Written
Definition A use case is a sequence of transactions that yields a meaningful result with a particular actor (Ivar Jacobson). It abstracts behaviour in the user's language — not a design, a screen or a test case.
ElementWhat it states"Place Order" example
Actora role played by a person or external system, outside the boundary, drawn as a stick figureCustomer; Payment Gateway
Preconditionwhat must already be true — an assumption, never the triggerregistered, logged in, cart not empty
Main flowthe basic sequence that always delivers the goalcheckout → summary → pay → confirm
Alternative flowsvariations, error and exception pathscard declined; stock changed; cancel
Postconditionwhat is guaranteed true after success — a resultorder confirmed, stock reserved
Triggerthe boundary event that starts the use casecustomer clicks "Checkout"
  • Primary actor — whose goal the use case delivers; it drives the system
  • Supporting / secondary actor — provides a service the use case needs (Payment Gateway); a tertiary actor only benefits indirectly (Courier)
  • An actor is a role, not a person: one person may play several actors, one actor several people.
Worked example: "Place Order" ✍ Main flow: ① customer selects Checkout → ② the system shows the summary → ③ the customer enters card details → ④ the gateway authorises → ⑤ the system creates the order, reserves stock and confirms → ⑥ the order ID is shown. Alternative flows: card declined → another card; stock changed → recalculate; cancel → no order.
Exam trap A use case is not a screen, a class or a test case. Name it verb + noun at the user-goal level.
Memory trick Precondition in, Main flow through, Postcondition out. An actor is a role, outside the box.

6Use Case Relations, SSD & Sequence Diagrams

high-yield
RelationshipWhen it is usedDirection & notation
<<include>>mandatory — the base use case always performs the included onebase → included; dashed arrow, open head
<<extend>>optional — added only under a condition; never completes aloneextending → extended
Generalisationa specialisation inherits the flow and adds or overrides stepsspecialised → general; hollow triangle
System Sequence Diagram (SSD) Draws the whole system as one black box: only events crossing the boundary appear. Rules (Cockburn): one event per step, names in verb + noun form, no internal messages, no loops.
SSD for "Place Order" ✍
  1. Customer → System: createOrder(items)
  2. System → Customer: paymentRequired(total)
  3. Customer → System: makePayment(cardDetails)
  4. System → Customer: orderConfirmed(orderId)
A gateway call is inside the box here — that is why an SSD is not a sequence diagram.

Reading a sequence diagram

  • Time flows downward; read each message left → right, then move down.
  • Lifelines = the objects taking part.
  • Numbered messages give the order.
  • Activation bar = focus of control.
  • Filled arrow = synchronous · open arrow = asynchronous · dashed = reply · [guard] = condition.
  • Dot = exists · open circle = created · X = destroyed.
Communication (= collaboration) diagram The same interaction redrawn as a graph of object links, messages numbered on the links: it shows who is connected to whom (structure), not when things happen (time).
Exam trap "Withdraw Cash always performs Authenticate User" → <<include>>. "A discount only for members" → <<extend>>. Same arrow — the direction and the condition tell them apart.

7UML: What Each Diagram Is For

high-yield
UML The OMG standard visual language for specifying, visualising and documenting software, originating at Rational in the late 1980s (Booch, Rumbaugh, Jacobson) and an OMG standard since 1997. UML 2 has 14 diagrams: structural (what exists) and behavioural (what happens).
Structural (7)What it is FOR
Classstatic structure: classes, attributes, operations
Objecta snapshot of instances and their links
Composite Structurehow a classifier is built from parts
Componentmodules, interfaces, dependencies
Deploymentartifacts on hardware nodes and links
Packagegrouping into namespaces / folders
Profilestereotypes tailoring UML to a domain
Behavioural (7)What it is FOR
Use Caseactors and the goals they want from us
Activityworkflow: flow, decisions, swimlanes
State Machinelife of one object: states, events
Sequenceinteraction over time: lifelines + messages
Communicationthe same interaction as an object graph
Interaction Overviewhow interaction diagrams fit together
Timingobject values changing over time
RelationshipMeaning → notation
Association"a knows b"; role, navigability, multiplicity → solid line
Aggregationweak whole–part, parts live alone → hollow diamond
Compositionstrong whole–part, one owner → filled diamond
Dependencyweakest, temporary "uses a" → dashed + open head
Generalisation"is-a": subclass → superclass → solid, hollow △
Realisation"implements" a contract → dashed, hollow △
Exam trap Filled diamond = composition, hollow diamond = aggregation; a hollow triangle is generalisation, not a diamond. "Collaboration diagram" is the old UML 1.x name for the Communication diagram.

SE · Waterfall & UMLOO design

8Designing Objects: Principles, Process & CRC

written favourite
OO principleExactly what it means
Encapsulation
(information hiding)		data and its operations bundled in one class; state private, changed only through the public interface
Abstractionexposing what the object does, not how
Inheritancea subclass inherits and specialises state and behaviour ("is-a")
Polymorphismthe same message, different behaviour, decided at run time

The OO design process

  1. Develop or reuse a design model
  2. Find the design classes for each element
  3. Assign each class its responsibilities (CRC cards)
  4. Assign each class its collaborators
  5. Design collaborations, associations, generalisations
  6. Refine classes; repeat until all behaviour is held

Responsibility = what a class knows (attributes, linked objects) or does (operations); a collaborator is a class that helps fulfil it.

ClassKnows (state)Does (operations)
Customername, email, cartaddToCart(), checkout()
Cartproducts, quantitiescalculateTotal(), createOrder()
OrderorderId, linesconfirm(), generateInvoice()
Paymentmethod, amountprocessTransaction()
Concept vs design class A domain (concept) class is pure information — no operations that calculate — named as a singular common noun. A design class is any class of the design model — implementation-level, with attributes and operations in full detail; it need not be abstract.
Reuse & refactoring Reuse = patterns, inheritance, composition. Refactoring = a behaviour-preserving restructuring of code, in small steps, never mixed with feature work.
Categories of object Entity = the data of the use case · Boundary = what the user touches · Control = the sequencing logic.
Domain model ✍ The domain model is the conceptual representation of the domain's real-world concepts: every domain noun becomes a concept class with its attributes and associations, but no operations — nothing calculates, nothing is implemented. Online shopping: Customer, Order, OrderLine, Product, Payment, data only.
Multiplicity ✍ The number at each end of an association says how many: 1 exactly one · 0..1 zero or one · * or 1..* many. Read it at the far end — Customer 1 — * Order: one Customer places many Orders, so read back each Order is for exactly 1 Customer. Likewise Order 1 — * OrderLine, OrderLine * — 1 Product.
